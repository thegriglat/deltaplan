# Как ведётся работа над Deltaplan (процесс с агентами)

Внутренний документ (не для сайта). Короткая выжимка — в `CLAUDE.md` в корне.

## Роли
- **Пользователь (автор)** — заказчик и автор решений: идеи, выбор между вариантами, границы модели, приёмка. Обсуждает и контролирует через главную сессию. Решает развилки, которые план не закрывает.
- **Главная сессия (глобальный координатор)**:
  - превращает запросы пользователя в планы (сама или через исследователя/планировщика), задаёт вопросы по плану одним списком;
  - на модуль/направление заводит ветку и копию (`dp module new <модуль>`) и запускает **одного координатора модуля** (`dp-coordinator`); мелкие одиночные задачи — сразу исполнителю в своей копии;
  - решения пользователя пишет через `dp decide <модуль> "…" --by user --why "…" --plan` (и в журнал, и в план), ответы на шлюзы — `dp questions` / `dp answer <Qn> "…"`; координатору в сообщении — коротко «см. `dp inbox`» (без пересказа от себя как решения); правки плана и контрактов — `dp plan edit … --commit`;
  - ветки и копии — `dp sync <модуль>` (влить main), `dp merge <ветка> [--push]` (после одобрения пользователя; слияние в main сам обновляет смысловой индекс в фоне, `--no-index` — нет), `dp gc [--remove]` (влитые копии);
  - каждые 30 минут — отчёт о статусе: `dp status --since 30m` (агент `dp-status` — только если нужен разбор зависаний), основа записи дневника — `dp digest --since today`;
  - вливает ветки в `main` после одобрения пользователя, пушит и выпускает версии — по его команде.
- **Координатор модуля** (`dp-coordinator`) — держит план модуля и журнал хода работ (`docs/plan/<модуль>/` через `tools/dp`, раздел «Журнал и задания — tools/dp»), **до запуска исполнителей формулирует контракты** (ниже), раздаёт задачи исполнителям — одна задача = один свежий исполнитель в своей рабочей копии, — принимает по условиям приёмки (`dp accept` + вердикт ревьюера, раздел «Приёмка»), приходит к главной сессии на шлюзах. Сам код не пишет и **не ревьюит** (код и диффы задач не читает).
- **Исполнитель** (`dp-engineer`, `dp-researcher`, `dp-writer`, `dp-mechanic`) — одна задача в рамках контракта, в своей рабочей копии; отчёт по условиям приёмки.
- **Ревьюер** (`dp-reviewer`) — свежий агент с пустым контекстом на одну задачу dp-engineer/dp-researcher после PASS в `dp accept`: читает карточку, план, контракты, отчёт и дифф ветки, выборочно перезапускает проверки; вердикт `accept|rework` с замечаниями — в журнал (`dp review`). Ничего не правит и не коммитит.

## Жизненный цикл
1. Идея (пользователь) → при необходимости исследование или прототип (`dp-researcher`, данные сохраняются).
2. План в `docs/plan/<модуль>.md`: цель, решения пользователя, физика и границы модели, задачи со скоупом, файлами, **условиями приёмки** и оценкой, волны, риски. Вопросы пользователю — одним списком.
3. Ответы пользователя вписываются в план («Решения пользователя (не обсуждаются)»).
4. Ветка `feature/<модуль>` + рабочая копия `~/deltaplan-<модуль>` от `main`; координатор модуля.
5. **Контракты** — до первого исполнителя (ниже).
6. Волны задач (≤ ~4 исполнителя одновременно); у каждой задачи карточка (`dp task new`), своя копия `~/deltaplan-<модуль>-<задача>`, ветка `<модуль>/<задача>` от `feature/<модуль>`; приёмка — `dp accept` → `dp-reviewer` (для engineer/researcher, раздел «Приёмка») → решение координатора, merge в `feature/<модуль>`, прогон затронутых тестов (`dp accept --here`), удаление копии.
7. **Шлюзы**: условие остановки из плана или развилка, которую план не решает, — координатор возвращается с вариантами и рекомендацией; главная сессия спрашивает пользователя; вопрос — `dp decide <модуль> "…" --ask`, ответ — сообщением координатору и `dp decide … --by user --answers Qn` (существенное — и в план).
8. Полёт пилота (сборка, вопросы простым языком) → записать ответ, не шлифовать.
9. Слияние `feature/<модуль>` в `main` после одобрения пользователя; push — по его команде.

## Контракты систем (обязательно для координатора)
Файл `docs/contracts/<модуль>.md` (или раздел плана) — по каждому стыку между задачами/системами:
- владелец (задача) и потребители;
- точный интерфейс: сигнатуры, формат данных (поля, единицы, системы координат, порядок осей, тип чисел), поведение при отсутствии данных, инварианты;
- версия контракта.
Правила: фиксировать то, что уже есть в коде, а не придумывать заново; расхождения между задачами выявить и раздать; исполнитель работает в рамках контракта; **менять интерфейс — только через координатора**: версия +1, что изменилось, уведомление всех потребителей, их правка в том же шаге. **Контрактные тесты** (headless) проверяют форму данных на стыке и ломаются, если формат поменяли без правки контракта.

## Приёмка (координатор не ревьюит сам)
Ревью съедало контекст координатора (~40 % — чтение кода при сверке, ~11 % — `git diff/show`), поэтому:
1. `dp report <ID> --show` → `dp accept <ID>` — детерминированные проверки карточки.
2. FAIL → сразу на доработку (новый исполнитель или тот же с итогом `dp accept`), ревьюер не нужен.
3. PASS: задачи `dp-writer`, `dp-mechanic` — принято (`dp accept` пишет `accepted`). Задачи `dp-engineer`, `dp-researcher` — `dp accept` пишет `checked`, дальше **по риску** (решение пользователя — беречь токены):
   - **без ревьюера** (по умолчанию): координатор читает только отчёт (`dp report <ID> --show`: сводка, проверки, поле `uncertain` — места, где исполнитель не уверен, и что он проверил) и `git diff --stat` (файлы в скоупе карточки). Сомнения исполнителя выглядят разумно и закрыты проверками → `dp event <ID> accepted --note "по отчёту"`; нет — вопрос исполнителю или ревьюер.
   - **свежий `dp-reviewer`** — только если: физика/численные схемы/GPU, стык контракта (формат данных между задачами), задача вернулась на доработку второй раз, или сомнения в `uncertain` серьёзные. Ревьюер разбирает места из `uncertain`, стыки контрактов и формулы, остальное — по `--stat` и выборочно 1–2 места; полное чтение диффа — только для сложной физики (`model: fable`). Задание ревьюеру — только: «Ревью задачи <ID>», копия и ветка задачи. Историю, свои догадки и пересказ отчёта не передавать — ревьюер соберёт всё из `dp`.
4. Ревьюер пишет вердикт `dp review <ID>` (событие `reviewed`, файл `tasks/<ID>.review.json`; в `dp status` — `rev:rework 2B`).
5. Координатор решает по вердикту: `accept` → `dp event <ID> accepted --note "по ревью"` и слияние; `rework` → замечания (`dp review <ID> --show`) — исполнителю на доработку, после неё снова `dp accept` и свежий ревьюер. Спорное замечание — вопрос ревьюеру или исполнителю (SendMessage), а не чтение кода самим.

**Координатору запрещено** читать код, диффы (`git diff/show`) и логи задачи ради ревью — это работа `dp-reviewer`. Разрешено: `dp status/log/report --show/review --show`, итог `dp accept`, `git diff --stat` при слиянии.

## Общие правила (для всех агентов)
- Агенту остаются только задачи, которые детерминированным скриптом не решить, — подумать: спроектировать, решить, разобрать причину, написать текст/код. Всё, что можно сделать скриптом (поиск, сводки, проверки, перенос, слияние, отчёты по числам), — делает `tools/dp` или скрипт задачи; повторяющуюся ручную операцию — оформить командой dp (через обратную связь).
- Детерминированное — командами dp: поиск и работа с планами, журналами, документами, ветками — только через `tools/dp` (`dp search`, `dp search --sem`, `dp plan`, `dp docs …`, `dp log`, `dp status`, `dp task …`, `dp sync/merge`); свои grep/python-скрипты для этого не писать (исключение — код игры и исследовательский код задачи). Не хватило команды — обойти один раз и сразу записать обратную связь (`dp event <модуль> note --note "dp: …"` или поле dp_feedback).
- **Физика прежде «нравится»**: корректность в заявленных границах модели; параметры — с физическим смыслом, из физики/измерений; в документах — какие законы и приближения учтены и чего модель не умеет. Отзывы пилотов — проверка после, не подгонка (в калибровку не входят; расхождение → «Границы модели»).
- **Не шлифовать**: «несовершенство = реализм»; мелкие визуальные детали — не больше 2 попыток, берём лучшую.
- **Всё можно менять**: пользователей нет — никакой совместимости со старыми настройками, форматами, флагами (и для скриптов/тестов), миграций, «привыкли к UI».
- **Godot** — только с временным профилем: `XDG_DATA_HOME=$(mktemp -d) godot …`. Godot с окном переписывает `project.godot` (шапка «It's best edited using the editor UI…», перестановка ключей) — такое не коммитить, возвращать `git checkout -- project.godot`; намеренные правки — только свои строки.
- **Тесты**: headless — `tests/run_tests.tscn` (`--filter=подстрока`), до 8 процессов параллельно; известные падения под нагрузкой (порог времени) и занятый порт 8080 — не регрессии. GPU-тесты — `tools/gpu_tests.sh` (окно маленькое). **Общие замки:** замок GPU — только для долгих GPU-счётов (обучение нейросетей, исследовательские расчёты на CuPy) — `dp lock gpu <имя> -- <команда>` или `dp job --lock gpu start <имя> <таймаут_с> <команда>`; тесты отрисовки, GPU-тесты, скриншоты, сборки — без замка GPU; тяжёлые CPU-прогоны (пачки тестов, индексация на CPU, подготовка наборов) — `dp lock cpu …` (семафор на N слотов, `DP_CPU_SLOTS`); кто держит — `dp lock status`. Долгие запуски — `dp job start|wait|status|stop`.
- **Коммиты** — только свои файлы: `git add <пути> && git commit -m "..." -- <пути>` (индекс общий); сообщения по-русски + строка `Claude-Session: …` из системного напоминания; коммитить на логичных шагах; **не пушить**.
- **Скриншоты** — всегда в главную копию: `/home/greg/deltaplan/build/screenshots/<задача>/` (абсолютный путь; не в `build/` рабочей копии задачи или модуля — `build/` не под git и пропадает при удалении копии; пользователь смотрит всё из одной папки), каждая задача в свою подпапку (номера с 01 внутри подпапки, русские имена); в корень `build/screenshots/` не класть. Принятые видимые изменения (JPEG q88 для сайта) к версии — в `site/content/releases/<версия>/screenshots/`.
- **CHANGELOG.md** — функционально, по-русски, в «В работе» при приёмке.
- **Публичные тексты** (сайт, itch, docs/, CHANGELOG): родители — только «родители автора — пилоты, это дало старт идее»; иначе «пилот». Семейное и личное — не публиковать.
- **Пачки запусков** (подбор параметров, замеры, серии тестов/кадров, повторы для частоты): не циклы «запустил → посмотрел → поправил», а сразу весь план одним скриптом → один фоновый прогон с записью по строке на запуск (csv/json, продолжение с места после прерывания) → одно ожидание до конца (без сон-циклов с чтением вывода) → итог одним скриптом (таблица, графики) → разбирать только итог. Большой план — сначала оценить время по 1–2 пробным точкам. Токены тратятся на каждый шаг агента, а не на время расчёта.
- **Массовые численные данные — с контрактом формата** (решение пользователя 04.10: компактно, контракт данных, воспроизводимость — фиксированная схема не даёт формату расползаться между задачами и агентами). Контракт — `docs/contracts/<модуль>.md` с версией + контрактный тест (имена, формы, типы, единицы, атрибуты).
  - **Однородные массивы** (корпуса рельефов, таблицы условий, поля решателя, выборки) — **HDF5**: группы и наборы данных, int16/float16 со смещением и масштабом в атрибутах, чанки + сжатие (gzip/lzf/blosc), метаданные (версии, зерно, шаг сетки) — атрибутами. Параллельная генерация — каждый процесс свой файл, общий вид — виртуальный набор (VDS) или слияние; запись во временный файл и переименование в конце. Файл пишется один раз и дальше только читается.
  - **Разнородные записи и сообщения** (метаданные мест, манифесты, сетевой протокол) — **protobuf** с `.proto` в репозитории; массивы внутри — `bytes`, не `repeated float`.
  - Сырые промежуточные данные после упаковки удалять (места на диске мало). Не в этих форматах: журналы и логи (jsonl), небольшие сводки и конфиги (json/csv/md), таблицы для чтения человеком.
- **Долгие запуски** (godot, python, сборки, прогоны > 1–2 мин) — фоном средствами агента (`run_in_background`, о конце придёт уведомление) или `/home/greg/deltaplan/tools/dp job start <имя> <таймаут_с> <команда…>` → `wait <имя>` (абсолютный путь — работает из любой копии). **Не** ждать и не убивать по `pgrep -f`/`pkill -f` — они находят сам цикл ожидания и свою оболочку; чужие процессы не трогать (подробно — «Наблюдение»).
- **Бережливость токенов** (решение пользователя): токены тратит каждый агент и каждый его шаг, а не время расчёта.
  - Слои: небольшой модуль (2–3 задачи) — без координатора, главная сессия даёт задание исполнителю сама; координатор — для больших модулей.
  - Не останавливать и не перезапускать агентов ради новых правил — передать сообщением (SendMessage); перезапуск = повторное чтение всего контекста.
  - Модели: исполнители по умолчанию Sonnet; `model: opus` — только для сложной физики/GPU/численных схем (решает координатор при запуске); Fable — планирование и ревью сложной физики.
  - **Картинки** (≈1,5 тыс. токенов каждая) — генерировать и открывать **только для 3D-моделей** (вид модели, крыла, объекта в игре) **или по запросу пользователя**. Графики для проверки не нужны: проверка — числами и таблицами из скрипта; графики к исследованию можно сохранять в файлы для статьи/пользователя, но агенты их не открывают.
  - План и контракты — разделами (`dp plan <модуль> <раздел>`), не целиком; большие планы делить по этапам.
  - Исполнитель в отчёте перечисляет сомнения (`uncertain`) — это фокус приёмки вместо чтения всего диффа.
- **Данные исследований** сохранять и коммитить (картинки, таблицы, команды воспроизведения); крупное — локально, путь в README.
- **Не выдумывать**: числа — из замеров, результаты агентов — из их отчётов.
- Настройки Claude, права, CLAUDE.md и `.claude/` — не менять (кроме случаев, когда это задача).

## Журнал и задания — `tools/dp`
Справка — `tools/dp.md` (`tools/dp -h`); вызывать `/home/greg/deltaplan/tools/dp` (старый `tools/dp` в копии сам перезапускается из главной копии, `DP_NO_REEXEC=1` — отключить). ID задачи — `<КОД>-<n>[буква]` (`^[A-Z]{2,4}-\d+[a-z]?$`, напр. NN-7, NN-7a); КОД — поле `code` в `module.json` (2–4 заглавные латинские, уникален; `dp init/module new --code`); `dp task new <модуль>` без ID берёт следующий номер; `T-<n>` — реестр TODO.md, код T зарезервирован; контракты (C1, П1, N1…) — не задачи; старые ID не переименовывать. Журнал модуля — `docs/plan/<модуль>/`: карточки, отчёты, `events.jsonl`, `decisions.jsonl`; события и решения **только дописываются** командами `dp` — журнал руками и целиком не переписывать (Write/python-вставки), md-вид для людей и дневника — `dp render <модуль>`. Старые `*_progress.md` идущих модулей ведутся как были; новые модули — через `dp`.
- Карточка задачи — `dp task new` (скилл `start-to-do`): цель, контракты с версиями, копия/ветка, скоуп, «не трогать», проверки приёмки `{name, cmd|tests, expect}`. Исполнитель читает `dp task show <ID>` и нужные разделы плана `dp plan <модуль> <раздел>`, а не весь план.
- События: `dp event <ID> started|blocked|cancelled|merged|note`; отчёт исполнителя — `dp report <ID> < отчёт.json` (схема — `dp report --template`, неверный не примется) — пишет в копию модуля, это единственное исключение из «чужие копии не трогать»; приёмка — `dp accept <ID>` (таблица PASS/FAIL, логи в `build/dp/<ID>/`, итог — событие), а не чтение кода и логов глазами; ревью — `dp-reviewer` → `dp review <ID>` (раздел «Приёмка»); решения — `dp decide`.
- Статус — `dp status [<модуль>]` (несколько строк: задачи, ветки, «тихо» > 40 мин, вопросы пользователю) вместо опросов `git log/status`; `git diff/show` — только по делу.
- Перед новой работой — `dp search <текст|regex> [--module М]` по прошлым модулям (карточки, отчёты, события, решения; старые журналы переведены в dp); по смыслу — `dp search --sem "запрос"` (docs, исследования, дневник, журналы; нужен `dp index`).
- В начале каждого шага координатор читает `dp inbox <модуль>` (новые решения пользователя, ответы, правки плана, заметки; метка чтения — `docs/plan/<модуль>/.read_<читатель>`, в .gitignore); пусто — «нового нет».
- Коммит журнала — координатор, своими путями: `git add docs/plan/<модуль> && git commit -m "…" -- docs/plan/<модуль>`.
- **Обратная связь по `dp`** — обязательно в конце работы: исполнитель — поле `dp_feedback` отчёта, координатор — `dp event <модуль> note --note "dp: …"` (чего не хватило, что неудобно; можно «нет»).

## Документация: куда что класть (`docs/INDEX.md`)

Точка входа — `docs/INDEX.md` (путь — тип — статус — summary). «Что мы знаем про X»: `dp docs findings X` (реестр выводов `docs/registry/findings.md`), `dp docs find [--type T] [--module M] текст`, `dp search`, `dp search --sem`; не grep.
- `docs/guide/` — как устроена система (kebab-case), `docs/contracts/<модуль>.md` — контракты стыков, `docs/research/` и `tools/research/<тема>/README.md` — исследования (вывод, данные, где применено), `docs/plan/` — только живые и отложенные планы (`status: idea|postponed`), `docs/archive/plan/` — планы и журналы закрытых работ (не удалять, `git mv`; выводы перед архивированием — в `findings.md`).
- Каждый md в `docs/`, паспорт `tools/research/**/{README,summary}.md`, TODO.md и REQUIREMENTS.md начинается с frontmatter: `type` (guide|plan|contract|research|reference|journal|registry), `status` (active|idea|postponed|closed|superseded), `module`, `updated`, `summary` (1 строка), `related`; research — ещё `conclusion`, `data`, `applied_in`; contract — `contracts: [{id, version}]`. Новому файлу — `dp docs init`.
- Перед коммитом docs — `dp docs check` (frontmatter, живые ссылки, файл > 40 КБ — разбить). Реестры `docs/INDEX.md`, `docs/registry/{research,contracts,decisions}.md` генерирует `dp docs index` — руками не править; `findings.md` пишется вручную.
- Просмотр в Obsidian — `docs/obsidian.md`.

## Типы агентов (`.claude/agents/`)
| Тип | Модель / усилие | Для чего |
|---|---|---|
| `dp-coordinator` | Opus / high | координатор модуля: план, контракты, копии, приёмка, шлюзы; скилл `start-to-do`; сам не ревьюит |
| `dp-engineer` | Sonnet / medium (сложная физика, GPU — `model: opus`) | код игры, физика, GPU, тесты к своему коду |
| `dp-researcher` | Sonnet / medium (сложная физика — `model: opus`) | прототипы (Python/CuPy), замеры, литература и данные, веб |
| `dp-writer` | Sonnet / medium | документы, страницы сайта, дневник, тексты для пилотов |
| `dp-mechanic` | Haiku / low | механическое: замены по шаблону, прогоны тестов/сборок, скриншоты готовыми инструментами, слияния без конфликтов |
| `dp-reviewer` | Opus / medium (сложная физика — Fable) | ревью по риску (физика, стыки контрактов, повторная доработка) после PASS в `dp accept`, пустой контекст; фокус — `uncertain` исполнителя; только чтение и перезапуск проверок; вердикт — `dp review` |
| `dp-status` | Haiku / low | сбор статуса агентов, веток и процессов — короткая сводка для главной сессии |
Модель можно переопределить при запуске (например, `dp-researcher` на Sonnet для поиска литературы). Исполнители и ревьюер агентов не порождают — только координатор.

## Наблюдение
- Каждые 30 минут главная сессия запускает `dp-status` (или сама `tools/dp status`) и пересказывает пользователю: что сделано (коммиты), кто работает над чем, зависшие, вопросы, ждущие решения.
- Зависание: у агента нет коммитов, событий (`dp status` помечает «⚠тихо») и изменений файлов > 30–40 мин, или процесс (godot/python/цикл ожидания) идёт дольше обычного. Разобраться (что делает, чей процесс), сообщить; долгие запуски — только так, без опроса по имени процесса (`pgrep -f` находит сам цикл ожидания, `pkill -f` — свою же оболочку):
  1. свой запуск — фоном средствами агента (`run_in_background`): о конце сообщают, ждать не надо;
  2. если нужен код выхода и ожидание в скрипте — `/home/greg/deltaplan/tools/dp job start <имя> <таймаут_с> <команда…>` → `/home/greg/deltaplan/tools/dp job wait <имя>` (ждёт PID через `tail --pid`, печатает код и хвост лога; таймаут обязателен — код 124);
  3. чужой процесс — ждать по PID (`tail --pid=PID -f /dev/null` с `timeout`), найдя его один раз; убивать — только по PID после `readlink /proc/PID/cwd` (своя копия).

## Шаблоны
**Задание координатору**: где работать (копия, ветка), план и связанные документы, что уже сделано (коммиты), решения пользователя, как вести (волны, копии на задачу, контракты до исполнителей, журнал, шлюзы, «стоп»), правила — ссылкой на этот документ, что вернуть в отчёте.

**Задание исполнителю** (скилл `start-to-do`): карточка `dp task new` + вывод `dp task show <ID>` (задача, копия и ветка, контракты с версиями, скоуп, не трогать, проверки приёмки, отчёт через `dp report`); особенности задачи — текстом рядом.

**Отчёт исполнителя/координатора**: что сделано (файлы, коммиты), числа приёмки, что не вышло и почему, открытые вопросы, как проверить, 5–8 путей к картинкам, обратная связь по `dp`. Исполнитель — `dp report <ID>` (те же поля в JSON) и коротко текстом координатору.

**Задание ревьюеру**: «Ревью задачи <ID>», копия и ветка задачи (модель — параметром запуска). Больше ничего: ни истории, ни пересказа отчёта, ни подсказок, что искать.

**Отчёт на шлюзе**: условие/развилка, варианты с ценой и последствиями, рекомендация, что ждёт решения, что продолжается независимо.
