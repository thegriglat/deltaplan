# Как ведётся работа над Deltaplan (процесс с агентами)

Внутренний документ (не для сайта). Короткая выжимка — в `CLAUDE.md` в корне.

## Роли
- **Пользователь (автор)** — заказчик и автор решений: идеи, выбор между вариантами, границы модели, приёмка. Обсуждает и контролирует через главную сессию. Решает развилки, которые план не закрывает.
- **Главная сессия (глобальный координатор)**:
  - превращает запросы пользователя в планы (сама или через исследователя/планировщика), задаёт вопросы по плану одним списком;
  - на модуль/направление заводит ветку и рабочую копию и запускает **одного координатора модуля** (`dp-coordinator`); мелкие одиночные задачи — сразу исполнителю в своей копии;
  - пересылает координаторам решения пользователя, передаёт пользователю шлюзы и вопросы (без пересказа от себя как решения);
  - каждые 10 минут — отчёт о статусе (через `dp-status`), лимит, зависшие;
  - вливает ветки в `main` после одобрения пользователя, пушит и выпускает версии — по его команде.
- **Координатор модуля** (`dp-coordinator`) — держит план модуля и журнал хода работ (`docs/plan/<модуль>_progress.md`), **до запуска исполнителей формулирует контракты** (ниже), раздаёт задачи исполнителям — одна задача = один свежий исполнитель в своей рабочей копии, — принимает по условиям приёмки (сам перепроверяет тесты/числа), приходит к главной сессии на шлюзах. Сам код почти не пишет.
- **Исполнитель** (`dp-engineer`, `dp-researcher`, `dp-writer`, `dp-mechanic`) — одна задача в рамках контракта, в своей рабочей копии; отчёт по условиям приёмки.

## Жизненный цикл
1. Идея (пользователь) → при необходимости исследование или прототип (`dp-researcher`, данные сохраняются).
2. План в `docs/plan/<модуль>.md`: цель, решения пользователя, физика и границы модели, задачи со скоупом, файлами, **условиями приёмки** и оценкой, волны, риски. Вопросы пользователю — одним списком.
3. Ответы пользователя вписываются в план («Решения пользователя (не обсуждаются)»).
4. Ветка `feature/<модуль>` + рабочая копия `~/deltaplan-<модуль>` от `main`; координатор модуля.
5. **Контракты** — до первого исполнителя (ниже).
6. Волны задач (≤ ~4 исполнителя одновременно); у каждой задачи своя копия `~/deltaplan-<модуль>-<задача>`, ветка `<модуль>/<задача>` от `feature/<модуль>`; приёмка — merge в `feature/<модуль>`, прогон затронутых тестов, удаление копии.
7. **Шлюзы**: условие остановки из плана или развилка, которую план не решает, — координатор возвращается с вариантами и рекомендацией; главная сессия спрашивает пользователя; ответ — сообщением координатору и в план/журнал.
8. Полёт пилота (сборка, вопросы простым языком) → записать ответ, не шлифовать.
9. Слияние `feature/<модуль>` в `main` после одобрения пользователя; push — по его команде.

## Контракты систем (обязательно для координатора)
Файл `docs/<модуль>_contracts.md` (или раздел плана) — по каждому стыку между задачами/системами:
- владелец (задача) и потребители;
- точный интерфейс: сигнатуры, формат данных (поля, единицы, системы координат, порядок осей, тип чисел), поведение при отсутствии данных, инварианты;
- версия контракта.
Правила: фиксировать то, что уже есть в коде, а не придумывать заново; расхождения между задачами выявить и раздать; исполнитель работает в рамках контракта; **менять интерфейс — только через координатора**: версия +1, что изменилось, уведомление всех потребителей, их правка в том же шаге. **Контрактные тесты** (headless) проверяют форму данных на стыке и ломаются, если формат поменяли без правки контракта.

## Общие правила (для всех агентов)
- **Физика прежде «нравится»**: корректность в заявленных границах модели; параметры — с физическим смыслом, из физики/измерений; в документах — какие законы и приближения учтены и чего модель не умеет. Отзывы пилотов — проверка после, не подгонка (в калибровку не входят; расхождение → «Границы модели»).
- **Не шлифовать**: «несовершенство = реализм»; мелкие визуальные детали — не больше 2 попыток, берём лучшую.
- **Всё можно менять**: пользователей нет — никакой совместимости со старыми настройками, форматами, флагами (и для скриптов/тестов), миграций, «привыкли к UI».
- **Godot** — только с временным профилем: `XDG_DATA_HOME=$(mktemp -d) godot …`. Godot с окном переписывает `project.godot` (шапка «It's best edited using the editor UI…», перестановка ключей) — такое не коммитить, возвращать `git checkout -- project.godot`; намеренные правки — только свои строки.
- **Тесты**: headless — `tests/run_tests.tscn` (`--filter=подстрока`), до 8 процессов параллельно; известные падения под нагрузкой (порог времени) и занятый порт 8080 — не регрессии. GPU-тесты — `tools/gpu_tests.sh` (окно маленькое).
- **Коммиты** — только свои файлы: `git add <пути> && git commit -m "..." -- <пути>` (индекс общий); сообщения по-русски + строка `Claude-Session: …` из системного напоминания; коммитить на логичных шагах; **не пушить**.
- **Скриншоты** — каждая задача в свою подпапку `build/screenshots/<задача>/` (номера с 01 внутри подпапки, русские имена); в корень `build/screenshots/` не класть. Принятые видимые изменения (JPEG q88 для сайта) к версии — в `site/content/releases/<версия>/screenshots/`.
- **CHANGELOG.md** — функционально, по-русски, в «В работе» при приёмке.
- **Публичные тексты** (сайт, itch, docs/, CHANGELOG): родители — только «родители автора — пилоты, это дало старт идее»; иначе «пилот». Семейное и личное — не публиковать.
- **Пачки запусков** (подбор параметров, замеры, серии тестов/кадров, повторы для частоты): не циклы «запустил → посмотрел → поправил», а сразу весь план одним скриптом → один фоновый прогон с записью по строке на запуск (csv/json, продолжение с места после прерывания) → одно ожидание до конца (без сон-циклов с чтением вывода) → итог одним скриптом (таблица, графики) → разбирать только итог. Большой план — сначала оценить время по 1–2 пробным точкам. Токены тратятся на каждый шаг агента, а не на время расчёта.
- **Данные исследований** сохранять и коммитить (картинки, таблицы, команды воспроизведения); крупное — локально, путь в README.
- **Не выдумывать**: числа — из замеров, результаты агентов — из их отчётов.
- Настройки Claude, права, CLAUDE.md и `.claude/` — не менять (кроме случаев, когда это задача).

## Типы агентов (`.claude/agents/`)
| Тип | Модель / усилие | Для чего |
|---|---|---|
| `dp-coordinator` | Opus / high | координатор модуля: план, контракты, копии, приёмка, шлюзы; скилл `start-to-do` |
| `dp-engineer` | Opus / medium | код игры, физика, GPU, тесты к своему коду |
| `dp-researcher` | Opus / medium | прототипы (Python/CuPy), замеры, литература и данные, веб |
| `dp-writer` | Sonnet / medium | документы, страницы сайта, дневник, тексты для пилотов |
| `dp-mechanic` | Haiku / low | механическое: замены по шаблону, прогоны тестов/сборок, скриншоты готовыми инструментами, слияния без конфликтов |
| `dp-status` | Haiku / low | сбор статуса агентов, веток, процессов и лимита — короткая сводка для главной сессии |
Модель можно переопределить при запуске (например, `dp-researcher` на Sonnet для поиска литературы). Исполнители агентов не порождают — только координатор.

## Наблюдение и лимиты
- Каждые 10 минут главная сессия запускает `dp-status` и пересказывает пользователю: что сделано (коммиты), кто работает над чем, зависшие, лимит.
- Зависание: у агента нет коммитов, записей в журнале и изменений файлов > 30–40 мин, или процесс (godot/python/цикл ожидания) идёт дольше обычного. Разобраться (что делает, чей процесс), сообщить; долгие запуски — только так, без опроса по имени процесса (`pgrep -f` находит сам цикл ожидания, `pkill -f` — свою же оболочку):
  1. свой запуск — фоном средствами агента (`run_in_background`): о конце сообщают, ждать не надо;
  2. если нужен код выхода и ожидание в скрипте — `tools/job.sh start <имя> <таймаут_с> <команда…>` → `tools/job.sh wait <имя>` (ждёт PID через `tail --pid`, печатает код и хвост лога; таймаут обязателен — код 124);
  3. чужой процесс — ждать по PID (`tail --pid=PID -f /dev/null` с `timeout`), найдя его один раз; убивать — только по PID после `readlink /proc/PID/cwd` (своя копия).
- Недельный лимит аккаунта (только для этого проекта — аккаунт общий с основной работой): 80 % — предупредить пользователя; 85 % — «стоп» координаторам: закоммитить наработки, записать состояние и как продолжить в журнал, остановиться; продолжить после сброса окна (1–2 дня). Фоновый наблюдатель — скрипт, опрашивающий usage API раз в 10 мин.

## Шаблоны
**Задание координатору**: где работать (копия, ветка), план и связанные документы, что уже сделано (коммиты), решения пользователя, как вести (волны, копии на задачу, контракты до исполнителей, журнал, шлюзы, «стоп»), правила — ссылкой на этот документ, что вернуть в отчёте.

**Задание исполнителю** (скилл `start-to-do`): задача и её место в плане; рабочая копия и ветка; контракты стыков задачи (ссылки и версии); скоуп и ключевые файлы; условия приёмки из плана; что не трогать; правила — ссылкой; формат отчёта.

**Отчёт исполнителя/координатора**: что сделано (файлы, коммиты), числа приёмки, что не вышло и почему, открытые вопросы, как проверить, 5–8 путей к картинкам.

**Отчёт на шлюзе**: условие/развилка, варианты с ценой и последствиями, рекомендация, что ждёт решения, что продолжается независимо.
