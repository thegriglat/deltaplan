# start-to-do — запуск задачи исполнителем

Аргумент: номер/название задачи из плана модуля (например `AM-07б`).

## 1. Задача и контракты
- Найти задачу в плане модуля: `tools/dp plan <модуль>` (оглавление) → `tools/dp plan <модуль> <раздел>`: скоуп, ключевые файлы, условия приёмки, оценка, зависимости.
- Стыки задачи: по `docs/<модуль>_contracts.md` (`tools/dp plan <модуль> --contracts <раздел>`) — какие контракты задача использует или поставляет, их версии. Нет контракта для нового стыка — **сначала описать** (владелец, потребители, интерфейс, единицы, инварианты, версия) и добавить контрактный тест; расхождения с кодом — записать и раздать.
- Зависимости готовы? Если нет — может ли задача работать против контракта на подставных данных (поля из файлов, заглушки)? Иначе — не запускать.

## 2. Рабочая копия
```
git -C <копия модуля> worktree add ~/deltaplan-<модуль>-<задача> -b <модуль>/<задача> feature/<модуль>
```
(от актуальной ветки модуля, после вливания уже принятого). Первый запуск Godot в новой копии — `godot --headless --path . --import`.

## 3. Тип исполнителя
| Работа | Тип |
|---|---|
| код игры, физика, GPU, UI, сеть | `dp-engineer` |
| прототип, эталон, замеры, литература/данные | `dp-researcher` |
| документы, страницы сайта, тексты | `dp-writer` |
| замены по шаблону, прогоны, скриншоты готовыми инструментами | `dp-mechanic` |
Модель можно переопределить (`model` в Agent), если задача явно проще или сложнее типа. Повтор неудачной задачи — новый исполнитель с более чёткой спецификацией (можно `fable`).

## 4. Карточка и задание
Карточка — `tools/dp task new` (справка `tools/dp.md`); проверки приёмки — из плана, исполняемыми командами:
```
tools/dp task new <модуль> <ID> --type dp-engineer --title "…" --goal "1–2 фразы, зачем" --plan-ref "<заголовок раздела>" \
  --contract <имя>@<версия> --scope <путь> --dont-touch <путь> --test <фильтр тестов> \
  --check <имя> "<команда>" "<exit=0 | re:… | num:(…) <=X>"
```
(копия и ветка по умолчанию — `~/deltaplan-<модуль>-<ID>`, `<модуль>/<ID>`; длинное — `--from card.json` или правкой JSON карточки.)
Задание исполнителю = вывод `tools/dp task show <ID>` + особенности задачи текстом (GPU-замок, большие данные — где лежат, скриншоты — в `/home/greg/deltaplan/build/screenshots/<задача>/`). Отчёт исполнитель сдаёт `tools/dp report <ID>` и коротко текстом, в конце — `dp_feedback`.

## 5. Журнал
`tools/dp event <ID> started --note "<тип>, <копия>"`; карточку и события коммитит координатор: `git add docs/plan/<модуль> && git commit -m "…" -- docs/plan/<модуль>`.

## 6. Приёмка (после отчёта)
Координатор **не читает код, диффы и логи задачи** — ревью делает `dp-reviewer`.
1. `tools/dp report <ID> --show` → `tools/dp accept <ID>` (в копии задачи; таблица PASS/FAIL).
2. FAIL → на доработку, ревьюер не нужен.
3. PASS у `dp-writer`/`dp-mechanic` → событие `accepted`, дальше п. 5.
4. PASS у `dp-engineer`/`dp-researcher` → событие `checked`; запустить свежего `dp-reviewer` (сложная физика — `model: fable`) с заданием ровно: «Ревью задачи <ID>. Копия <путь>, ветка <ветка>.» — без истории и пересказа отчёта. Вердикт — в журнале: `tools/dp review <ID> --show`. `accept` → `tools/dp event <ID> accepted --note "по ревью"`; `rework` → замечания исполнителю (новому или тому же), после доработки снова п. 1 и свежий ревьюер. Спорное — вопрос ревьюеру/исполнителю.
5. Влить `<модуль>/<ID>` в `feature/<модуль>`, `tools/dp accept <ID> --here --commit <слияние>` (затронутые тесты на ветке модуля), `git worktree remove` и удалить ветку, `tools/dp event <ID> merged`; решения по ходу — `tools/dp decide`. Модуль со старым `<модуль>_progress.md` — журнал как был.
