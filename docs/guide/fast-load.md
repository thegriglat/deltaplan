# Загрузка места (после fast-load)

Как загрузка места устроена сейчас. Контракты — `docs/contracts/fast-load.md` (FL-К1 кеш поля, FL-К2 общие данные места, FL-К3 формат замера); замеры — `tools/research/load_profile/final.md`. Правило потоков — `docs/contracts/perf.md` PF-К4: рабочий поток работает на снимке или данных только для чтения, дерево сцены не трогает; результат подменяется на главном потоке целиком.

## Порядок этапов

1. Рельеф (`TerrainRelief`, слои высот, меш, деревья, трава) — как в `docs/guide/terrain.md`. Модели пород деревьев грузятся в фоне (`load_threaded_request` в начале `load_location`/`load_point`), сцена породы разбирается один раз, а не по разу на каждый из 40 вариантов (этап trees на Онгудае 3,4 → 1,3 с).
2. `WorldLink.link` собирает **`PlaceData`** (FL-К2) один раз: слои высот, участки застройки, `OsmData`, один план домов `VillagePlacer.plan` с домами OSM, `height_at(x, z)` без узлов сцены. Маска просек и `WorldObjects` берут данные только из него. Ключ кеша `VillagePlacer` — из данных места (`loc_key`, `BuiltPatches.data_key()`, конфиг, число домов OSM), не из `get_instance_id()`.
3. Старт выбирается **до** объектов. Поле воздуха (запечённое → кеш → расчёт) идёт фоном одновременно с объектами; `PlaceData` и маска просек — в `WorkerThreadPool` (растр долей застройки считается на главном потоке до задачи). Пока поле считается, планер и препятствия у старта нужны ботам — они уже готовы.
4. Источники термиков (`AirThermals.build`) считаются в пуле сразу по готовности поля; расстановка термиков и сетка поиска строятся порциями по 40 мс за кадр (`Atmosphere.begin_load_refresh` / `load_refresh_step`), вид ботов — по одному на кадр. Полёт начинается только после готовности термиков.
5. Слой OSM (земля города, дороги, слой «для пилота», дома OSM) и дома посёлков: расчёт в пуле (массивы, `Transform3D`, свой `ObstacleIndex`, высота через `PlaceData.height_at`), узлы собираются на главном потоке шагами по тайлу.
6. Подготовка областей воздуха: снимок поверхности — задача пула (на главном потоке остаётся ~10 мс); `block_mean` и `surface_flux` — полосами строк в пуле; грубая (1200 м) и основная (400 м) области и оба решения `PreparedCase.prepare` — параллельно. Поле на GPU с прежним путём совпадает побитно (u, v, w, θ, hc); этап wind короче примерно на 2 с. `Game._load_air_field` ждёт снимок опросом по кадрам.

Вложенные параллельные циклы из задач пула идут через `PoolFor.run` (`scripts/core/pool_for.gd`): из пула — задачи высокого приоритета с совместным ожиданием, иначе — прежняя группа. Причина: в Godot 4.7 `wait_for_group_task_completion` из рабочего потока — семафор без помощи очереди, при пуле 2 потока загрузка вставала после dem (воспроизведено и на `main`).

## Кеш поля воздуха

- Код — `scripts/atmosphere/air_field_cache.gd` (`AirFieldCache`), вне `scripts/atmosphere/air_model/` (файлы той папки входят в `AirBakedField.code_hash()`).
- Папка — `user://air_cache/`: пара `<имя>.json` + `<имя>.bin` в формате TI-К3 v3 (`AirBakedField.save` / `load_file`), `<имя>` — первые 16 hex sha256 канонического JSON ключа; `index.json` — размеры и время использования (LRU). Нет или испорчен `index.json` — восстанавливается по файлам; файлы без пары и временные удаляются.
- Ключ (FL-К1): формат кеша (2), место (`loc.id` или ключ точки), центр, хеш данных места, старт, шаги областей, месяц и день, условия (час — до слота пересчёта 15 мин, ветер 0,01 м/с, направление 0,1°, температура 0,1 °C, небо, `wind_ref`), пояс часов места и снимок поверхности. Совпадение — только точное. Хеш модели не совпал, файл повреждён или `load_file` вернул null → запись удаляется, предупреждение, поле считается заново.
- Порядок поиска: запечённое поле (TI-К3) → кеш → расчёт. При попадании чтение идёт в пуле, этап «Рассчитываем ветер» не показывается, дальше обычный фоновый пересчёт.
- Что пишется: поле, принятое игрой после расчёта при загрузке места (включая `not_converged` и `previous_pass`). Не пишется: аналитический ветер без GPU, запечённое поле, пересчёты в полёте. Запись — в фоне (упаковка, zstd, временный файл и переименование), выход из игры дожидается записи; в тесте кадр записи ~1–5 мс.
- Формат 2 (без потерь): каналы float32 и числа `meta` с полной точностью. С float16 источники термиков из кеша отличались от посчитанных (Онгудай 3074 против 3072); теперь бит-в-бит, иначе в сети ведущий и клиент получили бы разные термики. Запечённые поля по-прежнему float16. Запись Онгудая ≈ 17 МБ (с float16 было 6,5 МБ).
- Включает кеш только игра (`AirRuntime.cache_enabled = false` по умолчанию, тесты и инструменты кеш не трогают).

### Настройка размера

«Настройки → Игра → Кеш ветра на диске»: ползунок 0–2000 МБ, шаг 50, по умолчанию 200 (≈ 11 записей Онгудая). Ключ `atmosphere.air_cache.max_mb` в `configs/atmosphere.json`, машинный (`UserSettings.LOCAL_KEYS`, лежит в `user://local/configs`, не уходит в облако). 0 — кеш выключен (ни чтения, ни записи). После каждой записи, пока сумма больше предела, удаляется запись с самым давним использованием.

## Пирамида высот

Пирамида максимумов высот слоя (`make_max_texture`) кешируется в папке места: `cache/<слой>_maxpyr.bin`, для `res://` — `user://height_cache/<путь>`. При повторной загрузке читается в рабочем потоке `load_files`, до раздачи слоя потокам. Текстура высот с мипами (`make_texture`, 10–30 мс) не кешируется.

## Ошибка вырубки

Маска просек считала план домов без домов OSM и без учёта `buildings.enabled`: 293 275 «домов» против 18 149 расставленных (точка). Теперь лес вырубается только под планом `WorldObjects`: площадь вырубки на точке 140,2 → 106,2 км², на Онгудае 26,6 → 26,2 км² (вырубка «без обоснования» 3 219 пикс → 0). Коридоры ЛЭП маска не рубит (и не рубила).

## Границы и где симулятор честно врёт

- Цель «попадание ≈ 10 с» на Онгудае не достигнута (12,5 с): остаток — этап glider 6,8 с на главном потоке и objects 2,5 с. Точка — 18,0 с при цели ≈ 17.
- Промах кеша (первая загрузка места, смена условий или модели воздуха) почти не быстрее прежнего: расчёт поля ~15–16 с остаётся. Промах на Онгудае измерен двумя запусками (разброс 23–34 с).
- Замирание ≤ 2 с выдержано на 20 потоках (1,0–1,5 с); на 4 потоках и меньше — 3–6 с. Промежуточные пулы не мерились. Железа с 4 физическими ядрами для замера не было.
- Сборка источников термиков (`AirThermals.build`) масштабируется только до 4 потоков (много обращений к объектам, общий spin-lock `ObjectDB`); на попадании кеша не вызывается, на промахе — работает. Тень клетки термиков (первый обход до 190 мс на клетку) прерывается по сроку; генерация клеток остаётся на главном потоке (пишет в общие кеши).
- Замеры — одна машина; часть выигрыша — меньшая нагрузка машины, чем при замере «до» (load average 0,5–3,6 против 82–91), vsync при замере «после» выключен.
- Число источников термиков между запусками одного места различается, если не задан `--seed`: «Лететь» берёт новый сид мира; это есть и на `main`.
- Повторная загрузка места в том же процессе не измерялась.
