# Аудит работы за спиной камеры (GR-1)

Только анализ, код не менялся, новых замеров GPU нет (GPU занят GR-2). Стенд цифр — замеры PF-10
(`docs/perf/frame_profile/after-fixes.md`, архив `pf10_run1.tar.gz`): ongudai, RTX 4070 SUPER,
пресет medium, без облаков (`nocloudfx`), три отметки (старт@2 — кабина, лес@30 и облака@60 — сзади).
Порог «заметно» — задание: ≥ 0,05 мс GPU на medium или ≥ 1 мс CPU на кадр/рывок.

## Допущения и границы

- **Доля кадра.** Камера по умолчанию: `configs/camera.json → fov_deg` 90° по вертикали, 16:9 →
  по горизонтали `2·atan(tan 45°·16/9)` = 121,3°. В кадре 121,3/360 = **33,7 %** кольца вокруг камеры
  (FOV 45° → 20 %, FOV 100° → 36 %); остальные **66 %** — сбоку и за спиной. Это верхняя оценка доли
  отсекаемого для объектов, раскиданных по кругу равномерно; наклон камеры вниз и рельеф доли не меняют
  существенно (кольцо плоское, рельеф — десятки метров на километры).
- **Потеря в мс — верхняя оценка.** Вне кадра вершинный шейдер всё равно отрабатывает (отсечение
  пирамидой — после него, на растеризации). Ранний выход оставляет выборку индексов и несколько
  операций на вершину, поэтому реальный выигрыш меньше доли вершин. Для травы и крестов вершинный шейдер
  тяжёлый (десятки выборок высоты), для моделей и камней лёгкий. Значения «до X мс» — не замер, а
  `цена объекта × 66 %`; проверит GR-5 после GR-3.
- **Шум.** Опыты PF-10 — один прогон, шум ±0,02 мс на отметку; значения < 0,05 мс неразличимы.
- **Проход теней.** Оценка по устройству движка (каскад вписывается сферой вокруг куска пирамиды) —
  в Godot 4.7.2 не проверялась.
- **Треугольники.** Числа «треугольников» — `primitives` из jsonl PF-10 (счёт движка по экземплярам,
  включая вырожденные); вершины = экземпляры × вершин на экземпляр (из кода/glb).

## По строкам: обоснование оценок

**Трава.** Кольца из `configs/vegetation.json → grass`: ближнее r 14 м, шаг 0,21 м, 6 травинок × (2·3+1) = 42 вершины на пучок;
среднее 8,4–36 м, шаг 0,3 м, 30 вершин; дальнее 26–115 м, шаг 0,85 м (`density_scaled` ложно), 18 вершин.
Число пучков — `GrassField.ring_offsets` (см. «Как считали»), сумма 2 979 594 вершин; треугольников
14 817·30 + 44 592·18 + 56 640·6 = 1 587 006 — **ровно** `nograss` Δprimitives в jsonl. Рамка:
`custom_aabb` на весь слой (`layer.size_x × size_z`), поэтому движок не отсекает ни одного пучка и не может:
у `MultiMeshInstance3D` одна рамка на все экземпляры. Шейдер `grass.gdshader` считает всё в `vertex()`:
позицию пучка из хеша клетки, 5 `h_bilinear` (высота + градиент), класс поверхности, маску приминания,
цвет луга (`relief_at`, `meadow_*`) — десятки выборок текстур. Ранний выход в строке 93 бывает только для
прореженных (по хешу `rank`), причём после хешей и расстояния. Цена 0,90 мс — три отметки 0,86–0,93 (PF-10).
Доля вне кадра — 66 %, но вершинная часть цены доминирует (раздельно не измерено), поэтому «до ≈ 0,6 мс» — потолок, ожидание GR-3 — 0,3–0,5 мс.
Вершинный шейдер идёт дважды (Depth Pre-Pass и Opaque, `measurements.md`), так что выигрыш раннего выхода удваивается.
Тень трава не отбрасывает (`cast_shadow = OFF`) — выход без оглядки на проход теней.

**Кресты.** Сетка `cell_m` 8 м, радиус по пресету `cross_radius_m` 900/1100/1500 (low/medium/high):
`ring_offsets(8, -1, R)` даёт 41 185 / 61 141 / 112 825 экземпляров; у креста 8 вершин и 4 треугольника (`cross_mesh`).
В шейдере `tc_present` — дешёвая проверка «есть дерево по хешу клетки», дорогая ветка только для живых: до 6
выборок высоты, породу, 4 пробы опушки. Рамка — на весь слой. Опыт `notrees` кресты не прячет
(`HIDE_CLASSES["notrees"] = [TerrainTreeModels, TerrainTrees, ForestImpostors]`), поэтому цена крестов
в PF-10 «зашита» в базу. Оценка цены: 0,49 млн вершин × (0,09 мс/млн у импостеров … 0,30 мс/млн у травы) = 0,04–0,15 мс,
вне кадра ×66 % → 0,03–0,10 мс (округлено). Это **оценка по аналогии**: нужен опыт `nocrosses`
(добавить в `tools/bench/frame_profile.gd`, вне скоупа GR-1). Ссылка на неё и в `dp_feedback`.
Подсчёт баланса треугольников на кабине@2 (3,12 млн всего: трава 1,59 + импостеры 0,68 + рельеф 0,65 + деревья 0,05 + камни/кусты 0,10 + объекты 0,01 = 3,08 млн) оставляет 0,04 млн на 245 тыс. треугольников крестов: баланс не сходится (опыты перекрываются: тени и рельеф считают кадр по-разному), вывод — не полагаться на баланс.

**Импостеры.** `n = ceil(2·3500/12)+1 = 584`, `n² = 342 225` экземпляров по 4 вершины, 684 450 треугольников — равно `noimpostors` Δprimitives.
Сетка квадратная, а работает только кольцо [`inner_m` ≈ 825, `outer_m` 3500] (кольцо крестов `r_far·k_min − dither/2` и далее):
площадь кольца 36,3 км², квадрата 49,1 км² → 26 % клеток мертвы всегда (углы квадрата и дыра в центре). В кадре
34 % кольца, т. е. 25 % всей сетки. Мёртвые клетки идут по короткой ветке (хеш, `d`, выход), поэтому их цена мала;
основная цена — живые клетки с `is_forest` и `h_bilinear`. 0,08–0,18 мс (три отметки), вне кадра 66 % живых → 0,05–0,09 мс — на пороге.

**Модели деревьев.** 5 пород × 8 вариантов × 3 LOD = 120 `MultiMeshInstance3D`, у каждого `custom_aabb` на слой (`terrain_tree_models.gd:66`).
Экземпляры набирает `TreePlacer.build` в рабочем потоке (круг `radius_m`, перестройка при сдвиге на 16 м), поэтому кучки
не зависят от угла камеры. Отсечь по углу можно только на GPU. Для сравнения: LOD0 лиственницы — 2 699 В / 1 870 треуг.,
береза 2 939 / 1 950, LOD1 634 / 554 В. Δprimitives `notrees − noimpostors`: 51 / 158 / 226 тыс. на отметках. Цена вне кадра — по шкале
`notrees − noimpostors` = −0,03 / 0,21 / 0,61 мс × 66 % ≈ 0 / 0,14 / 0,40 мс. Тени деревьев (`notreeshadow`: 0,08 / 0,37 / 0,63 мс, 31 / 120 / 175 тыс. треуг.)
— отдельно, в строке «Тени».

**Камни и кусты.** Δprimitives `noscatter` 98,9 / 98,9 / 99,1 тыс. треуг., 117 вызовов; GPU 0,53 / 0,27 / 0,22 мс. Модели камней дорогие
(LOD0 до 1280 треуг., `rocks.glb`), поэтому GR-4 заменит их на 20–80. `ShrubScatter._apply` ставит одну рамку `max(650, 1600)` на все
кучки, включая деревья групп (`shrubs.trees.radius_m` 1600) — камера внутри любой из них, отсечения нет. Вне кадра 66 % → ≈ 0,15–0,35 мс
как потолок, но после GR-4 цена камней упадёт кратно и отсечение дальше потеряет смысл.

**Тени солнца.** `directional_shadow_mode` = 4 каскада (`SHADOW_PARALLEL_4_SPLITS`), разбиение 0,05 / 0,2 / 0,5 от `shadow_max_distance_m` (medium 2000 м → 100 / 400 / 1000 / 2000 м),
атлас 2048. Sphere-fit каскада вписывает кусок пирамиды в шар: расчёт для FOV 90° 16:9: радиус 210 / 830 / 2060 / 4110 м,
центр на 50 / 250 / 700 / 1500 м впереди камеры; за плоскостью камеры лежит 35 / 31 / 29 / 27 % диска, сама пирамида — 13 / 12 / 11 / 10 %.
Кастеры выбирает движок по рамке — и у MultiMesh (деревья, камни, кусты — `cast_shadows` истинно) рамка огромная, так что они в каждом каскаде целиком.
Нужны только кастеры, чья тень падает в пирамиду: при солнце высотой 52° длина тени дерева 26 м — 0,78·26 ≈ 20 м, т. е. деревья дальше ~20 м от
пирамиды в сторону от солнца бесполезны. Верхняя оценка за спиной 27–35 % × 0,76 мс ≈ 0,2 мс. Дешёвого рычага в движке нет, отсекать
нужно рамкой кастера (тайлы), что для 120 кучек деревьев дорого; на medium LOD1/2 в тенях уже выключены (`shadow_lods` 1).

**Рельеф.** Чанки с рамкой по высотам чанка (`terrain_renderer.gd:134`) — движок отсекает их по пирамиде того же кадра. Прогревочные
`MeshInstance3D` с рамкой ±1e6 (строка 352) живут `WARM_FRAMES` кадров и потом освобождаются. Потери нет.

**Облака.** Проход — compute по буферу пониженного разрешения (medium 0,33), значит пиксели только вида; список облаков режется
`_visible_records` по плоскостям пирамиды (запас — радиус облака), CPU на кадр 0,13–0,59 мс (`measurements.md`) — ниже порога 1 мс.
`_select` — выбор из круга 25 км на 28–43 мс (порциями) — состояние физики с плавным появлением за 40 с (`fade_in_s`) и 60 с (`fade_out_s`),
привязка к камере только через `eye` и предел `max_clouds`; ограничивать вид нельзя — при повороте облако должно уже быть выбрано и
растаявшим-проявленным. Карта теней облаков — квадрат 32 км вокруг пилота, 2D-вьюпорт, до 220 квадов, раз в 3 кадра: тень на земле позади камеры
видна после поворота, камерой не определяется. Для вращения важно другое: `CloudCompositorEffect` (`CUT_DEG` = 25°) сбрасывает историю
перепроекции при повороте больше 25° за кадр, т. е. при ≈ 1500 °/с на 60 кадр/с — на несколько кадров облака в неполной выборке (мерцание шума), а не «дорисовка» на краю.

## Незаметное (одной строкой)

- Дымка (`sky_environment.gd:265–271`) — экранный квад ±1e6 из вершинного шейдера, считается по пикселям; −0,07…−0,11 мс, вне кадра нет.
- Перистые (`cirrus_layer.gd:55`) — плоскость 16×16 с `extra_cull_margin` 1e5, режется пирамидой, цена — фрагменты видимого неба.
- `gust_dust.gd:52` — 480 квадов (80 событий × 6), рамка ±4,5 км; `thermal_signs.gd:46` — ≤ 8 термиков; `bird_flock.gd:48` — ≤ 6 стай: ≪ 0,01 мс.
- `osm_traffic.gd:170` — ≤ 200 машин, рамка ±60 км; `city_trees.gd:251` — круг `radius_m` 700 м (medium), только в городах; тайлы OSM
  (`world_tiles.gd`, `osm_roads.gd`, `city_ground.gd`) — рамка и `visibility_range_end` на тайл, отсекает движок. Весь `world_objects`:
  `noobjects` −0,03…−0,04 мс.
- Пасхалки (`easter_eggs/*.gd`: стада, тюки, УАЗ, гуси, шар, лайнер) — штуки/десятки экземпляров, рамки по `reach` или огромные, но малые.
- Отражения: `ReflectionProbe`, SSR, SSAO, SDFGI в проекте нет (`ssr false` в env jsonl), радиансная карта неба от камеры не зависит.
- Occlusion culling в проекте выключен (в `project.godot` не включался) — для открытого рельефа он ничего бы не дал.
- CPU по кругу, не по камере: `Atmosphere.refresh_now` (24–39 мс/с) и `AirThermals.build` — физика воздуха вокруг планера в радиусе 20 км, камера ни при чём;
  `dust_devils`/`thermal_signs`/`bird_flock` обходят термики (18–33 мс раз в 0,5–1 с, `after-fixes.md`) — состояние мира, от направления камеры не зависят
  (у птиц `ahead_bias` — от курса планера). Отсекать по камере нельзя: после поворота термик должен быть на месте.

## Запас при быстром повороте

**Скорость поворота камеры в свободном режиме — предела нет.** Обзор мышью: `camera_rig.gd:_look` берёт `event.relative × look_sensitivity_deg_per_px`
(`configs/controls.json → mouse.look_sensitivity_deg_per_px` = **0,12 °/пиксель**) и прибавляет к `_free_rot`; `_update_free` сразу ставит `global_basis` —
сглаживания и ограничения скорости поворота нет (в кабине голова ограничена по углу ±120°, но не по скорости; клавиши `look_*` — 90 °/с). Строка
`world.json → preview.mouse_sensitivity_deg` (0,15) — только инструменты превью (`terrain_preview.gd`, `world_objects_preview.gd`), на игру не влияет. Входные события Godot
складывает за кадр (накопление включено по умолчанию), поэтому угол за кадр = сумма пикселей кадра × 0,12°.

**Оценка резкого рывка** (допущение автора, не из литературы): мышь 800 DPI = 31,5 пикс/мм; рука в рывке 0,5 м/с → 15 750 пикс/с × 0,12 °/пикс ≈ **1900 °/с ≈ 2000 °/с**
(половина оборота за ~0,09 с; игровые мыши с 1600 DPI и быстрые руки дают вдвое больше). Берём **2000 °/с** как расчётное. Угол за кадр:

| частота кадров | угол за кадр при 2000 °/с |
|---|---|
| 30 | 67° |
| 60 | 33° |
| 144 | 14° |

**Запас по задержке обновления** (угол за краем кадра = скорость поворота × задержка):

| способ отсечения | задержка | запас при 2000 °/с | вывод |
|---|---|---|---|
| рамка сектора/чанка, отсекает движок (`custom_aabb` на сектор, предсобранные MultiMesh) | 0 (пирамида того же кадра: `camera_rig._process` ставит базис до отрисовки) | **0°** по углу; по размеру — рамка сектора с запасом ≥ размера объекта | годится |
| ранний выход в шейдере (`CAMERA_POSITION_WORLD`, `INV_VIEW_MATRIX`, `PROJECTION`) | 0 | **0°** по углу; по размеру — 1,5 м (трава), 26–37 м (деревья) в плоскости, ± высота | годится |
| CPU, правка списка/видимости на следующем кадре | 1 кадр | 33° (60 кадр/с) — половина боковой доли кадра (60,6° от оси) | допустимо только для переключения `visible` готовых кучек |
| CPU, перестройка в рабочем потоке (`TreePlacer.build`, `RockScatter._build`) | ≥ 100 мс (сборка + применение через кадр) | ≥ 200° — практически весь круг | **бессмысленно**: секторная перестройка по камере не годится |
| CPU, выбор облаков (`CloudLayer._select`) | 1 с | 2000° (5,5 оборота) | не отсекать по камере |
| сброс истории облаков (`CUT_DEG` 25°/кадр) | — | порог 1500 °/с при 60 кадр/с | мерцание шума, не дорисовка |

Правило для правок отсечения (GR-3 и далее): **секторы допустимы только как предсобранные MultiMesh с рамкой сектора, которые отсекает сам движок; перестройка
по сектору камеры при свободном вращении запрещена**. Для шейдера плоскости пирамиды надо задавать с запасом в **метрах** (а не градусах): запас 1,5 м
(трава: наклон `lean·hh` ≤ 1,41·0,9 = 1,3 м + радиус пучка 0,15 м + ширина) выглядит как 37° на расстоянии 2 м, 6° на 14 м, 2,4° на 36 м, 0,75° на 115 м — значит
у самой камеры запас по углу велик и работа не отсекается, а вдали отсекается почти целиком. Это следует учесть в тесте GR-3.

**Отдельно (не вращение).** Скорость свободной камеры до `max_speed_ms` 120 м/с × `fast_factor` 4 = 480 м/с (8 м за кадр при 60 кадр/с): центр кольца травы
(`GrassField._process`, `grid_center_cell`) сдвигается раз в клетку 0,21 м, запас кольца — 2 клетки (0,42 м), поэтому в быстром пролёте у земли край кольца отстаёт; трава включена до 120 м над
землёй. Не связано с отсечением, но тест GR-3 при поступательной скорости ≥ 10 м/с в свободном режиме покажет и это.

## Что делать (по убыванию выигрыша)

1. **GR-3** (трава): ранний выход по пирамиде до всех выборок; ожидание — 0,3–0,5 мс medium (потолок 0,6). Запас: 1,5 м в плоскости, 1,2 м по высоте, угла 0.
2. **Кресты и импостеры**: сначала `nocrosses` в `HIDE_CLASSES` (отдельная задача bench), затем тот же ранний выход, что в GR-3; ожидание 0,05–0,15 мс суммарно. Запас по размеру дерева.
3. **Камни/кусты**: ничего — GR-4 снижает число треугольников; отсечение не окупает усложнения.
4. **Модели деревьев и тени**: отдельная задача после GR-5 и только если GR-3 покажет выигрыш раннего выхода; в теневом проходе выход
   нельзя (камера прохода — свет, а не игрок; не проверено в 4.7.2), нужен признак прохода или отдельный материал.
5. **Облака, рельеф, объекты мира, CPU-перебор термиков**: не трогать.

## Как считали

Числа ниже воспроизводятся без Godot (Python 3.12, стандартная библиотека), данные — из конфигов и `docs/perf/data/pf10_run1.tar.gz`:

```python
import math
def ring(sp, inner, outer):          # = GrassField.ring_offsets
    m = math.ceil(outer / sp) + 2
    lo, hi = max(inner - 2 * sp, 0), outer + 2 * sp
    return sum(1 for j in range(-m, m + 1) for i in range(-m, m + 1)
               if lo <= math.hypot(i, j) * sp <= hi)
# трава: ring(0.21,-1,14)*42 + ring(0.3,8.4,36)*30 + ring(0.85,26,115)*18  -> 2 979 594 вершин
# кресты: ring(8,-1,R)*8, R = 900 / 1100 / 1500 -> 329 480 / 489 128 / 902 600
# импостеры: (math.ceil(2*3500/12)+1)**2 * 4 -> 1 368 900
# горизонтальный FOV: 2*math.degrees(math.atan(math.tan(math.radians(90/2))*16/9)) -> 121.3
```

Разность `primitives` (base − опыт) и `gpu_ms` — из строк `exp` в `medium_ongudai_{2,30,60}_noclouds.jsonl` архива PF-10. Вершины на меш:
