# Весь ветер в крейте (идея пользователя, 2026-10-25; код задач RW)

Обзор кандидатов — [rust-ext.md](rust-ext.md); встраивание Пикара — [rust-air-integration.md](rust-air-integration.md); живой воздух — [air-cascade.md](air-cascade.md), «Главное направление: воздух со временем». Статус — на паузе с 2026-10-26 (недельный лимит), раздел «Состояние».

## Состояние на 2026-10-26 (пауза)
На паузе по недельному лимиту, этап 3 отложен. Что сделано, что красное, что в ветках задач и порядок продолжения — [rust-wind-state.md](rust-wind-state.md).

## Цель
**Независимость, не скорость.** Зачем (пользователь): безопасно менять расчёт ветра и экспериментировать с ним без бесконечных правок Godot и шейдеров (GPU-Пикар, `air_window.glsl` и ядра фаз уходят вместе с переносом). Игра не знает, как получается ветер в точке и когда он пересчитывается; расчёт меняется без правок в `scripts/` вне фасада.

**Главный довод — подмена модели.** В `air-cascade.md` ветер не формульный: Пикар 400 м задаёт крупное течение, уровни 200 → 12,5 м считаются шагами по времени, коробки едут за пилотом; термики, склоновый ветер, отрыв и болтанка — из правил клеток. Если весь ветер за одной границей в крейте, переход «формулы → живой воздух» — замена реализации в крейте; игра не меняется. Поэтому граница с самого начала рассчитана на живой воздух, а не на формулы.

## Что входит в крейт
Всё, из чего сейчас складывается `Atmosphere.air_velocity_at` (`scripts/atmosphere/atmosphere.gd:763`):
- поле Пикара с грубым стартом 1200 м, окна, подмена за `blend_s`, фоновый пересчёт, вход `domain_case` — как в [rust-air-integration.md](rust-air-integration.md);
- болтанка поля (`FieldTurbulence`) и шум порывов (`GustSpectrum`; `FastNoiseLite` — воспроизвести или заменить);
- аналитика (`WindModel`, линия тени и склоновый подъём по `GroundField`): подмешивается в полосе края поля (`a < 1`) и работает при `air_model.enabled = off`;
- термики и фоновое опускание (`ThermalField`, `AirThermals`);
- `_extra_flow`: грозы (`StormField`), волны и роторы (`WaveField`), выброс из облака (`CloudPhysics.sample`);
- погода из прогноза и ход дня (`WeatherModel.derive`, `AtmoDay`, коэффициенты `_cache_coefficients`);
- конфиги этих расчётов (`configs/atmosphere.json`, `configs/weather_model.json`, `configs/weather/*`) — читает крейт; игра передаёт их как есть.

Это снимает прежние исключения из области: термики (A4) и упрощённый ветер входят — ради границы, не ради скорости.

## Граница (под живой воздух)
Контракт — `docs/contracts/rust-wind.md` (RW-0), с версией и контрактным тестом.
- **Игра → крейт:**
  - растры места — один раз при загрузке; сброс — явным вызовом при смене места;
  - конфиги; прогноз (температура, ветер, дата, место) или эталонная погода; сид;
  - **время:** `advance_to(t)` — крейт продвигается сам; опрос — всегда на текущий момент, без произвольного `t` в каждом вызове (живой воздух хранит состояние);
  - **старт с момента `t`** (`Atmosphere.start_at`) — команда, которой разрешено занять время (разгон живого воздуха); готовность — флаг, игра ждёт его на экране загрузки;
  - **фокусы — список** (пилот, боты, другие игроки), с весом; уровень детализации у точки выбирает крейт;
  - статические термики и режим термиков; направление солнца, если его ведёт игра.
- **Крейт → игра:**
  - `sample_many(PackedVector3Array)` → скорость и σ **неразрешённой** болтанки (в живом воздухе крупные вихри — в скорости); одиночный `sample(pos)` для редких вызовов;
  - **описания — найденное, а не заданное:** ядра подъёма (место, сила, размер), облака, гроза, гребни волн, база облаков. У формульной модели это её список, у живой — поиск ядер в поле. Игре это нужно для облаков, ассистента термиков, ботов;
  - **отладка:** разложение ветра в точке по слагаемым одним вызовом (для `wind_field_debug.gd`, `debug_overlays.gd`, `atmo_fingerprint.gd`); набор слагаемых — у реализации, не в контракте;
  - **сеть — не цель (решение пользователя 2026-10-25):** сетевая игра не главное, игроки в ней не в одной точке. Каждый клиент считает свой воздух от общей погоды и сида; выгрузки состояния и синхронизации воздуха в контракте нет.
- Колбэков из крейта в Godot нет (`height_fn`, `surface_fn`, `sun_fn` сейчас — Callable; класс вылета CR-17).
- Без `Dictionary`/`Object` в горячем пути; плохой вход не роняет игру (`panic = "abort"`).

**Что сейчас мешает границе** (`grep` по `scripts/`, 2026-10-25): потребители лезут во внутренности `Atmosphere` (`atmo.field.thermals` — 16 мест, `atmo.wind.*`, `atmo.ground.*`, `atmo.cloud_phys.*`, `atmo.wave.crests`, `atmo.storm.*`): `bot_pilots.gd`, `net_flight.gd`, `atmo_fingerprint.gd`, `bird_flock.gd`, `dust_devils.gd`, `thermal_signs.gd`, `cloud_shadow_map.gd`, `gust_dust.gd`, `cirrus_layer.gd`, `atmosphere_preview.gd`, `cloud_layer.gd`, `debug_overlays.gd` (`air.field.thermals`).

## Риски
- Объём на порядок больше встраивания (6–11 дней): одни термики — ~2,4 тыс. строк (`thermal_field.gd`, `air_thermals.gd`).
- Болтанку и линию тени настраивали с пилотами — расхождение меняет ощущение полёта; GDScript — эталон до T9.
- Облачная физика связана с отрисовкой облаков — граница требует отдельного разбора (RW-11).
- Сборка под macOS с Linux, запуск — только у друга с Mac.

## Решения пользователя

- **Цель модуля: весь ветер и его расчёты — из GDScript/GLSL в Rust-библиотеку; Godot только запрашивает состояние ветра на нужный момент, сам не считает** (2026-10-26) — независимость расчёта ветра от Godot и шейдеров
- **Карта рельефа для ветра и подложка (покров, вода, производные поля) грузятся в крейт один раз при загрузке места; всё тяжёлое считает Rust** (2026-10-26) — в Rust должно считаться всё
- **Учесть docs/plan/rust-ext.md (принцип горячих циклов — в Rust, данные места — в крейте, инфраструктура workspace) и наработки picard-rs: расчёт Пикара в Rust уже оптимизирован по счёту — брать его, не писать заново** (2026-10-26)
- **Первым делом — публичный контракт крейта (RW-0: API dp-air/dp-gd, типы, оси, единицы, время, фокусы, описания, разложение, ошибки, версия). После его фиксации — две параллельные ветки работ: Godot-сторона (эталоны RW-1, фасад RW-2, перевод потребителей RW-3, подвязка к расширению по контракту) и крейт (RW-4…12) против того же контракта; порядок задач в плане перестроить под это** (2026-10-26) — контракт развязывает Godot и крейт — их можно делать одновременно
- **Профили сборки крейта (RW-4): для разработки и настройки — отдельный профиль вида C -O2 -g (opt-level 2, debug-символы, без LTO, codegen-units по умолчанию/инкрементально, быстрая пересборка); fat LTO + codegen-units=1 + panic=abort — только релизный профиль для выпуска; tools/build.sh для релиза берёт релизный, игра в разработке — профиль разработки** (2026-10-26) — быстрая пересборка при настройке ветра; fat LTO только к релизу

- **Отменяет предыдущее решение о шлюзах «готово к проверке пилотом»: промежуточных тестовых сборок нет. Пользователь проверяет игру один раз — на тестовой сборке Linux перед сдачей модуля, когда координатор закончит все задачи; до этого — только автоматические тесты (T1–T9)** (2026-10-26)
- **Координатор меняется по этапам: этап 0 (контракт RW-0) → этап 1–2 (Godot-сторона RW-1…3 и крейт RW-4…7 параллельно) → этап 3 (слагаемые RW-8…12) → этап 4 (уборка RW-13, подготовка к проверке пользователем). На плотном этапе 1–2 главная может перезапустить и посередине** (2026-10-26) — чтобы контекст координатора не распухал
