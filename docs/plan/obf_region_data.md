# Региональные файлы карт вместо загрузки по точке («obfp», OBF, PBF, MBTiles/PMTiles)

Исследование, 30.09.2026. Код игры не менялся. Эксперимент — `tools/research/obf_region/`.

**Коротко.** Переходить на OsmAnd OBF не стоит: условия сервиса OsmAnd запрещают
автоматическое скачивание и раздачу их файлов, формат нестандартный (своих библиотек нет), а
рельеф и земной покров он всё равно не заменяет. Сама идея «качать регион целиком» полезна, и
главный выигрыш у неё не в скорости: **сейчас в произвольной точке с карты вообще нет объектов
OSM** (дорог, воды, ЛЭП, домов, заборов). Они есть только у четырёх встроенных локаций, а в
произвольной точке качаются только рельеф и WorldCover. Если это важно, лучший путь — делать
региональный пакет самим из `.osm.pbf` Geofabrik в наш формат. MBTiles/PMTiles нужны для
векторной карты выбора старта, а данные для полёта из них брать нельзя.

## 1. Что такое «obfp»: какую трактовку приняли

| Вариант | Итог |
|---|---|
| **OsmAnd OBF** (OsmAnd Binary Format, `.obf`) — офлайн-карта региона: карта, маршрутизация, POI, адреса; отдельно `srtm`-изолинии и `Heightmap_*.tif` | **Принят** как основная трактовка |
| Опечатка/сплав «obf + pbf» → **`.osm.pbf`** (OSM Protocolbuffer Binary Format, региональные выгрузки Geofabrik) | Тоже правдоподобно. Разобран как альтернатива, в итоге рекомендуем именно его |
| Формат с названием ровно «OBFP» | Поиск ничего не нашёл ([поиск](https://github.com/tumic0/GPXSee/issues/417) приводит к тем же OBF/PBF/MWM). Отвергнут |
| Organic Maps `.mwm`, Garmin `.img` | Того же класса, что OBF: закрытые схемы под своё приложение, без плюсов перед OBF. Отвергнуты |

## 2. Как сейчас (по коду)

- **Рельеф в произвольной точке:** тайлы AWS Terrain Tiles (Terrarium) z12 (≈24 м/пикс на 52°) и
  z9 для дали, кеш `user://terrain_cache` (`scripts/terrain/terrarium_loader.gd`,
  `configs/world.json → runtime_terrain`).
- **Земной покров:** ESA WorldCover 10 м, чтение COG по HTTP range (`worldcover_loader.gd`).
- **OSM:** Overpass API вызывается **только офлайн**, из `tools/osm/fetch_osm.py`, для встроенных
  локаций (квадрат 40×40 км). Результат — `data/osm/<id>.json`, от 1 до 2,8 МБ, всего 7,3 МБ.
  Слои: дороги, здания (с этажностью), ЛЭП и опоры, реки/ручьи/каналы, озёра, посёлки, поля
  (meadow/grass/farmland), заборы/стены. **В игре Overpass нет**, поэтому в произвольной точке
  пусто: нет рек по OSM (только класс «вода» WorldCover), дорог, ЛЭП для столкновений, домов.
- **Карта выбора старта:** своя отмывка из тех же тайлов Terrarium, без внешних карт
  (`map_picker.gd`). В TODO есть пункт «Векторная карта для выбора старта (рендер через martin)».

## 3. Что лежит в OBF (проверено на файле Алтая)

Скачан `Russia_altay_asia_2.obf.zip` (Республика Алтай, выгрузка 01.09.2026): 84 МБ в zip,
122 МБ распакованный, скачивание 28 с (~3 МБ/с). Разобран своим читателем на 150 строк Python.

Разделы файла: карта (map) 78,3 МБ, маршрутизация 31,8 МБ, POI 10,3 МБ, адреса 1,1 МБ, прочее
< 1 МБ. Нам нужна только карта. В ней 1090 правил тегов (`tag=value`) и 4 уровня детализации:
z9–10, z11–12, z13–14, z15–22. Геометрия на подробном уровне — дельты в 31-битной сетке (>>5),
это порядка 0,5 м, для нас достаточно.

Состав в квадрате 40×40 км вокруг Онгудая (подробный уровень, блоки дерева, пересекающие
квадрат; полный вывод — `tools/research/obf_region/ongudai_20km.txt`):

| Что нам нужно | В OBF | Сейчас у нас (`data/osm/ongudai.json`) |
|---|---|---|
| Дороги | `highway=*`, 36 значений: track 588, residential 275, trunk 33 … | 1104 |
| Здания, этажность | `building=*` ≈5,9 тыс.; есть `building:levels`, `height` | 5482 |
| ЛЭП | `power=tower` 308, `pole` 2965, `minor_line` 127; `power=line` в словаре есть, в этом квадрате на подробном уровне не нашёлся (не проверено, где лежит) | 125 линий |
| Реки/ручьи | `waterway=river` 63, `stream` 294 (+canal, ditch…) | 241 |
| Озёра | `natural=water` 54 | 22 |
| Посёлки | `place=*` (city…isolated_dwelling) | 9 |
| Поля, луга | `landuse=meadow` 148, `farmland` 86 | 197 |
| Заборы | `barrier=fence` 5232, `wall` 42 | 4939 |
| Лес | `natural=wood` 1683, `landuse=forest` | — (берём из WorldCover) |

Счётчики не сравнимы один к одному: OBF режет линии по блокам и считает все блоки на краю, а
наш скрипт склеивает части. Но по составу **все слои, которые мы берём из OSM, в OBF есть**, с
названиями и этажностью. Это не удивительно: OBF — переупаковка тех же данных OSM.

**Чего в OBF нет:**
- **Растрового рельефа в карте нет.** Отдельные файлы: `srtm`/`srtmf` `.obf` — только изолинии
  (Алтай — 249/204 МБ в zip); `Heightmap_Russia_altay_asia.tif` — GeoTIFF 200 МБ с сеткой около
  75 м ([обсуждение](https://github.com/osmandapp/OsmAnd/discussions/19011)). Это втрое грубее
  нашего Terrarium z12 (24 м). Физике склона и динамического потока нужно не хуже, так что
  **рельеф OBF нам не замена**.
- **Земного покрова уровня WorldCover нет.** Лес и луга в OSM — полигоны там, где их нарисовали
  картографы. На Алтае покрытие неполное, а классов «голый грунт/скалы/кустарник» в нужной
  нам сплошной форме нет. Для термиков (источник по классу поверхности) нужен сплошной растр,
  то есть WorldCover остаётся.

## 4. Формат и чтение

- **Спецификация:** protobuf-схема [OBF.proto](https://github.com/osmandapp/OsmAnd-resources/blob/master/protos/OBF.proto)
  и [описание](https://osmand.net/docs/technical/osmand-file-formats/osmand-obf/). Устроено
  так: R-дерево боксов по уровням зума, блоки объектов со своими таблицами строк, типы через
  таблицу правил. Схема нестандартная: большие разделы и смещения пишутся **собственным типом
  провода 6** (fixed32 big-endian), и в комментарии прямо сказано, что сообщения «не
  предназначены для разбора движком google». Штатный protobuf-парсер файл не прочитает, нужен
  свой ручной разбор (мы его сделали для дерева карты).
- **Библиотеки вне OsmAnd:** не нашли ни одной живой на Python/Rust/Go/C#. Есть только
  OsmAnd-java (`BinaryMapIndexReader`), OsmAnd-core (C++) и OsmAndMapCreator. Код OsmAnd —
  [GPLv3 с исключением](https://osmand.net/help-online/license/), графика — CC BY-NC-ND.
  Вшивать их в игру нельзя: GPL-связывание и тяжёлые зависимости. Остаётся свой читатель.
- **Из GDScript** читатель писать можно: `FileAccess` плюс varint, примерно 300–500 строк на
  дерево карты, блоки и декодирование координат и типов. Скорость: квадрат 40×40 км в Python
  разбирается за 0,2 с. Но формат версионируется OsmAnd без обещаний совместимости.

## 5. Доставка и лицензии OBF

- Размеры в zip (индекс `download.osmand.net/get_indexes?xml`, 29.09.2026): Республика Алтай —
  84 МБ (122 распак.), Алтайский край — 153 МБ, Казахстан — 317 МБ. Сибирский ФО целиком —
  нарезан на субъекты. Обновление — раз в месяц (дата выгрузки 01.09.2026).
- **Условия:** в [Terms of Use OsmAnd](https://osmand.net/help-online/terms-of-use/) (редакция
  25.08.2026), п. 9.2, сказано: «Any use of these services for … automated data extraction, bulk
  downloading, caching, redistribution, or integration into other services without prior
  written consent from OsmAnd B.V. is strictly prohibited». То есть **качать OBF из игры с их
  сервера и раздавать их у себя без письменного согласия нельзя**. Данные внутри — ODbL, но
  прав на их сборку и сервер это не даёт. Сделать OBF самим можно (OsmAndMapCreator, GPL), но
  тогда проще сразу собрать свой формат.

## 6. Альтернативы того же класса

### 6.1 Региональный `.osm.pbf` (Geofabrik)
- Сырые данные OSM за регион, без потерь, со всеми тегами. Выгрузки ежедневные
  ([Geofabrik, Россия](https://download.geofabrik.de/russia.html)): Россия — 3,9 ГБ, Сибирский
  ФО — 557 МБ, Уральский — 376 МБ, Приволжский — 738 МБ, Центральный — 837 МБ. Отдельных
  субъектов у Geofabrik нет, мелкий регион вырезается `osmium extract` за секунды.
- Лицензия — ODbL: можно раздавать и производные с атрибуцией «© OpenStreetMap contributors»
  (она у нас уже есть). Сервер Geofabrik для разовых скачиваний открыт.
- Читать `.pbf` в игре незачем. Правильно переработать его **офлайн** (pyosmium) тем же кодом
  упаковки, что `tools/osm/fetch_osm.py` (у него уже есть `pack_*`), и порезать на ячейки.
- Против текущего подхода: даёт OSM-объекты в **любой точке** региона, без Overpass, офлайн,
  детерминированно (одна дата выгрузки), с нашей схемой слоёв.

### 6.2 Собственный региональный пакет (наш формат)
То же, что 6.1, в готовом для игры виде: ячейки, например 0,25°×0,25° (~28×18 км), в каждой JSON
или бинарник нашей схемы `data/osm`, сжатый brotli, как `data/terrain`. Оценка размера по
нашим данным: 40×40 км Онгудая дают 1,8 МБ JSON, после brotli ≈ 0,2–0,4 МБ (не мерили). Вся
Республика Алтай (~93 тыс. км², в основном пустые горы) — **порядка 10–30 МБ** (оценка).
Раздаётся с сайта или itch как «пакет региона», или качается игрой по ячейкам. Цепочка
`scripts/world_objects/osm_data.gd` не меняется.

### 6.3 MBTiles / PMTiles и martin (отдельный вариант)
**Что это.** MBTiles — SQLite-файл с таблицей тайлов `(z, x, y) → blob`. Blob — векторный тайл
MVT (protobuf, gzip) или растр PNG/WebP. PMTiles — тот же набор тайлов в одном файле с
индексом, читается HTTP range-запросами без сервера. Оба формата — одна пирамида тайлов на
регион.

**martin** ([документация](https://maplibre.org/martin/)) — сервер тайлов на Rust. Источники:
PostGIS, MBTiles, PMTiles, COG (растр), GeoJSON. Умеет отмывку и изолинии при раздаче.
[`martin-cp`](https://maplibre.org/martin/martin-cp.html) копирует тайлы любого своего источника в
MBTiles/PMTiles по bbox и диапазону зумов, может сливать несколько источников в один архив.
**Из `.osm.pbf` martin векторные тайлы сам не строит.** Нужен либо PostGIS (osm2pgsql/imposm +
SQL-функции слоёв, тяжёлая установка), либо генератор:
- [planetiler](https://github.com/onthegomap/planetiler) (Java, Apache-2.0) строит MBTiles/PMTiles
  из `.osm.pbf` по схеме OpenMapTiles за минуты на регион. Свои слои задаются профилем
  (YAML/Java).
- Готовые тайлы: [Protomaps basemap](https://docs.protomaps.com/basemaps/downloads) (ежедневная
  сборка планеты в PMTiles, порядка 100+ ГБ, регион вырезается `pmtiles extract --bbox`),
  OpenMapTiles.

**Схема слоёв и полнота.** В OpenMapTiles есть water, waterway, landcover, landuse,
transportation, building (с `render_height`), place, mountain_peak, poi. В Protomaps — похожие
слои. **Ни в одной из стандартных схем нет ЛЭП и заборов**, а это у нас столкновения и
препятствия на посадке. Их придётся добавлять своим профилем planetiler. Кроме того,
векторные тайлы по устройству рассчитаны на картинку:
- линии и полигоны режутся по границам тайлов, для физики их надо склеивать обратно;
- на зумах ниже максимального геометрия упрощается;
- координаты квантуются сеткой 4096 на тайл (на z14 и 51° это ≈0,4 м, терпимо);
- лишние теги отбрасываются (этажность — только если профиль её сохранит).

Для полёта это хуже, чем свой формат из 6.2.

**Растровые слои в MBTiles.** Технически можно: Terrarium-PNG рельефа и WorldCover (PNG
классов) лягут в MBTiles как растровые тайлы. martin отдаёт COG напрямую, `martin-cp` соберёт
MBTiles по bbox. Для Terrarium z12 это просто упаковка тех же PNG в один SQLite-файл.

**Чтение из игры.** MBTiles — SQLite. Варианты:
- GDExtension [godot-sqlite](https://github.com/2shady4u/godot-sqlite) (MIT, сборки
  Win/Linux/macOS): плюс нативная библиотека в сборке на каждой платформе;
- свой читатель файла SQLite на GDScript — неразумно;
- распаковка тайлов из MBTiles при установке региона в `user://` — тогда MBTiles только способ
  доставки.

PMTiles читается проще: заголовок, каталог, смещения, всё это `FileAccess`, около 200 строк
GDScript. Декодер MVT (protobuf, команды геометрии) — ещё 200–300 строк. Рендер векторной
карты в `map_picker.gd` (линии и полигоны по стилю) пишется на Godot с нуля: MapLibre в Godot
нет.

**Размеры** (оценка, не мерили): векторный MBTiles Республики Алтай z0–14 — десятки МБ, того же
порядка, что раздел карты OBF (78 МБ). Растровый пакет Terrarium z12 на bbox 49–53° с. ш.,
84–90° в. д. — 5110 тайлов × ~35 КБ (среднее по 4 скачанным тайлам) ≈ **180 МБ**, плюс z9 —
100 тайлов, ~3 МБ.

**Как это ложится на выбор точки.** Здесь MBTiles/PMTiles и полезны: подложка с реками,
дорогами, посёлками и подписями делает выбор старта осмысленнее, чем голая отмывка. Нужна
цепочка planetiler → PMTiles региона (или `pmtiles extract` из Protomaps) → свой рендер MVT в
Godot. martin как **сервер** нам не нужен: у нас нет своего сервера, а поднимать его ради семьи
и друзей незачем. Файл лежит локально или на статическом хостинге (PMTiles по HTTP range).
martin/`martin-cp` пригодится как инструмент сборки, если данные будут в PostGIS или нужно
слить векторные и растровые источники в один архив. Для чистого пути из PBF хватает planetiler.

### 6.4 Overture Maps
[GeoParquet на S3](https://docs.overturemaps.org/), выборка по bbox через DuckDB. Темы: base (вода,
land use, land cover, инфраструктура, включая ЛЭП), buildings, transportation, places.
Лицензии смешанные: ODbL для производных OSM, CDLA для places. Даёт то же, что OSM, в
табличном виде, плюс свои здания. Для России и Казахстана добавки к OSM почти нет, а в
цепочку добавляются DuckDB/Parquet. Не нужно (не проверяли покрытие Алтая).

### 6.5 Рельеф и земной покров целиком
OBF их не заменит. «Скачать регион» для них означает:
- **Terrarium z12 + z9** на bbox региона: ~180 МБ для Республики Алтай (см. выше). Формат,
  загрузчик и кеш уже наши, нужно только заранее заполнить `user://terrain_cache`.
- **Copernicus GLO-30** (тот же источник, что Terrarium в этих широтах, но без PNG-упаковки):
  тайлы 1°×1° COG, ~24 штуки на Алтай, оценочно 0,5–1 ГБ. Выигрыша против Terrarium z12
  (≈24 м против 30 м) нет, только объём.
- **WorldCover:** тайлы 3°×3° COG, на Алтай 4–6 файлов, оценочно 0,3–0,6 ГБ целиком. Либо
  вырезка только нужного bbox нашим `cog_reader` и сохранение в кеш.

## 8. Что это даёт нам по существу

1. **Реализм в произвольной точке** — главное. Сейчас старт с карты даёт рельеф и покров, но без
   рек (вода только по WorldCover 10 м, узкие реки теряются), дорог, посёлков, ЛЭП. Нет ЛЭП —
   нет и столкновения с ними, то есть в физике посадки не хватает реальной опасности.
   Региональные данные OSM это закрывают. Можно дешевле, без регионов: вызывать Overpass из
   игры для квадрата точки (код упаковки уже есть в Python, его надо перенести в GDScript или
   сделать сервис). Минус этого варианта — зависимость от живого Overpass в момент выбора точки.
2. **Время старта в новой точке:** сейчас сначала ~десятки тайлов Terrarium и range-чтения
   WorldCover. С заранее скачанным регионом загрузка идёт с диска. Выигрыш — секунды, это не
   главное.
3. **Офлайн:** «скачать регион» перед поездкой — да, удобно (на выезде с плохой сетью).
4. **Размер сборки:** в сборку регионы класть не надо, это отдельные загрузки. Сборка не растёт.
5. **Лицензии:** OBF не проходит из-за ToS. PBF, свой пакет и PMTiles — ODbL, атрибуция уже есть.
6. **Риск:** OBF — чужой, нестандартный, версионируемый формат. Свой пакет из PBF — наш код и
   наша схема, риск минимальный.

## 9. План и оценка (если делать)

| Этап | Что | Дни |
|---|---|---|
| 0 | Прототип: `osmium extract` Алтая из Сибирского ФО → pyosmium → нарезка ячеек нашим `pack_*` → замер размера после brotli | 0,5 |
| 1 | Инструмент `tools/osm/build_region.py` (PBF → ячейки brotli, индекс ячеек, атрибуция); сборка 1–2 регионов | 1–1,5 |
| 2 | Игра: `OsmData` собирается из ячеек вокруг точки (склейка по границам ячеек для рек и ЛЭП или перекрытие ячеек); загрузка пакета в `user://`, пункт «скачать регион» | 1,5–2 |
| 3 | Рельеф и покров региона: предзаполнение `user://terrain_cache` Terrarium z12/z9 и WorldCover по bbox региона | 0,5–1 |
| 4 | (отдельно) векторная карта выбора старта: planetiler (+профиль с водой, дорогами, посёлками, при желании ЛЭП) → PMTiles региона → читатель PMTiles + MVT + рендер в `map_picker.gd` | 3–5 |

Этапы 0–3 — **~4–5 дней**, этап 4 — отдельная задача. Переход на OBF оцениваем в 5–8 дней
(свой читатель, склейка, типы), и он всё равно упирается в ToS.

Риски: склейка объектов на границах ячеек, полнота OSM в глуши (есть и сейчас), размер
Terrarium-пака для больших регионов (Россия целиком — десятки ГБ, поэтому только субъекты или
bbox вокруг полётных мест).

## 10. Рекомендация

- **OBF — не переходить.** ToS OsmAnd запрещает автоматическое скачивание и раздачу, формат
  нестандартный, рельефа и покрова нужного качества в нём нет. Всё полезное в OBF — это данные
  OSM, которые законно и проще взять из `.osm.pbf`.
- **Частично — да, если пилотам важны старты не из списка.** Сделать свой региональный пакет OSM
  из Geofabrik PBF (этапы 0–2) и предзагрузку рельефа и покрова региона (этап 3). Это даст
  реки, дороги, посёлки, дома и ЛЭП в любой точке региона, офлайн и детерминированно. Если
  старты с карты используются редко, сначала сделать этап 0 и посмотреть размеры.
- **MBTiles/PMTiles — только для векторной карты выбора старта** (пункт TODO), и в варианте
  «planetiler → PMTiles → свой рендер», без сервера martin. Для физики мира они хуже своего
  пакета: объекты порезаны по тайлам, нет ЛЭП и заборов в стандартных схемах. Растровые
  MBTiles как контейнер для Terrarium/WorldCover дают только «один файл вместо папки» ценой
  SQLite-GDExtension — не нужно.
