# План rust-ext — что ещё вынести в Rust (обзор)

## Статус
Идея, обзор по чтению кода и docs (2026-10-24); **замеров не делалось**, исполнителей и модуля нет. Числа с пометкой «оценка» — расчёт из
чужих замеров, не измерение. Рабочая копия и ветка модуля не заведены; документ нужен, чтобы решить, какие места брать после
шага 0 из [air-cascade.md](air-cascade.md) («Вариант: библиотека на Rust»; тут не повторяется).

## Цель
Выбрать расчёты **рантайма игры**, которые выигрывают от нативной библиотеки (GDExtension через godot-rust/gdext), и порядок их взятия.
Только рантайм: `tools/` и любые офлайн-расчёты (пересчёт полей, подготовка данных, исследования) вне области.
Критерии: горячий цикл в GDScript; работа на главном потоке или упор в `WorkerThreadPool`; долгая загрузка/генерация;
нестабильность; зависимость от GPU, которую хорошо иметь на CPU (слабые машины, headless, тесты).

## Что есть в коде сейчас (опора выводов)
- GDScript — ~98 тыс. строк в `scripts/`; крупнейшие тяжёлые файлы воздуха: `scripts/atmosphere/air_model/air_runtime.gd` (1843 строки),
  `air_thermals.gd` (1152), `thermal_field.gd` (1241 строка), `atmosphere.gd` (1181), `wind_field.gd` (739), `air_phase_cpu.gd` (754).
- Почти вся тяжёлая работа уже вынесена в `WorkerThreadPool` (`PoolFor`, `scripts/core/pool_for.gd`; `docs/guide/fast-load.md`), то есть
  остаётся выигрыш на ядро (GDScript → нативный код) и снятие ограничений пула, а не «распараллеливание».
- Пул Godot 4.7 даёт ограничения, описанные в `docs/guide/fast-load.md`: `wait_for_group_task_completion` из рабочего потока при пуле 2 потока
  вставал (обход — `PoolFor`); `AirThermals.build` масштабируется только до 4 потоков (общий spin-lock `ObjectDB`, много обращений к объектам);
  при пуле 2 потока загрузка 24 с против 12,5 с на 20 потоках (`tools/research/load_profile/final.md`).
- GDExtension в проекте уже есть как класс решения: GodotSteam (`docs/guide/steam.md`, `tools/steam/fetch_godotsteam.sh`, пресеты «… Steam» в
  `export_presets.cfg`) — но только как скачанный бинарник, не как свой код. Rust в репозитории есть только офлайн (`tools/osm_tiles/packer/Cargo.toml`).
- Сборки: Linux x86_64, Windows x86_64, macOS universal (`export_presets.cfg`: `binary_format/architecture`); собирает автор на Linux (`tools/build.sh`),
  CI игры нет (`.github/workflows/` — только сайт); macOS собирается без возможности запуска на месте («проверяет друг с Mac»,
  `.claude/skills/new-release/SKILL.md`).

Пояснения:
- **R1 vs R2 связаны.** Если воздух идёт на Rust (шаг 0 `air-cascade.md`), то R1 — естественный вход «ветер в точке» (там и сказано: «вызов функции, без чтения поля с GPU»); R2 — недостающие куски вокруг Пикара. Брать вместе, поэтапно: Пикар → ветер в точке → фазы/подготовка → окна.
- **Группа B.** Постановка задачи упоминала параллельную сборку объектов (`scripts/game/game.gd:426-430`) и `_air_field_job` как возможную причину. По `cr-2.md` гонка стадий `objects`/`wind` в числе «не причина» (первая загрузка с тем же порядком проходит); подозревается жизненный цикл общего локального `RenderingDevice` при **повторной** загрузке (`air_runtime.gd`, `air_gpu_job.gd`) либо TDR/драйвер Blackwell. Rust-воздух на CPU убрал бы этот `RenderingDevice` как класс проблем, но это следствие, а не доказанное лечение; правка жизненного цикла RD (`cr-2.md`, «Предложение правки») дешевле и не зависит от Rust.
- **Что стало бы быстрее во всех кандидатах** — не «параллелизм» (он есть), а скорость на ядро и независимость от размера пула Godot. На 4-ядерной машине это важнее, чем на 20 потоках автора (`final.md`: пул 4 → 18,1 с, замирание 2,8 с; пул 2 → 24,2 с).

## Общая инфраструктура
Предложение (без реализации):
- **Один репозиторий-крейт `rust/`, workspace из нескольких крейтов, одна загружаемая библиотека.** Чистые крейты без Godot (`dp-air`, `dp-world`, …:
  `cargo test`, `criterion`, сверка с фикстурами `fixtures/air_model/` и `tests/fixtures/`) + один тонкий крейт-обёртка `dp-gd` (`cdylib`, gdext),
  собирающий **один** `.gdextension` и один бинарник на ОС. Причины: один файл на ОС в сборке и подписи macOS; один общий пул потоков (`rayon`);
  изменения контракта границы — в одном месте. Несколько `cdylib` дали бы несколько пулов потоков (перегрузка ядер) и несколько бинарников в релизе.
- **Граница.** Только `PackedFloat32Array/PackedFloat64Array/PackedInt32Array/PackedByteArray/PackedVector3Array` на входе и выходе (gdext даёт срез без
  копирования на входе, выход — одно копирование); без `Dictionary`/`Object` в горячем пути; крупные состояния живут в Rust за `RefCounted`-обёрткой.
  Рабочие потоки Rust не трогают объекты Godot. Формат каждой границы — контракт `docs/contracts/rust-ext.md` с версией и контрактным тестом
  (правило workflow «Контракты»), побитная/допусковая сверка с GDScript-эталоном на фикстурах.
- **Потоки.** Один `rayon`-пул, размер задавать из настройки игры (иначе спор за ядра с `WorkerThreadPool`: пул 2/4/20 даёт 24/18/12,5 с, `final.md`);
  вызов из главного потока не должен ждать пул дольше порции (сравни `chunk_ms` для GPU, `air_gpu_job.gd`).
- **Профиль сборки** — как в air-cascade: `lto = "fat"`, `codegen-units = 1`; без `target-cpu=native`; ветка AVX2 во время работы. `panic = "abort"` из air-cascade
  обратной стороной: паника в расширении валит всю игру без записи стадии — на границе проверять входы и решить (вопрос), нужен ли `panic = "unwind"` ради сообщения об ошибке.
- **Сборка и поставка.** `.gdextension` с путями под `linux.x86_64`, `windows.x86_64`, `macos` (универсальный dylib через `lipo`); `tools/build.sh` вызывает `cargo build --release`
  для трёх целей до экспорта; без бинарника на ОС — запасной путь на GDScript (ключ в конфиге), пока Rust не станет обязательным. Кросс-сборка Windows с Linux автора —
  `cargo-xwin`/`cargo-zigbuild`; macOS с Linux требует SDK Apple (лицензия, `osxcross`) либо сборки на Mac — **вопрос**. Бинарники в git не класть (как GodotSteam, `.gitignore`).
- **Тесты.** Модульные — `cargo test` без Godot; игровые — существующие GDScript-тесты (`tests/…`, `tools/gpu_tests.sh` для GPU-путей) плюс тест «нативный = эталон GDScript».
  Для каждого перенесённого места GDScript-реализация остаётся эталоном до тех пор, пока тесты не станут зелёными на всех трёх ОС (macOS у автора запустить негде).
- **Совместимость gdext с Godot 4.7.2** — вопрос ниже; проверить на минимальной библиотеке (функция «сложить два массива») **до** любых решений.

## Открытые вопросы
1. **gdext и Godot 4.7.2.** Поддерживает ли актуальная версия godot-rust/gdext API 4.7 (feature `api-4-x`/`api-custom`, `extension_api.json` из `godot --dump-extension-api` самого 4.7.2)? Бинарник, собранный под более раннюю 4.x, вообще совместим вперёд, но не проверено; игра идёт на официальной сборке Godot 4.7.2 (`godot --version` → `4.7.2.stable.official`). Не проверено — нужна проба.
2. **macOS без возможности запуска у автора.** Как проверять нативную библиотеку на универсальной сборке (`lipo`, ad-hoc подпись внутри `.app` — `tools/build.sh`)? Без проверки на Mac риск молчаливого отказа загрузки расширения; нужен запасной путь на GDScript.
3. **Кросс-сборка.** `cargo-zigbuild`/`cargo-xwin` с Linux под Windows MSVC и macOS без Apple SDK — допустимо ли по лицензиям; или CI-матрица (в репозитории CI для игры нет, `.github/workflows/pages.yml` — только сайт).
4. **Определённость шума и термиков в сети.** `GustSpectrum` опирается на `FastNoiseLite` Godot (`gust_spectrum.gd:41-60`); термики/источники у ведущего и клиента должны совпадать (`fast-load.md`, «Кеш поля воздуха» — бит-в-бит). `air-cascade.md` снял требование побитового детерминизма для воздуха; для термиков и шума порывов — решить отдельно (какая реализация симплекса — одна на всех, или порывы у каждого свои).
5. **CPU-доля первой сборки места (R4) и объектов (R5).** Сколько из 55–62 с холодной сборки — сеть, сколько — расчёт? Без этого выигрыш не оценить. Замер и точка отсчёта — `tools/research/load_profile/`.
6. **Цена в кадре ветра в точке (R1) сегодня.** Последний замер — 48–50 мкс (`turbulence.md:239`) на старой выборке; `docs/guide/air-model/field-cpu.md:6` ещё пишет «3 точки × 120 Гц», в коде — 18 точек × 60 Гц (`pendulum_model.gd:1289-1305`, `configs/pendulum.json:79`). Нужен свежий замер на актуальном `main`: доля `air_velocity_at` в кадре и в тике физики.
7. **Rust-воздух и слабые машины.** Если CPU-решатель медленнее GPU (оценка в `air-cascade.md`: 15–50 мс/итерацию против 3,9 мс), нужно ли держать GPU-путь как основной, а Rust — как запасной (headless, без GPU)? Влияет на то, какие из R1/R2 окупаются.
8. **Пул потоков.** Как делить ядра между `rayon` и `WorkerThreadPool` во время загрузки (оба заняты) и в полёте (рендер, звук)?
9. **Репозиторий и владение.** Правила `workflow.md` (контракты на стыки, `task brief`) нужно распространить на крейты: кто пишет `docs/contracts/rust-ext.md` и фикстуры эталонов — координатор модуля.
