# План rust-ext — что ещё вынести в Rust (обзор)

## Статус
Идея, обзор по чтению кода и docs (2026-10-24); **замеров не делалось**, исполнителей и модуля нет. Числа с пометкой «оценка» — расчёт из
чужих замеров, не измерение. Отдельно сделана проба gdext на Godot 4.7.2 (раздел «Проба gdext») — она работает. Документ нужен, чтобы решить, какие
места брать после шага 0 из [air-cascade.md](air-cascade.md) («Вариант: библиотека на Rust»; тут не повторяется).

## Цель
Выбрать расчёты **рантайма игры**, которые выигрывают от нативной библиотеки (GDExtension через godot-rust/gdext), и порядок их взятия.
Только рантайм: `tools/` и любые офлайн-расчёты (пересчёт полей, подготовка данных, исследования) вне области.
Область по решению пользователя (2026-10-24): **воздух по рельефу — главный кандидат и самый тяжёлый; затем расстановка объектов; маятник; CPU-подготовка графики**.
Упрощённый ветер (аналитика при `air_model.enabled = off`) не рассматривается. Звук, сеть, интерфейс — вне области.
Критерии: горячий цикл в GDScript; работа на главном потоке или упор в `WorkerThreadPool`; долгая загрузка/генерация; нестабильность;
зависимость от GPU, которую хорошо иметь на CPU (слабые машины, headless, тесты).

**Принцип (решение пользователя 2026-10-24):** горячие циклы и проходы по миллионам точек — в Rust; в GDScript горячих циклов быть не должно.
- **Данные места — в крейте.** Карта рельефа и местности (высоты, покров, вода, производные поля) передаётся в крейт целиком один раз при загрузке места. Дальше крейт сам считает по ней всё тяжёлое: вход воздуха, поля рельефа, расстановку.
  - **Объём** — на примере `volcano_island`. Слои `detail` и `far` — по 1601×1601 (шаг 25 и 100 м), около 10 МБ на слой в `f32`. Вместе с масками 10/25 м (покров, вода) — десятки мегабайт, порядка поля Пикара.
  - **Передача:** один раз, `PackedFloat32Array` / `PackedByteArray` → gdext. Это одно копирование, миллисекунды (оценка, не замер); возможно, удастся и без копии.
  - **Текстуры для отрисовки остаются у Godot.** Две копии по десятку мегабайт допустимы.
  - **Граница.** Имеются в виду растры готового места из кэша `user://locations`. Сборка места из исходников — Copernicus, WorldCover, стадии `LocationBuilder` — остаётся в GDScript.
- **Godot опрашивает результаты** — по точкам или пачками.
- **Кандидаты на одни данные:** A1 (подготовка входа воздуха), A3 (`TerrainRelief`, стадии сборки), O2 (расстановка объектов), а также опрос высоты/покрова в точке (`height_at`, `surface_at`, `forest_at`). Последний сейчас идёт через Callable — источник вылета CR-17.
- **При смене места** данные крейта сбрасываются явным вызовом.

## Что есть в коде сейчас (опора выводов)
- GDScript — ~98 тыс. строк в `scripts/`; крупнейшие тяжёлые файлы воздуха: `scripts/atmosphere/air_model/air_runtime.gd` (1843 строки),
  `air_thermals.gd` (1152), `thermal_field.gd` (1241), `wind_field.gd` (739), `air_phase_cpu.gd` (754); маятник — `scripts/flight/pendulum/` (3260 строк).
- Почти вся тяжёлая работа уже вынесена в `WorkerThreadPool` (`PoolFor`, `scripts/core/pool_for.gd`; `docs/guide/fast-load.md`), то есть
  остаётся выигрыш на ядро (GDScript → нативный код) и снятие ограничений пула, а не «распараллеливание».
- Ограничения пула Godot 4.7 (`docs/guide/fast-load.md`): `wait_for_group_task_completion` из рабочего потока при пуле 2 потока вставал (обход — `PoolFor`);
  `AirThermals.build` масштабируется только до 4 потоков (общий spin-lock `ObjectDB`); при пуле 2 потока загрузка 24 с против 12,5 с на 20 потоках
  (`tools/research/load_profile/final.md`).
- GDExtension в проекте уже есть как класс решения: GodotSteam (`docs/guide/steam.md`, `tools/steam/fetch_godotsteam.sh`, пресеты «… Steam» в
  `export_presets.cfg`) — но как скачанный бинарник, не свой код. Rust в репозитории — только офлайн (`tools/osm_tiles/packer/Cargo.toml`).
- Сборки: Linux x86_64, Windows x86_64, macOS universal (`export_presets.cfg`: `binary_format/architecture`); собирает автор на Linux (`tools/build.sh`),
  CI игры нет (`.github/workflows/` — только сайт); macOS собирается без возможности запуска на месте («проверяет друг с Mac»,
  `.claude/skills/new-release/SKILL.md`).

### 4. Графика — CPU-подготовка
Узкое место кадра графики — GPU (облака, трава: `docs/perf/frame_profile/measurements.md`); CPU-подготовка уже в потоках. Что можно считать массивами:

| № | Что | Почему | Выигрыш | Цена / риск | Приоритет |
|---|---|---|---|---|---|
| G1 | **Выбор облаков** `CloudLayer._select` (`cloud_layer.gd:653`), `CloudModel.select`, записи облаков для компоновщика | Раз в 1 с ~31 мс на вызов (`after-fixes.md`, п. 2: прямой замер; в игре размазано по кадрам, PF-8) → 1 %-худших кадров 21–38 мс. Работает по `Dictionary` термиков | Пик ~31 мс/с → единицы мс (оценка) | Работает по `Dictionary` термиков (сами термики вне области). Отрисовка облаков — GPU, остаётся | средний |
| G2 | **Текстуры по рельефу**: `HeightLayer.make_max_texture` (пирамида максимумов, `height_layer.gd:275`, кеш на диске), `make_texture` (10–30 мс) | `R.mat.max_tex` 262–677 мс на материале рельефа (`table_lp.csv`, холодно, до fast-load; в тёплом профиле читается из кеша `maxpyr.bin`) | Холодная загрузка: сотни мс (оценка) | Малая граница (`PackedFloat32Array` → `PackedByteArray`); `ImageTexture` создаёт Godot | низкий |
| G3 | **Таблица пропускания солнца** `SunTransmission.build` (`cloud_layer.gd:~590`, первая сборка синхронная, пересборка в потоке) | Численная таблица; первая сборка на главном потоке при старте | Мал; не измерено | Малая граница | низкий |

Отрисовка облаков и теней — шейдеры, Rust к ним не применим (решение пользователя).

Для сравнения: `TerrainRenderer.build` (1,1–3,8 с на главном потоке, `table_lp.csv`) — материалы, текстуры и шейдерный прогрев, то есть API Godot; `trees.load_lods` 1,2–2,1 с — загрузка GLB. Это не считается в Rust.

Пояснения:
- **A1 и A2 связаны с шагом 0.** Если воздух идёт на Rust, то A2 — естественный вход «ветер в точке — вызов функции» (там и сказано), A1 — недостающие куски вокруг Пикара. Брать поэтапно: Пикар → ветер в точке → фазы/подготовка → окна.
- **Группа B.** Постановка упоминала параллельную сборку объектов (`scripts/game/game.gd:426-430`) и `_air_field_job` как возможную причину. По `cr-2.md` гонка стадий `objects`/`wind` в числе «не причина» (первая загрузка с тем же порядком проходит); подозревается жизненный цикл общего локального `RenderingDevice` при **повторной** загрузке (`air_runtime.gd`, `air_gpu_job.gd`) либо TDR/драйвер Blackwell. Rust-воздух на CPU убрал бы этот RD как класс проблем, но это следствие, а не доказанное лечение; правка жизненного цикла RD (`cr-2.md`, «Предложение правки») дешевле и от Rust не зависит.
- **Что стало бы быстрее везде** — не «параллелизм» (он есть), а скорость на ядро и независимость от размера пула Godot: на 4-ядерной машине это важнее, чем на 20 потоках автора (`final.md`: пул 4 → 18,1 с, замирание 2,8 с; пул 2 → 24,2 с).

## Что не выносить / вне области
- **Скалярные колбэки** (`height_at`, `ground_fn`, `air_fn` по одной точке): вызов через FFI не дешевле вызова GDScript; выигрыш только у пакетных границ (A2). Переносить `HeightLayer.sample` отдельно бессмысленно.
- **Шейдеры отрисовки** (`*.gdshader`: рельеф, трава, деревья, облака `cloud_raymarch_cs`, `cloud_composite_cs`, тени) и `CompositorEffect`: рендер на CPU на порядки медленнее. В Rust — расчёт воздуха, не отрисовка.
- **Создание ресурсов Godot**: `ArrayMesh`, `MultiMesh`, `Image`, WebP-кодек, загрузка GLB, `TerrainRenderer.build`. Это API движка; Rust может готовить массивы, но не заменить его.
- **`FlightModel`** (боты, 30 мкс/шаг), **`CloudField.step`** (сетка 400 м, уже в потоке, цена не видна).
- **Вне области по решению пользователя:** термики (A4 снят 2026-10-24: «расставить ~20 термиков — не дорого»; замер 2,9–4,2 с на генерацию клеток `F.gen` был до fast-load), упрощённый ветер, звук, сеть, UI/приборы/цели, Steam, отчёты о вылетах (менять путь отчётов нельзя, пока вылеты групп A/B не диагностированы), `tools/` и офлайн-расчёты.

## Общая инфраструктура
Предложение (без реализации):
- **Один workspace `rust/`, несколько крейтов, одна загружаемая библиотека.** Чистые крейты без Godot (`dp-air`, `dp-world`, …: `cargo test`, `criterion`, сверка с фикстурами
  `fixtures/air_model/` и `tests/fixtures/`) + один тонкий крейт-обёртка `dp-gd` (`cdylib`, gdext) — **один** `.gdextension` и один бинарник на ОС. Причины:
  один файл на ОС в сборке и подписи macOS; один общий пул потоков (`rayon`); изменения контракта границы — в одном месте. Несколько `cdylib` дали бы несколько пулов потоков и несколько бинарников в релизе.
- **Граница.** Только `PackedFloat32Array/PackedFloat64Array/PackedInt32Array/PackedByteArray/PackedVector3Array` на входе и выходе (вход — срез без копирования: проба `sum` читает
  `as_slice()`; выход — одно копирование); без `Dictionary`/`Object` в горячем пути; крупные состояния живут в Rust за `RefCounted`-обёрткой. Рабочие потоки Rust не трогают объекты Godot.
  Формат каждой границы — контракт `docs/contracts/rust-ext.md` с версией и контрактным тестом (правило workflow «Контракты»), сверка с GDScript-эталоном на фикстурах.
- **Потоки.** Один `rayon`-пул, размер из настройки игры (иначе спор за ядра с `WorkerThreadPool`: пул 2/4/20 даёт 24/18/12,5 с, `final.md`); вызов из главного потока не ждёт пул дольше порции
  (сравни `chunk_ms` для GPU, `air_gpu_job.gd`). Проба: поток `std::thread` внутри Rust главный не вешает (раздел ниже).
- **Профиль сборки** — как в air-cascade: `lto = "fat"`, `codegen-units = 1`, `panic = "abort"` (проба с ним собирается и работает); без `target-cpu=native`; ветка AVX2 во время работы. Обратная сторона `panic = "abort"`:
  паника в расширении валит всю игру без записи стадии — на границе проверять входы; нужен ли `panic = "unwind"` ради сообщения — вопрос.
- **Сборка и поставка.** `.gdextension` с путями под `linux.x86_64`, `windows.x86_64`, `macos` (универсальный dylib через `lipo`); `tools/build.sh` вызывает `cargo build --release` для трёх целей до экспорта;
  без бинарника на ОС — запасной путь на GDScript (ключ в конфиге), пока Rust не станет обязательным. Кросс-сборка Windows с Linux автора — `cargo-xwin`/`cargo-zigbuild`; macOS с Linux требует SDK Apple
  (лицензия, `osxcross`) либо сборки на Mac — **вопрос**. Бинарники в git не класть (как GodotSteam).
- **Тесты.** Модульные — `cargo test` без Godot; игровые — существующие GDScript-тесты (`tests/…`, `tools/gpu_tests.sh` для GPU-путей) плюс тест «нативный = эталон GDScript». GDScript-реализация остаётся эталоном,
  пока тесты не зелёные на всех трёх ОС (macOS у автора запустить негде).

## Проба gdext на Godot 4.7.2 (ответ на вопрос 1)
Код — `tools/research/rust_ext/gdext_probe/` (`rust/` — крейт, `godot/` — минимальный проект, не игра; `run.sh [debug|release]`). Проверено 2026-10-24, Linux x86_64, Godot `4.7.2.stable.official`, rustc/cargo 1.97.1.

**Результат: работает.** Крейт `godot` **0.5.5** (godot-rust/gdext, последняя на crates.io) с фичей **`api-4-7`**; пересборка с `extension_api.json` (`api-custom`) не понадобилась.
- Фичи API у 0.5.5: `api-4-2` … `api-4-7`. Без фичи крейт собирается под **API 4.6** («Initialize godot-rust (API v4.6.stable.official, runtime v4.7.2.stable.official)») и на 4.7.2 тоже работает без предупреждений — совместимость вперёд есть; `api-4-7` печатает «API v4.7».
- Собрались и загрузились: `debug` (101 МБ `.so`, `safeguards strict`) и `release` с `lto = "fat"`, `codegen-units = 1`, `panic = "abort"` (3,2 МБ, `safeguards balanced`). Холодная сборка debug ~55 с, release с fat LTO — несколько минут (шла параллельно вторая сборка).
- `Probe` (`RefCounted`): `add(a,b)` → 5; `sum(PackedFloat32Array 1e6 × 0,5)` → 500000.0; `start(ms)` запускает `std::thread`, `is_done()` / `take_result()` — **главный поток не завис**: за 1000 мс фонового счёта 148 кадров headless, наибольший интервал между кадрами 7–10 мс; повторный `take_result()` → `nan` (как задумано).
- В логе нет предупреждений совместимости и ошибок; единственная строка расширения — «Initialize godot-rust …».
- Не проверено: Windows и macOS, `rayon`, экспорт игры (`export_presets.cfg`), загрузка расширения в сборке-шаблоне `release` (проверено `.so` release под ключом `linux.debug` в редакторном бинаре).

Команды воспроизведения (из каталога пробы):
```
cd tools/research/rust_ext/gdext_probe && ./run.sh debug     # или ./run.sh release
# вручную: (cd rust && cargo build) ; XDG_DATA_HOME=$(mktemp -d) godot --headless --path godot --import (два раза) ; godot --headless --path godot
```
Грабли:
- **Первый `--import` в проекте без `.godot/` падает** (SIGABRT, код 134) и сообщает «Identifier "Probe" not declared» — расширение ещё не в списке; второй `--import` и запуск проходят. В CI/скриптах — импорт дважды (в `run.sh` так и сделано). Воспроизводится и с `reloadable = true`; без расширения в проекте код 0. Причина не разбиралась.
- `.gdextension` не может ссылаться на файл вне проекта (`res://../rust/…`): в пробе `godot/bin` — симлинк на `rust/target`; `run.sh` копирует проект во временный каталог и подставляет полный путь.
- Редакторный бинарь Godot (`godot`) берёт ключ `linux.debug`, даже если библиотека release: для проверки release-сборки её подставляют под этот ключ.
- Из-за `compatibility_minimum = 4.7` в `.gdextension` расширение не загрузится на Godot старее 4.7 — для релиза с игрой на 4.7.2 это нужное ограничение.
