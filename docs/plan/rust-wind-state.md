# rust-wind — состояние на паузе

Модуль остановлен посреди этапа 1–2 по решению пользователя (недельный лимит 74 %); этап 3 отложен. Подробности — заметка «пауза» (`.dpcli/dpcli log rust-wind`) и карточки задач (`.dpcli/dpcli task show <ID>`).

**Сделано (влито в `feature/rust-wind`, 29 задач):**
- контракт `docs/contracts/rust-wind.md` + разделы `rust-wind/{input,solver,trait,fixtures-tolerances}.md` (W1–W11; W2 v2, W4 v3, W5 v6, W11 v8);
- workspace `rust/`: `dp-air` (трейт `AirModel`, `picard_rs`), `dp-gd` (`DpAir`, `.gdextension`), сборка Linux и Windows (mingw-w64), профиль разработки; стенд `dp-stand` (RW-4, RW-4b, RW-5);
- эталоны со старого кода, два набора, `tools/wind_fixtures/` (RW-1, RW-1b); фасад `Atmosphere` по W2 (RW-2); починены три теста, падавшие на `main` (RW-0b, RW-0c);
- весь путь поля Пикара в крейте (RW-6a…6t): вход области, погода и солнце для поля, сборка случая, фазы 1–3 и заморозка колонн, решатель с запасными правилами, грубый старт 1200 → 400 м как общая операция, поле с подменой за `blend_s`, запечённые поля и кеш, оркестровка, окна 100/50 м (итерации = GPU-окна игры, побитно одинаково на 2 и 4 потоках). Разбор пути — `docs/research/rust-wind-field-path.md`.
- опрос `formula`: 3,3 мкс на 18 точек, 75 мкс на 1000 (RW-6q, бенч; не влит).

**Красное в `feature/rust-wind` — чинить первым:**
1. `rust/…/tests/contract.rs` `api_version_matches_contract_header` — ждёт версию 1, W2 уже v2.
2. `tools/wind_fixtures/verify.sh` — в `cases/*.json` устаревший sha1 `configs/atmosphere.json` (поменялся в RW-6j); `.bin`, `.desc.json`, `places/*` совпадают.

**В ветках задач, не влито (состояние — в `task note`):**
- **RW-3a** — потребители на фасад W2. Ревью accept, 4/5 проверок; не досчитано сравнение `tests/` с базой: в копии 42 падения после перезапусков, базовая сторона не досчитана.
- **RW-0e** — `tools/tests_vs_base.sh` (a9486500c). Без приёмки; полный прогон копии ~35 мин (цель была 25) — запускать job с таймаутом ≥ 9000 с.
- **RW-6q** — приёмка RW-6, часть 1 (c8c3011b4, 624db4778). Зелёные: T2, T4, T4a, T8, `pilot_left_baked`, бенч, места обоих островов; док `docs/research/rust-wind-rw6-acceptance.md`. **Красный T1 сильного ветра по 8 запечённым полям:** без правок ошибка 14–670× допуска. Нужны правки контракта (патч опыта — в доке, не закоммичен):
  - W11 v9: `apply_bc_all` / `init_warm` / `init_parent` обнуляют грани-стенки (tu/tv/tw = 0) и θ′, θ′_d в клетках земли, как `K_BC` (`air_picard.glsl:234`);
  - W5 v7: в заголовке места `climate_lag` — климат на дату − `water.lag_days` (30); сейчас `PlaceClimate::cell` даёт климат даты места, вода тёплая.

  С обеими правками: `lee_bowl` в допуске; окна `thermal_plain`, `east_cliffs`, `crater_ridge` в допуске (область — 9,8×, 2,3×, 2,3×); вне допуска `landing_hill` (слабый ветер, 473×) и `ridge_west`, `plateau_landing`, `thermal_slope` — `k` расходится на 0,6–2,5 %, **причина не найдена**.

**Не начато:** RW-2b, RW-3b, RW-3c, RW-6u (T1 слабого ветра), RW-7 (переключатель `gd | rust`); этап 3 (RW-8…12) и этап 4 (RW-13).
- RW-3c должна закрыть замечания ревью RW-3a: `--net-hide-remote` (`scenes/main.gd`) ничего не делает; боты и сетевые игроки не передаются фокусами; мёртвые поля воздуха в сетевой схеме; `CalmAir` отдаёт ветер вместо нуля по W2.

**Открытое:**
- таймаут поля: на 2 потоках область — 192 с при `tol_scale` 1, больше `air.timeout_s` = 180 с; RW-6q предлагает `timeout_s · clamp(sqrt(8/потоков), 1, 2)` — конфиг не менялся;
- загрузка на CPU на слабых машинах (оценка координатора 70–100 с на 2 потоках, замер выше) — порог не задан;
- macOS не собирается (решение пользователя: Mac-игроки на последней GPU-версии).

**Порядок при продолжении** (свежий координатор этапа 1–2):
1. Две красные проверки ветки модуля.
2. W11 v9 и W5 v7 → T1 сильного ветра; разобрать расхождение `k` на 0,6–2,5 % до переноса чего-либо ещё — переносить поверх поля, не сходящегося с эталоном, нельзя.
3. RW-0e (приёмка) → RW-3a (сравнение с базой, 42 падения) → RW-3b/3c → RW-2b.
4. RW-6u, затем RW-7 — первое место, где игра реально идёт на Rust.
5. Этап 3 — только отдельным решением пользователя (объём: одни термики ~2,4 тыс. строк GDScript; этап 1–2 занял ~13 % недельного лимита).
