# Модуль «ускорение расчёта ветра» (air-speed)

Ветка `feature/air-speed`, копия `~/deltaplan-air-speed` (от `main` a554502). Журнал — `docs/plan/air-speed_progress.md`,
контракты — `docs/air_speed_contracts.md` (S1, S2) поверх `docs/air_model_contracts.md` (C2 v5, C7 v2, C9 v2 в `main`).
Фон: `docs/air_model.md` → «Загрузка и пересчёт поля (AirRuntime, AM-06Б)», «Клипмапы»; `docs/air_model_gpu.md` →
«Замеры»; код — `scripts/atmosphere/air_model/`.

## Цель
Сократить время расчёта среднего поля ветра: этап загрузки «Рассчитываем ветер» и пересчёт в полёте. Физика и
результат поля не меняются.

Исходные числа (RTX 4070 SUPER, Онгудай 12:00, 3 м/с со 150°):
| Что | Сейчас |
|---|---|
| этап «Рассчитываем ветер», только область 400 м | 3,3–3,9 с: подготовка на CPU ~1,2 с (рабочий поток) + решатель 1,6–2 с стены (GPU 0,73 с) + сборка поля |
| то же с окнами 100/50 м | 5,0–5,5 с |
| пересчёт в полёте | 3,7–4,1 с стены, GPU 0,8–1,0 с |
| `AirThermals.build` | ~0,8 с на главном потоке (кадр) на каждое новое поле |
| итерация 400 м | ~4 мс, ограничена числом запусков (136–161) и барьерами |

Гипотезы главной сессии (по коду, не замерены): полёт — одна порция на кадр, sync только на следующем кадре, бюджет
≤ 0,8 промежутка кадров, GPU делится с отрисовкой, RD локального устройства — только главный поток; загрузка —
`poll_slice(40 мс)` отдаёт кадр, пока рисуется кадр, на GPU одна порция — простой; подготовка на CPU — поклеточные
вложенные циклы GDScript (`AirPlace.block_mean`/`water_fraction`/`solar_flux`, `AirCase.prepare`), дважды (пара).

## Решения пользователя (01.10.2026, не обсуждаются)
- **П. 2 (загрузка):** на этапе «Рассчитываем ветер» **замораживать UI и считать одним проходом** (без отдачи кадров,
  как `run_blocking`; область и окна). Отменяет прежнее требование плана air_model «окно не замирает» для этого
  этапа (формулировку в `docs/plan/air_model.md` / `docs/air_model.md` поправить при приёмке SP-2). Перед замиранием
  полоска загрузки показывает, что идёт этап ветра (последний кадр перед блокировкой).
- **П. 3 (подготовка на CPU):** поклеточные циклы — на шейдер (compute на том же RD) и/или операции `Image`
  (resize/усреднение) — что быстрее и проще; результат совпадает с нынешним (допуск — контракт S1, проверка
  эталонным тестом).
- **П. 1 (пересчёт в полёте):** сначала **разобраться, что можно сделать** — исследование/замер с вариантами, ценой и
  последствиями (кадр, плавность, AMD), без реализации; затем шлюз к пользователю с рекомендацией.
- Общие: физика и результат поля не меняются (побитно или в оговорённом допуске против нынешних эталонов, итерации
  те же); Vulkan compute, переносимо на AMD (целевая машина — RX 5600 XT 6 ГБ, Ryzen 5 4500, Win11; без CUDA и
  расширений NVIDIA); не шлифовать; совместимость не нужна.

## Границы и чего не трогаем
- Решатель (`air_picard.glsl`, `Params`, калибровка, число итераций) — не меняется. Слияние ядер/меньше запусков —
  только как вариант исследования SP-1 (на шлюз), не в SP-2/SP-3.
- Параллельный модуль `feature/air-start` (`~/deltaplan-air-start`) правит те же `AirRuntime`/`AirCase`/`AirPlace`/
  `AirWindowCase`/`AirClipmap` (C2 v6 `inflow_k`, C7 v3, C9 v3 — второй проход поля при загрузке). Его не трогаем;
  правки точечные; когда его вольют в `main` — влить `main` в `feature/air-speed`. Номера версий C7/C9 в
  `air_model_contracts.md` — при слиянии (после air-start), до тех пор наши изменения — в `docs/air_speed_contracts.md`.
- Термики (`AirThermals.build` на главном потоке) — не в SP-2/SP-3; вариант для полёта — в исследовании SP-1.

## Задачи

### SP-3 — подготовка входа решателя без поклеточных циклов GDScript (п. 3) — `dp-engineer`
Скоуп: замер разбивки CPU-подготовки (вход места, `domain_case`, `block_mean`, `water_fraction`, `solar_flux`,
`context`/`day`, `AirCase.prepare` ×2 — с нагревом и без, `gauss2d`, подготовка окон 100/50 м) на 4070-машине; **до
правок** — эталон нынешних выходов (фикстура из кода `feature/air-speed` a554502); перенос горячих циклов на
`Image` (resize/mipmap/усреднение, сохранение в рабочем потоке) или compute на RD — что быстрее и проще; контракт S1.
Файлы: `air_place.gd`, `air_case.gd` (внутренности `prepare`/`_closure`/`gauss2d`), `air_window_case.gd`; новый тест
`tests/atmosphere/test_air_prep_ref.gd` + фикстура. Не трогать: `air_runtime.gd`, `air_clipmap.gd`, `air_gpu_job.gd`
(SP-2), шейдеры решателя.
Приёмка:
- эталонный тест (headless, если подготовка без RD) зелёный на новом коде **и** на старом (фикстура из старого кода);
  допуски S1: целые (`kf`, `n_unk`, `n_fluid`, доля воды) — точно; `hc` ≤ 1e-3 м, `heat` ≤ 1e-3 Вт/м²; `col`/`lev`/`prm`
  ≤ 1e-5·max(1, |x|); область 400 м и окна 100/50 м Онгудая (12:00, 3 м/с со 150°) + ещё одно место/час (утро 9:00);
- GPU: поле после решателя (область + окна) — итерации те же, |Δu|, |Δv|, |Δw| ≤ 1e-3 м/с, |Δθ′| ≤ 1e-4 К против поля
  старого кода (лучше побитно); `tools/gpu_tests.sh --filter=test_air_` зелёные;
- время CPU-подготовки области (вход места + обе `prepare`) до/после, порознь по частям; цель — не больше 0,3 с
  (было ~1,2 с); то же для окон;
- подготовка остаётся вызываемой из рабочего потока (сигнатуры C2 v5 без изменений); если нужен RD — сначала к
  координатору (S1 v2: где идёт подготовка).
Оценка: 0,5–1 день.

### SP-2 — загрузка одним блокирующим проходом (п. 2) — `dp-engineer`
Скоуп: контракт S2 — `AirRuntime.load_field()` после кадра с этапом «Рассчитываем ветер» считает всё (подготовка,
решатель области, сборка поля, окна 100/50 м, сборка их полей) на главном потоке без отдачи кадров
(`AirGpuJob.run_blocking`, `AirClipmap.run_blocking`); кусками с кадром между ними — только если `LOAD_BLOCK_MS`
конечно (по умолчанию `INF` — один проход; значение решает шлюз (б)); `last_info` — разбивка времени. Полёт — без
изменений. Файлы: `air_runtime.gd`, `air_clipmap.gd`, при необходимости `air_gpu_job.gd`/`air_window_job.gd`
(только блокирующий путь), `game.gd` (кадр перед блокировкой — только если не хватает средств `AirRuntime`), тесты
`test_air_runtime_gpu.gd`/`test_air_window_gpu.gd`. Не трогать: `air_place.gd`, `air_case.gd`, `air_window_case.gd`
(SP-3), шейдеры.
Приёмка:
- контрактные тесты `--filter=test_air_speed_contracts` и `--filter=test_air_contracts` зелёные;
- поле загрузки побитно то же, что при нарезке `poll_slice` (те же итерации; GPU-тест);
- кадр экрана загрузки с этапом «Рассчитываем ветер» нарисован до замирания (кадр `load_probe --stage-shot=wind`,
  скриншот в `/home/greg/deltaplan/build/screenshots/sp2/`);
- стена этапа до/после на 4070 (`load_probe --location=ongudai --hour=12`, окно 1280×720; с окнами 100/50 м): этап,
  подготовка, решатель, сборка, окна; наибольший непрерывный кусок главного потока (`block_max_s`) — для шлюза (б);
- `tools/gpu_tests.sh --filter=test_air_` зелёные; пересчёт в полёте — прежние числа (не хуже).
Оценка: 0,5 дня.

### SP-1 — пересчёт в полёте: что можно сделать (п. 1) — `dp-researcher`, без реализации в игре
Скоуп: замер и разбор, куда уходят 3,7–4,1 с стены при GPU 0,8–1,0 с (порции на кадр, простои, бюджет, ожидание
sync, доля отрисовки, подготовка, сборка, окна); проверка гипотезы про RD из рабочего потока в Godot 4.7.2 (локальное
устройство в отдельном потоке, отдельное устройство на поток), общего RD (`RenderingServer.get_rendering_device()`),
двух порций в полёте, большего бюджета; цена на кадр (мс главного потока, рывки GPU), на плавность; `AirThermals.build`
0,8 с на главном потоке — вариант в рабочий поток; оценка времени этапа загрузки и пересчёта на RX 5600 XT (по
числу запусков, барьерам, памяти — из публичных чисел и замеров). Прототипы — в `tools/research/air_speed/`, не в
`scripts/`. Варианты с ценой (время работы, риск, AMD) и рекомендацией.
Приёмка:
- таблица разбивки времени пересчёта (замер на 4070, под замком GPU, с отметкой, был ли GPU занят), воспроизводимая
  командой;
- 3–6 вариантов: выигрыш (замер или прототип), цена кадра/плавности, переносимость на AMD, объём работы, риски;
- ответ «можно ли RD в рабочем потоке в 4.7.2» с проверкой (минимальный прототип);
- оценка стены этапа загрузки одним проходом на RX 5600 XT (для шлюза (б));
- данные и команды — `tools/research/air_speed/` (README), итог — в журнале модуля.
Оценка: 0,5–1 день.

## Волны
1. SP-3 ∥ SP-2 ∥ SP-1 — файлы не пересекаются (SP-3 — `air_place`/`air_case`/`air_window_case`; SP-2 —
   `air_runtime`/`air_clipmap`/`air_gpu_job`; SP-1 — только `tools/research/air_speed/`). Замеры на GPU — под замком.
2. Приёмка SP-3 и SP-2 → общий замер «до/после» модуля на 4070 (этап загрузки, пересчёт; порознь CPU-подготовка и
   решатель) → отчёт главной сессии.
3. По итогу SP-1 — шлюз (а); реализация выбранного варианта — новая задача после решения пользователя.

## Шлюзы
- (а) итог SP-1 — варианты пересчёта в полёте с ценой и рекомендацией.
- (б) этап загрузки одним проходом может выйти > ~4 с на слабой карте (Windows помечает окно «не отвечает» примерно
  после 5 с без обработки сообщений) — варианты (кусками по `LOAD_BLOCK_MS` с прокачкой событий между ними и т. п.).
- (в) любая развилка, которую решения выше не закрывают (например, SP-3 нужен RD → подготовка на главном потоке; стык
  с air-start).
- Приняты SP-2 и SP-3 — отчёт.

## Риски
- Замороженное окно на AMD (до ~15 с по оценке AM-06Б) — шлюз (б).
- air-start добавляет второй расчёт поля при загрузке (≈ +5 с): после слияния оба прохода — внутри блокирующего
  этапа; время этапа удваивается — учесть в шлюзе (б).
- Подготовка в float32 (`Image` RF, GPU) против float64 сейчас — сдвиг клетки `kf` при `hc` на границе уровня: допуск
  S1 требует `kf` точно; при сдвиге — к координатору.
- GPU общий с другими агентами — замеры под `flock -w 1800 /tmp/heat_ca_gpu.lock`, `nvidia-smi`, отметка о занятости.
