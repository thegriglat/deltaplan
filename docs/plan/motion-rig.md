# motion-rig — вывод движения на платформы подвижности

## Цель
Отзыв с Reddit (r/Hanggliding): у пилота платформа DOF Reality H4R (4 оси), его симулятор (Glidersim) её не поддерживает.
Сделать вывод движения из игры: рабочий для H4R и общий (generic UDP), чтобы подходили и другие платформы
через их софт (SimTools, FlyPT Mover, софт DOF Reality). Без зоопарка форматов.

## Решения пользователя (не обсуждаются)
- Общий модуль, а не только H4R.
- Физика прежде: в игре только честные величины из состояния физики полёта (удельная сила в точке пилота
  в связанной системе, углы, угловые скорости). Сглаживание, масштабы, washout, ограничения — в софте платформы.
- Вывод — из одного места состояния (движение пилота/подвесной системы): при появлении маятника пилот–крыло
  вывод не переписывать.
- Отправка не влияет на частоту кадров.
- Настройки — в настройках игры, по умолчанию выключено.
- Железа нет — приёмка по приёмнику-скрипту и тестам; в отчёте — что проверено только без платформы.

## Физика и границы модели
- Сейчас пилот и крыло — одна материальная точка (одно тело); точка пилота = центр масс системы, плюс
  кинематический перенос, если точка головы смещена от ЦМ (a_P = a_CM + ε×r + ω×(ω×r)) — по контракту M1.
- Удельная сила f = a − g (то, что чувствует вестибулярный аппарат; в горизонтальном полёте ≈ +1 g «вверх»
  по оси тела) — в связанной системе пилота.
- Углы ориентации — Эйлера (рыскание–тангаж–крен) пилота; угловые скорости — в связанной системе.
- Чего не умеет: маятник пилот–крыло (пока нет) — вывод возьмёт его автоматически из того же источника;
  вибрации, удары о землю как отдельный канал — нет (касание даёт то, что даёт физика).

## Задачи

### MR-1 Исследование протоколов (dp-researcher, веб)
Как DOF Reality H2/H3/H4R/H6 получают данные от игр: SimTools 2.x/3.x (GameEngine, Game Plugin, generic UDP / «GenericUDP»
плагин), FlyPT Mover (source «UDP» / generic, shared memory), собственный софт DOF Reality (DOF Reality Motion Software / «DOF Reality
Professional»). Какие величины ожидают (surge/sway/heave, roll/pitch/yaw, угловые скорости, скорость), единицы, частоты, знаки,
формат пакета (текст/бинарный, порядок, разделители), как приёмник задаёт формат. Есть ли готовые профили других авиасимов
(Condor, X-Plane, MSFS) — как пример.
Итог: `docs/research/motion-rig-protocols.md` (frontmatter type research, conclusion) — таблица «софт → вход → формат → URL»,
решение «какой протокол(ы) делаем» с обоснованием, рекомендованный формат пакета (поля, порядок, единицы), что игрок настраивает
в приёмнике. Не больше ~2 вариантов формата (желательно один).
Приёмка: файл есть, `dp docs check`, ≥ 6 URL, решение и формат пакета явно.

### MR-2 Отправка движения + настройки + приёмник (dp-engineer)
По контракту M1–M3: источник величин из состояния физики (M1), упаковка пакета (M2), отправка UDP из physics tick без
блокировки, настройки (M3) в UI настроек, по умолчанию выключено. Приёмник `tools/motion_rig/recv.py` (stdlib, печать и jsonl, оба формата MR-К2).
Тесты: формат пакета (контрактный), знаки на манёврах — горизонтальный установившийся полёт ≈ +1 g по вертикальной оси
вверх (heave ≈ +9.81 по контракту), крен вправо — знак roll, разгон вперёд — surge > 0; петля через приёмник
(игра headless шлёт → recv.py ловит → jsonl проверяется).
Приёмка: тесты `motion_rig` и контрактные — 0 упало; проверка приёмником; частота кадров — отправка без блокировок (неблокирующий сокет).

### MR-3 Документация и инструкция игроку (dp-writer)
`docs/guide/motion-rig.md` (как устроено, контракт, границы); англ. инструкция игроку `tools/motion_rig/README.md` (папка
`tools/motion_rig/` отдаётся игроку целиком: инструкция, recv.py, motion_generic.h, motion_formats.py; таблица полей обоих

почему SimTools/FlyPT Mover пока нет; generic — формат для самодельных приёмников). CHANGELOG — строка в «В работе».
Приёмка: `dp docs check`, файлы есть.

### MR-4 Вкладки в панели настроек (dp-engineer)

Правки минимальные: перенос существующих строк по вкладкам, без переделки самих настроек, ключей и сохранения; строки вкладок — в

Другие модули панель сейчас не трогают (проверено 10.10: правок settings_panel в ветках нет).
Приёмка: тесты `tests/ui/` — 0 упало; тест: у панели TabContainer, каждая прежняя настройка на одной из вкладок; скриншот панели
(по вкладкам) — по запросу пользователя.

## Итог MR-1 (принят 10.10)
Родной софт DOF Reality H-серии — Sim Racing Studio (SRS, Windows); вход для своих игр — SRS API v102 (UDP 33001, 236 байт, MIT).
SimTools 2/3 и FlyPT Mover общего UDP-входа не имеют (нужен свой плагин/код). Решение координатора: формат `srs` (по умолчанию)
+ один свой `generic` (64 байта, честные величины, для самодельных приёмников) — MR-К2. Знаки осей SRS не документированы —
проверка у игрока, инверсия в SRS.
