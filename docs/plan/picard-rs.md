# План picard-rs (код задач PR)

## Статус
Заведён 2026-10-24 от `main` @ 7087ca8b5 (после сдачи шага 0 air-cascade, 421d47685; полный журнал —
тег `archive/air-cascade`). Контракты — `docs/contracts/picard-rs.md`. Крейт —
`tools/research/air_cascade/picard_rs/` (README §7–17 и «multiversion против AC-R3» — исходные числа).

## Цель
Понять, годится ли Rust-Пикар на CPU для обоих случаев игры: расчёт поля при загрузке места (все ядра) и
фоновый пересчёт каждые `recompute_game_min` = 15 игровых минут и при смене ветра/погоды с тёплого старта
от текущего поля (`configs/atmosphere.json`, `scripts/atmosphere/air_model/air_runtime.gd`,
`docs/guide/air-model/runtime.md`).

## Решения пользователя (2026-10-24)
Задачи по порядку:
1. Оптимизация кода без asm: нельзя inline asm и ручные интринсики (`std::arch`/`core::arch`); можно
   перестройку данных и циклов — лишние чтения и копии, слияние проходов, блоки/плитки под L1/L2, порядок
   обхода, обратные величины в прогонке, индексные циклы → итераторы rayon / chunks. Мерить профилировщиком
   (`perf stat -e cache-misses,L1-dcache-load-misses,…`, `perf record`), не на глаз; каждое изменение — с
   замером и проверкой точности (итерации и `u_rel` против эталона, как AC-R3/R4).
2. Число потоков — параметр API решателя: свой `rayon::ThreadPool` на вызов solve, глобальный пул не
   трогать; функция библиотеки, не только флаг CLI (старт игры — все ядра, фон — часть).
3. Пересчитать время после оптимизации: полный solve 6/8/18 потоков, все случаи Онгудая, таблица до/после.
4. Меньшая невязка: поле после N итераций (30/50/100/150) против сошедшегося — max и rms |Δu|, |Δw|, м/с, во
   всей области и у старта; время до каждого N; порог «на глаз не видно» предложить с обоснованием —
   решение шлюзом пользователю.
5. Тёплое поле: тёплый старт от поля на T к условиям T+15 игровых минут, как в фоне игры — итерации, время
   на 2/3/6 потоках, сравнение с холодным; условия T+15 — как в игре; нет эталона пары — собрать из GPU-
   решателя / эталонных скриптов `tools/research/air_cascade` (как делались `ongudai_d400_*`). Ничего не
   выдумывать.

Требования к крейту (из air-cascade, в силе): комментарии на английском, функции по возможности чистые;
тесты на -O0, release `opt-level=3, lto="fat", codegen-units=1, panic="abort"`; multiversion оставить;
CPU без AVX2 не поддерживаем — базовую ветку не оптимизировать и не мерить; `cargo clippy` чисто,
`cargo fmt`; надёжный крейт вместо своего кода, pure-Rust; f32 в расчёте, f64 в редукциях — не менять
без замера. Замеры — только под `.dpcli/dpcli lock cpu <ID> -- tools/research/air_cascade/picard_rs/target/release/picard bench|solve …`
(18 слотов); время без замка или на фоне Godot не принимается; Godot — только под замком cpu с `timeout`.
- **Оптимизация пачками** (2026-10-24): правки не мерить по одной (выигрыш каждой — в пределах шума ~2 %); правки делать пачкой и мерить пачку целиком — время solve и perf-счётчики до/после; точность (итерации, u_rel против эталона) — после каждой пачки; пачка не ускорила или сломала точность — бисекция по её правкам.
- **Приоритеты оптимизации** (2026-10-24): 1) промахи L1 — главный акцент: порядок обхода, плитки/блоки, раскладка данных, мерить L1-dcache-load-misses; 2) rayon вместо последовательных/индексных циклов — вся работа в пуле параллельно; 3) не копировать память — без лишних clone/collect/временных массивов, буферы переиспользовать, срезы/представления; деления в прогонке и прочее — после этих трёх.
- **Арифметику не трогать** (2026-10-24): деления, FMA, перестановку формул — только если perf покажет упор в них; всё время — на память (L1, обход, копии) и параллельность через rayon.
- **API v2** (2026-10-24): SolveOpts — tol_scale (множитель к критерию эталона, 1.0 = как сейчас), max_iters, необязательный time_budget (остановка после итерации, на которой бюджет исчерпан, отдать текущее поле); Solved — достигнутые невязки (как Check), число итераций, причина остановки converged | max_iters | time_budget; CLI — тонкая обёртка; тест: каждая причина достижима, при tol_scale = 1.0 поля побитно те же. Делается отдельной задачей после PR-2 вместе с R4 (снимки, старт от снимка).
- **Пачка 1 оптимизации: слить build_mom** (2026-10-24): build_all_mom (solver.rs) строит шаблоны cu, cv, cw тремя проходами build_mom, читающими одни и те же nu, th, геометрию и маски — слить в один проход по ячейкам (общие входы читаются один раз); мерить L1-dcache-load-misses и время фазы mom до/после. Параллельность на уровне фаз (u/v/w через join, heat ∥ mom) не делать.
- **Мерить на 8 потоках** (2026-10-24): производительность при оптимизации (время и perf) — только 8 потоков, под замком cpu на все 18 слотов; серии 2/3/6/18 не гонять; таблица по другим числам потоков — только по просьбе пользователя на шлюзе.
- 2026-10-24: задача 5 (тёплый старт, PR-w) — замер на 2/3/6/8 потоках, один раз, на итоговом коде после оптимизации; «только 8 потоков» — для пачек оптимизации.
- 2026-10-24, задача 4 (PR-n): найти границу невязки, при которой поле годно для игры. По снимкам после N итераций (PR-5) и/или по tol_scale (1, 3, 10, 30, …) построить зависимость невязки (mom_rms, div_rms, th_rms) → отклонение поля от сошедшегося. Отклонение — в том, что чувствует пилот: |Δw|, |Δu| в м/с, max и rms по области, у старта и по высотам 10–400 м над рельефом; скорость потоков в термиках и на склонах. Время до каждой точки на 8 потоках. Порог предложить с обоснованием по вариометру и шуму термиков в игре (ничего не выдумывать); решение — шлюз. Для холодного и тёплого старта.
- **Порог невязки tol_scale = 5 принят и для загрузки (холодный старт), и для фонового пересчёта (тёплый старт)** (2026-10-24) — отклонение поля в пределах порога вариометра; с тёплого старта сойдётся ещё быстрее
- **Сходимость в штиль не разбирать** (2026-10-24) — в штиль стационарного течения физически нет — критерий там ничего не говорит
- 2026-10-24: итоговые замеры PR-o/PR-w (2/3/6/8 потоков) — при tol_scale 5, tol_scale 1.0 — база для сравнения; в PR-w добавить цепочку тёплых стартов T→T+15→T+30 (нужен случай h1230 — собрать инструментом PR-3; накопление ошибки против холодного h1230).
- 2026-10-24: объём модуля финальный — пачка 2 (PR-9), итоговые замеры PR-o/PR-w (2/3/6/8 потоков, tol_scale 5 и 1.0, цепочка T→T+15→T+30), описание крейта для интегратора (последняя задача; ревьюер с пустым контекстом проверяет, что по описанию можно встроить без чтения src), сдача. Встраивание в игру (gdext) — новый модуль, не здесь. Новых опытов не заводить.
- 2026-10-24, уточнение к описанию крейта: отдельной приёмки «по описанию без src» нет — обычная приёмка + ревью; главное — публичный API (типы, функции, поля, единицы, потоки, tol_scale, причины остановки, тёплый старт, формат входа/выхода, пример вызова); связь с игрой — коротко, ссылками файл:функция.

## Приёмка
- Точность каждого изменения кода: `blocks` ≤ 1e-5; `ref/` и Онгудай 8 потоков — `contract/tolerance.py
  --iters-tol 10` → `worst ≤ 1` (итерации ±10 от эталона f64 191/231/201/131, `u_rel` ≤ 1e-3, `th_abs` ≤
  0,05 К).
- Качество: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (dev),
  `check_contract.py --crate`, pure-Rust `cargo tree`, multiversion в зависимостях, нет `target-cpu=native`,
  нет `std::arch`/`core::arch`/`asm!`.
- Числа времени — только из R2-файлов, снятых под замком cpu, с `host.git` коммита кода.
- Ревью `dp-reviewer` — круги оптимизации (параллельный счёт, порядок редукций), R6 (пулы), PR-w/PR-n
  (выводы для шлюза).

## Шлюзы
- **Шлюз 1** (после PR-o): итог оптимизации — таблица до/после, что дало и что нет; продолжать ли круги.
- **Шлюз 2** (после PR-n, PR-w): порог невязки (сколько итераций), годится ли Rust-Пикар на CPU для
  загрузки места и для фона; вопросы одним списком.

## Условия остановки
- Оптимизация меняет итерации больше ±10 или `u_rel` > 1e-3 и причина не найдена за одну доработку — откат
  изменения, вопрос.
- Нет способа получить условия T+15 как в игре без выдумки (вход места на 12:15 не воспроизводится) — шлюз.
- Профилировщик недоступен (Q1) — круги оптимизации не начинать.
