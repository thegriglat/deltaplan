# Контракты модуля air-synth

План — `docs/plan/air-synth.md`, журнал — `tools/dp log air-synth`. Изменение интерфейса — только через координатора
модуля: версия +1, что изменилось, уведомление потребителей, их правка в том же шаге.

Код — `tools/research/air_synth/corpus/` (исследовательский, Python). Схема данных — **`proto/air_synth/v1/corpus.proto`
— единственный источник правды о полях**; Python-код из неё — `gen/` (`./gen.sh`, сгенерированное коммитится). Ниже —
то, чего в .proto не выразить: каталоги, кодировки, инварианты, поведение.

**Каталог данных** (вне git): `$AIR_SYNTH_DATA`, по умолчанию `~/air_synth_data` (из окружения, не зашит в код).
Место на `/home` на 04.10 — ~144 ГБ свободно; корпус 10⁴ рельефов (S1) ≈ 3,2 ГБ, условия — десятки МБ.
В git — код, .proto, контракт, небольшие сводки (json/md ≤ ~1 МБ).

## S1. Рельеф и корпус (версия 1)
**Владелец:** SY-1 (формат, чтение/запись, шарды, индекс, запуск корпуса). **Поставщик высот:** SY-2 (генератор, S3).
**Потребители:** SY-3 (условия), SY-4 (решатель, H7), SY-5 (массовая генерация), будущие задачи данных и обучения.

- Каталог корпуса: `$AIR_SYNTH_DATA/corpus/<имя>/` — `manifest.pb` (`CorpusManifest`, `contract = "S1 v1"`,
  `kind = "relief"`) + `manifest.txt` (тот же манифест в текстовом формате protobuf, для людей), шарды
  `reliefs-{shard:05d}.pb`, `index.pb` (`ShardIndex`, `kind = "relief"`), временное — `tmp/`.
- **Шард** — подряд идущие записи `Relief`: префикс длины varint32 + байты сообщения (protobuf delimited). Шард k содержит
  id [k·S, (k+1)·S) по возрастанию, S = `manifest.shard_size` (по умолчанию 100). Файл шарда появляется только целиком:
  запись в `tmp/` → fsync → переименование. Индекс — по всем готовым шардам, `entries` по возрастанию id; `offset` —
  начало префикса длины, `length` — длина сообщения без префикса. Индекс пересобирается из шардов детерминированно
  (отдельная команда), шарды — источник правды.
- **Высоты** (`HeightGrid`): h[j][i] = `offset_m` + `scale_m`·q, q — int16 little-endian, построчно (k = j·nx + i),
  i — восток (x растёт с i), j — север (y растёт с j; j = 0 — южный ряд); значение — средняя высота клетки, м над морем.
  Писатель выбирает `offset_m` = (min + max)/2, `scale_m` = max(0,05 м, (max − min)/65 000); |h − h_float| ≤ scale_m/2
  (+ 1e-9). Не `repeated float`.
- Сетки рельефа: `g100` — 384 × 384, dx = 100 м, x0 = y0 = −19 200 м (центр расчётной сетки генератора);
  `g400` — 96 × 96, dx = 400 м, x0 = y0 = −19 200 м, **блочное среднее 4 × 4 клеток g100 до квантования** (тот же
  конвейер, что у реального рельефа П6 air-nn: клетки 400 м — блочное среднее мелкой сетки по области
  x, y ∈ [−19 200, 19 200] м; `air3d/terrain.block_mean`). Обе сетки обязательны.
- `id` — номер рельефа (0 … n−1), ГСЧ рельефа — `numpy.random.SeedSequence([corpus_seed, id])`; `generator_version` —
  строка версии генератора (S3); `params` — **все** параметры генерации (именованные поля или `extra`), так что
  (corpus_seed, id, generator_version) → побитно те же float-высоты до квантования; `summary` — дешёвые сводки
  (определения — комментарии в .proto); `compute_seconds` в побитный повтор не входит.
- Инварианты: значения конечные; nx·ny·2 = len(h_i16); один и тот же запуск после прерывания продолжает с первого
  отсутствующего шарда и даёт побитно те же шарды, что непрерывный запуск (кроме `compute_seconds`); `manifest.complete`
  = true только когда все шарды есть и индекс собран.
- Чтение (Python, владелец SY-1, модуль `corpus_io.py`): открыть корпус по каталогу, `len`, получить рельеф по id через
  индекс (seek + чтение одной записи, без чтения шарда целиком), итерация по шардам, `to_float(grid) → float32 (ny, nx)`.
- **Контрактный тест** (`tools/research/air_synth/corpus/tests/test_contract_io.py`, pytest, без генератора — на
  искусственных полях): запись → чтение побитно; ошибка квантования ≤ scale/2; порядок осей (несимметричное поле:
  h растёт на восток и сильнее на север — проверка знаков после чтения); g400 = блочное среднее g100 ≤ scale;
  произвольный доступ по индексу совпадает с последовательным чтением шарда; пересборка индекса из шардов побитно та же;
  прерванная запись (файл в `tmp/`) не видна читателю; манифест с `contract` ≠ "S1 v1" — ошибка чтения; S2 — то же для
  `Conditions` (ссылка `relief_id` существует в корпусе).

## S2. Условия для сети (версия 1)
**Владелец:** SY-3. **Потребители:** SY-4 (H7), будущие наборы решателя и обучение (H1, H5).

- Каталог: `$AIR_SYNTH_DATA/conditions/<имя набора>/` — `manifest.pb`/`.txt` (`contract = "S2 v1"`,
  `kind = "conditions"`, `relief_corpus` — каталог корпуса S1), шарды `conditions-{shard:05d}.pb` (записи `Conditions`,
  шард k — рельефы id [k·S, (k+1)·S), внутри по (relief_id, cond_id)), `index.pb` (`kind = "conditions"`, `cond_id`
  заполнен). Шардирование, атомарность, продолжение — как S1.
- Исходные поля — те, по которым решатель P2 строил случай (`air_nn_pilot/airlite_gen.plan_rows` + `places.context`:
  час, U10, откуда дует, t_max, облачность, дата, lat/lon, сдвиг UTC). Модельный рельеф не имеет координат: lat/lon —
  условная точка из распределения мест P2 (выбор и обоснование — владелец SY-3, запись сюда при сдаче).
- `derived` — как их вычисляет код решателя (air3d/weather, ref_study) при построении случая, без своих формул там, где
  у решателя есть своя; дополнительно: `n_bv_s` (N над слоем перемешивания), `froude` = U_sat / (N·H), U_sat =
  U10·max_profile (скорость притока выше z_sat, `air3d/air.py → wind_profile`), H = `summary.relief_m` рельефа;
  `w_star_m_s` и `w_star_over_u` — **определение AN-4 (ann2)**, владелец восстанавливает его по документам и записывает
  сюда формулой; `mechanical` = w*/U < 0,5.
- Для H1 (сейчас): 1–2 условия на рельеф из распределения P2, только механический режим (`mechanical = true`; отбор —
  перевыбором с тем же зерном, детерминированно, доля отказов — в манифест `notes`). Штиль (U10 = 0) в набор H1 не входит.
- `strat_override` — для H5 (широкий диапазон Fr), **сейчас не заполняется** (`enabled = false`); решатель, которому
  дали `enabled = true`, обязан либо применить его, либо отказать — не игнорировать молча.
- Инварианты: один конфиг и зерно → побитно те же шарды; на каждый `relief_id` — `cond_id` 0 … k−1 без пропусков;
  значения конечные.

## S3. API генератора и запуск корпуса (версия 2)
**Владелец генератора:** SY-2 (`generator.py`). **Владелец запуска:** SY-1 (`run_corpus.py`). **Потребители:** SY-5.

- `generator.GENERATOR_VERSION: str` (напр. `"fs1-<7 знаков хеша файла генератора>"`).
- `generator.generate(corpus_seed: int, relief_id: int) -> (params: corpus_pb2.GenParams, z100: np.ndarray float64
  (384, 384))` — высоты над морем в осях [j — север, i — восток] (как S1), без квантования; чистая функция: без
  глобального состояния, ГСЧ только из `SeedSequence([corpus_seed, relief_id])`, результат побитно повторяется при
  `OMP_NUM_THREADS=1` (и при любом числе процессов запуска). `g400` и квантование делает запуск (S1), не генератор.
- Смесь типов — непрерывная: `params.mix` ∈ [0, 1] и параметры вокруг двух подобранных наборов (план §2), без
  дискретных типов; T (`t_total_yr`) — одно значение для корпуса.
- Запуск: `run_corpus.py gen --out $AIR_SYNTH_DATA/corpus/<имя> --n N --corpus-seed S --workers W [--shard-size 100]`
  (продолжение — той же командой; параллельно по шардам, процесс на ядро, `OMP_NUM_THREADS=1`), `run_corpus.py index
  <каталог>` (пересборка индекса), `run_corpus.py sample <каталог> --n 50 --seed 1 → id` (детерминированная выборка
  для проверок). Долгие запуски — `tools/dp job start` (tmux-сессия `dp`).
- **v2 (04.10, решение пользователя: параметры Fastscape настраиваются схемой Professor, корпус сэмплируется из облака
  настроек):** настраиваемые параметры θ передаются явно. `generator.TUNABLE: dict[str, (lo, hi, default)]` — имена
  и допустимые пределы θ (≈ 8–10: `uplift_max_m_per_yr`, `k0`, `diffusion_m2_per_yr`, `m_exp`, `k_logsd`,
  `fourier_amp`, `anisotropy`, `t_total_yr`, `tan_crit`, …; имена — поля GenParams или ключи `extra`).
  `generator.generate(corpus_seed, relief_id, theta: dict | None = None)` — θ задаёт настраиваемые параметры (прочие
  случайные выборы — формы, положения, поля — по-прежнему из `SeedSequence([corpus_seed, relief_id])`); `theta = None`
  — встроенное распределение генератора (непрерывная смесь, как v1). Настройка (Professor) зовёт генератор с θ точки
  и зёрнами 0…k−1; корпус — `run_corpus.py gen … --theta-cloud <файл.json>`: для рельефа id точка облака выбирается
  детерминированно из ГСЧ рельефа (отдельный поток `SeedSequence([corpus_seed, id, 1])`), θ и номер точки пишутся в
  GenParams (`extra["cloud_point"]`). Формат облака — `{"names": […], "points": [[…], …], "weights": […]?, "source": "…"}`.
- Go допустим только если замер покажет, что узкое место — наш Python-код (не ядро fastscapelib на C++), и Numba не
  помогает (решение пользователя 04.10).

## S4. Модельный рельеф → решатель (версия 1)
**Владелец:** SY-4. **Потребители:** будущие наборы решателя.

- Рельеф корпуса подаётся решателю P2 (`tools/research/air3d`, код решателя не правится; обрамление — как
  `air_nn_pilot/dataset.py`, набор `terrain`: только область 96 × 96 × 400 м, решения «с нагревом» и «без», предел
  итераций и цель «среднее поздних» П1 v3) как место с сеткой высот `g100` (после деквантования, float64, шаг 100 м,
  x0 = y0 = −19 200 м, вода — нет, стартов — нет). Высоты клеток решателя на 400 м (`R.grid_domain(loc, 400)`) совпадают
  с деквантованной `g400` с точностью до `scale_m` (тест).
- Время случая — стенное время решения области (оба решения), без подготовки; записывается с версией решателя
  (хеш `air3d/*.py`, как `s0-…` П1), устройством и числом воркеров.

## Потом (не делать сейчас): поля решателя
Решения решателя (13 высот × 7 каналов × 96 × 96 на случай, float16 ≈ 1,7 МБ) — **не в protobuf**: шарды массивов
(напр. `.npy`/raw float16 фиксированной раскладки, П1 `d400_*`), protobuf — только манифест и ссылки (случай → шард,
смещение, форма, dtype, версия решателя, статус и итерации, `late_spread60_p90`). Поля `Relief` 8–15 зарезервированы
под ссылки; схему опишет координатор новой версией S1/S5 перед задачей счёта.
