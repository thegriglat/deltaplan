# Контракты модуля air-synth

План — `docs/plan/air-synth.md`, журнал — `tools/dp log air-synth`. Изменение интерфейса — только через координатора
модуля: версия +1, что изменилось, уведомление потребителей, их правка в том же шаге.

Код — `tools/research/air_synth/corpus/` (исследовательский, Python, h5py). **Формат — HDF5** (решение пользователя
04.10, workflow.md «Массовые численные данные»: однородные массивы — HDF5; protobuf — только разнородные записи, здесь
не нужен). История: S1 v1–v2 и S2 v1 были на protobuf (шарды length-delimited) — **отменены до генерации данных**,
данных в старом формате нет.

**Каталог данных** (вне git): `$AIR_SYNTH_DATA`, по умолчанию `~/air_synth_data` (из окружения, не зашит в код).
Место на `/home` на 04.10 — ~144 ГБ свободно; корпус 10⁴ рельефов (S1) ≈ 3 ГБ, условия — единицы МБ.
В git — код, контракт, небольшие сводки (json/md ≤ ~1 МБ).

## Общее для S1 и S2
- Файл пишется **один раз** (временное имя в том же каталоге → закрыть → `os.replace`) и дальше только читается.
- **Части и общий вид.** Каждый процесс пишет свои файлы-части `part-{k:05d}.h5` (часть k — записи [k·S, (k+1)·S),
  S = атрибут `shard_size`, по умолчанию 100); общий вид — `corpus.h5` (S1) / `conditions.h5` (S2) из **виртуальных
  наборов (VDS)** по всем частям с теми же именами наборов и атрибутами корня + `complete = True`. Вид собирается
  детерминированно из частей отдельной командой и в конце запуска; части — источник правды. Читатель открывает вид
  (или одну часть — у неё та же схема). Продолжение после прерывания — с первой отсутствующей части; частично записанных
  частей не бывает (временные имена `*.tmp` читатель игнорирует).
- Строки — фиксированной длины (`h5py.string_dtype('utf-8', N)` или `S N`), числа — указанные типы.
- Атрибуты корня (обязательные): `contract` (str, напр. `"S1 v3"`), `kind` (`"relief"` | `"conditions"`), `created`
  (ISO), `git_commit`, `command`, `shard_size` (int), `n_records` (int — в части: записей в части, в виде: всего),
  `complete` (bool; в части всегда True). Читатель отказывает при неизвестном `contract`.

## S1. Корпус рельефов (версия 3)
**Владелец:** SY-1 (формат, `corpus_io.py`, запуск `run_corpus.py`, контрактный тест). **Поставщики высот:** SY-2
(генератор, S3), SY-6 (реальные места). **Потребители:** SY-3, SY-4, SY-5 (Professor), будущие задачи данных и обучения.

- Каталоги: модельный корпус — `$AIR_SYNTH_DATA/corpus/<имя>/`; реальные места air-nn v3 — `$AIR_SYNTH_DATA/real/p6v3/`;
  места игры — `$AIR_SYNTH_DATA/real/game/`. В каталоге — `part-*.h5`, `corpus.h5`, `manifest.json` (копия атрибутов
  корня + список частей, для людей).
- Атрибуты корня, кроме общих: `generator_version` (str: `"fs1-<7 знаков хеша>"` у модельных, `"real-p6v3"`,
  `"real-game"` у реальных), `corpus_seed` (uint64; у реальных 0), `theta_cloud` (str: путь и хеш облака S3 или "").
- Наборы (N — записей в файле; у всех ось 0 — запись, порядок по `relief/id` по возрастанию):

  | набор | форма, тип | что |
  |---|---|---|
  | `relief/id` | (N,) int64 | номер рельефа в корпусе (0 … n−1) |
  | `relief/h100` | (N, 384, 384) int16 | высоты на сетке 100 м |
  | `relief/h400` | (N, 96, 96) int16 | высоты на сетке 400 м |
  | `summary` | (N,) составной | `id` int64, `h_min_m`, `h_max_m`, `relief_m` (по h400), `slope_mean_deg_400` (центр. разности, без 1 клетки у края), `slope_p95_deg_100`, `compute_seconds` — float64 |
  | `gen/params` | (N,) составной | только у модельных: `id` int64, `corpus_seed` uint64, `cloud_point` int32 (−1 — без облака), далее столбцы `generator.PARAM_NAMES` (float64, порядок как в генераторе; список — атрибут `columns`) |
  | `place` | (N,) составной | только у реальных: `id` int64, `name` str16 (`t_0000`… или `askarovo`…), `lat_deg`, `lon_deg` float64 (центр), `system` str32 (горная система П6, `other` или `game`), `part` str8 (`pool` / `holdout` / `game`), `stratum` str32, `source` str32, `zoom` int32, `src_spacing_m` float64, `source_sha256` str64 |

- **Кодировка высот** (атрибуты наборов `relief/h100`, `relief/h400`): h = `offset_m` + `scale_m`·q, `offset_m` = 2500,0,
  `scale_m` = 0,15 (одинаковые для всего корпуса; диапазон −2415…7415 м над морем, ошибка ≤ 0,075 м); q = round(…);
  значение вне диапазона int16 — **ошибка записи** (не обрезать молча). Исключение — реальные места: узлы источника вне
  диапазона (артефакты карт, напр. `t_0164` −3244 м) обрезаются до границы, место вносится в `clipped_places` сводки
  `real/out/real_summary.json` и в атрибут корня `clipped_places` (str, через запятую); такие места не используются в
  настройке и приёмке. Прочие атрибуты: `dx_m` (100 / 400), `x0_m` =
  `y0_m` = −19 200 (западный и южный края области), `units` = `"m above sea level"`, `axes` = `"record, j (north), i (east)"`.
  Оси: i — восток (x растёт с i), j — север (y растёт с j; j = 0 — южный ряд); значение — средняя высота клетки (центр
  x = x0 + (i + 0,5)·dx).
- `h400` = **блочное среднее 4 × 4 клеток h100 до квантования** (тот же конвейер, что у реального рельефа П6 air-nn:
  клетки 400 м — блочное среднее мелкой сетки по области x, y ∈ [−19 200, 19 200] м). У реальных мест h100 — блочное
  среднее 4 × 4 узлов вырезки П6 (25 м, узел (800, 800) — центр); h400 тогда = `hc400` П6 (≤ 1e-6 м до квантования).
- Хранение: чанки (1, 384, 384) и (1, 96, 96) — один рельеф; сжатие gzip (уровень 4) + shuffle (lzf/blosc — только
  с записью здесь; blosc — только если `hdf5plugin` ставится без проблем).
- Модельный рельеф воспроизводим: (corpus_seed, id, generator_version, θ) → побитно те же float-высоты до квантования;
  `compute_seconds` в побитный повтор не входит. Продолжение после прерывания даёт части, равные непрерывному запуску
  по наборам `relief/*`, `gen/params` и столбцам `summary` кроме `compute_seconds`.
- **Места `part = holdout` (отложенные системы) не используются в настройке генератора и в обучении** — только
  приёмка H4.
- Чтение (`corpus_io.py`): открыть корпус по каталогу, `len`, рельеф по id (h100/h400 → float32 (ny, nx) в метрах),
  строки `summary`/`gen/params`/`place` по id, итерация пачками; запись части из списка готовых рельефов (генератор
  или реальные места).
- **Контрактный тест** (`tools/research/air_synth/corpus/tests/test_contract_io.py`, pytest, на искусственных полях):
  имена, формы, типы и атрибуты наборов; запись → чтение (ошибка квантования ≤ scale/2); порядок осей (поле растёт на
  восток и сильнее на север — знаки после чтения); h400 = блочное среднее h100 ≤ scale; вне диапазона int16 — ошибка;
  вид VDS по частям = чтение частей; пересборка вида побитно та же; `*.tmp` не виден; неизвестный `contract` — ошибка;
  `place` у реальных; S2 — то же для таблицы условий и существование `relief_id` в корпусе.

## S2. Условия для сети (версия 2)
**Владелец:** SY-3. **Потребители:** SY-4 (H7), будущие наборы решателя и обучение (H1, H5).

- Каталог: `$AIR_SYNTH_DATA/conditions/<имя набора>/` — `part-*.h5`, `conditions.h5` (вид), `manifest.json`. Атрибуты
  корня, кроме общих: `contract = "S2 v2"`, `kind = "conditions"`, `relief_corpus` (каталог корпуса S1), `cond_seed`,
  `k_per_relief`, `mechanical_only` (bool), `reject_fraction` (доля отказов перевыбора). Часть k — рельефы id
  [k·S, (k+1)·S), строки по (relief_id, cond_id).
- Набор `conditions/table` (M,) составной, gzip + shuffle:
  - ссылки: `relief_id` int64, `cond_id` int32;
  - исходные (вход решателя, как случай P2: `air_nn_pilot/airlite_gen.plan_rows` + `places.context`): `u10_m_s`,
    `wind_from_deg` (откуда, ° от севера по часовой), `hour_local`, `t_max_c`, `lat_deg`, `lon_deg`, `utc_offset_h` —
    float64; `sky` int8 (0 clear, 1 partly, 2 overcast; соответствие — атрибут `sky_codes`), `month`, `day` int8;
  - производные (как их вычисляет код решателя при построении случая): `alpha`, `max_profile`, `z_i_m`, `z_lcl_m`
    (над морем), `heat`, `brk`, `cap_agl_m`, `sun_el_deg`, `sun_az_deg`, `t_c`, `n_bv_s`, `froude`, `w_star_m_s`,
    `w_star_over_u`, `hs_w_m2` (средний поток тепла, по которому считался w*), `u_sat_m_s` (= U10·max_profile) —
    float64; `stability_class` int8 (A…F → 0…5), `has_cap`, `mechanical` — bool;
  - H5 (сейчас не заполняется): `strat_override` bool (False), `n_bv_override_s`, `z_i_override_agl_m` float64 (NaN).
    Решатель, получивший `strat_override = True`, обязан применить или отказать — не игнорировать молча.
- Определения: `n_bv_s` и `froude` — как `air_nn_pilot/pilotnn/film_bg.bg_raw`, но **без обрезки** (в P2 Fr обрезан
  на 3), хранится как есть (логарифм и обрезка — дело потребителя/сети): `froude` = U_sat / (N·H), U_sat = U10·max_profile
  (`air3d/air.py → wind_profile`), H = `summary.relief_m` рельефа. `w_star_m_s` = (g/θ₀ · Hs/(ρ·c_p) · z_i)^(1/3)
  (AN-4, ann2 `regime.py`), θ₀ = 300 К, ρ·c_p = 1206 Дж/(м³·К), Hs = среднее по области max(H, 0), H — поток тепла
  `air.solar_flux` с гашением у края (`heat_taper_m`), z_i — над средней высотой области; `w_star_over_u` = w*/U_sat;
  `mechanical` = w*/U_sat < 0,5. При N = 0 (нейтральный слой над z_i) `froude` = 1000 (заглушка «очень большое Fr»).
- lat/lon модельного рельефа — точка в боксе горной системы из конфига П6 (`terrain.yaml`): вес бокса ∝ площади, на
  систему ≤ 12 %, широта равномерна по площади; **только северное полушарие** (южные боксы — зеркально по широте), дата
  15 июля для всех, как в P2 (лето); utc = round(lon/15). У реальных мест — lat/lon места; места южного полушария —
  дата 15 января (лето). Распределение мест P2 точно не восстановить (индекс П6 удалён) — это приближение.
- Для H1 (сейчас): 1–2 условия на рельеф из распределения P2, только механический режим (перевыбор с тем же зерном,
  детерминированно); штиль не входит.
- Инварианты: один конфиг и зерно → побитно те же части; на каждый `relief_id` — `cond_id` 0 … k−1 без пропусков;
  значения конечные (кроме NaN полей H5).

## S3. API генератора и запуск корпуса (версия 3)
**Владелец генератора:** SY-2 (`generator.py`). **Владелец запуска:** SY-1 (`run_corpus.py`). **Потребители:** SY-5, SY-7.

- `generator.GENERATOR_VERSION: str` (`"fs1-<7 знаков хеша файла генератора>"`).
- `generator.PARAM_NAMES: tuple[str, ...]` — все параметры генерации (столбцы `gen/params`, float64; целые — как float),
  включая `mix`, `t_total_yr`, `dt_yr`, числа форм, вытянутость и т. п.
- `generator.TUNABLE: dict[str, (lo, hi, default)]` — настраиваемые θ (подмножество `PARAM_NAMES`, ≈ 8–10).
- `generator.generate(corpus_seed: int, relief_id: int, theta: dict | None = None) -> (params: dict[str, float]
  (ключи = PARAM_NAMES), z100: np.ndarray float64 (384, 384))` — высоты над морем, оси [j — север, i — восток], без
  квантования; чистая функция: ГСЧ только из `SeedSequence([corpus_seed, relief_id])`, побитный повтор при
  `OMP_NUM_THREADS=1` и любом числе процессов; θ обрезается по пределам TUNABLE; прочие случайные выборы от θ не
  зависят; `theta = None` — встроенное распределение (непрерывная смесь типов, `mix` ∈ [0, 1]); θ с NaN/inf — ошибка.
  **T — одно для корпуса**: `t_total_yr` может входить в TUNABLE (Professor настраивает его), но в облаке θ у всех точек
  одно значение T (общая подгонка T по всем квадратам эталона, затем подгонка прочих θ к каждому квадрату при этом T);
  `run_corpus` отказывает облаку с разными T.
- Запуск: `run_corpus.py gen --out <каталог> --n N --corpus-seed S --workers W [--shard-size 100] [--theta-cloud
  файл.json]` (продолжение — той же командой; несовпадение параметров с уже записанными частями — отказ; процесс на
  часть, `OMP_NUM_THREADS=1`); `run_corpus.py view <каталог>` (пересборка вида); `run_corpus.py sample <каталог> --n 50
  --seed 1`; долгие запуски — `tools/dp job start` (tmux-сессия `dp`).
- Облако θ: `{"names": […], "points": [[…], …], "weights": […]?, "source": "…"}`; точка для рельефа id — из
  `SeedSequence([corpus_seed, id, 1])`, номер точки — `cloud_point` в `gen/params`.
- Go — только если замер покажет узкое место в нашем Python-коде, а Numba не помогает (решение пользователя 04.10).
  Замер SY-1: ввод-вывод ≈ 0,1 % времени, остальное — ядро fastscapelib → Go не нужен.

## S4. Модельный рельеф → решатель (версия 2)
**Владелец:** SY-4. **Потребители:** будущие наборы решателя.

- Рельеф корпуса подаётся решателю P2 (`tools/research/air3d`, код решателя не правится; обрамление — как
  `air_nn_pilot/dataset.py`, набор `terrain`: только область 96 × 96 × 400 м, решения «с нагревом» и «без», предел
  итераций и цель «среднее поздних» П1 v3) как место с сеткой высот `relief/h100` (после декодирования, float64, шаг
  100 м, x0 = y0 = −19 200 м, вода — нет, стартов — нет). Высоты клеток решателя на 400 м (`R.grid_domain(loc, 400)`)
  совпадают с декодированной `relief/h400` с точностью до `scale_m` (тест).
- Время случая — стенное время решения области (оба решения), без подготовки; записывается с версией решателя
  (хеш `air3d/*.py`, как `s0-…` П1), устройством и числом воркеров.

## Потом (не делать сейчас): поля решателя

float16 (раскладка П1 `d400_*`: канал, высота AGL, j, i), чанк — один случай; таблица случаев (relief_id, cond_id,
статусы и итерации решений, `target`, `late_spread60_p90`, версия решателя); части и вид VDS — как S1.
