# Контракты модуля motion-rig

План — `docs/plan/motion-rig.md`. Менять — только через координатора (версия +1, что изменилось, уведомить потребителей).
Контрактный тест — `tests/contracts/test_motion_rig_contracts.gd` (headless, без сети и GPU): проверяет строки «## MR-К<n>. … (v<n>)»
этого файла, форму классов и полей ниже, разбор пакета по MR-К2.

## MR-К1. Точка пилота и величины движения (v3)
Владелец: MR-2 (v2 — MR-5, v3 — MR-6). Потребители: отправка (MR-2), будущий маятник пилот–крыло (поставщик точки пилота), документация (MR-3).

**Единственный источник — точка пилота в `Telemetry`.** `FlightModel._update_telemetry` заполняет в `Telemetry`
(`scripts/core/telemetry.gd`) три поля, мировая система сцены (X восток, Y вверх, −Z север), единицы СИ:
- `pilot_position: Vector3` — м, точка подвески/тела пилота (сиденье платформы ↔ тело пилота);
- `pilot_velocity: Vector3` — м/с, скорость этой точки относительно земли (инерциальная система);
- `pilot_basis: Basis` — ориентация связанной системы пилота: локальная −Z — вперёд, +Y — вверх (от ног к голове/по стойке),
  +X — вправо.
Сейчас (одна материальная точка): `pilot_position = position`, `pilot_velocity = velocity`, `pilot_basis = telemetry.basis`
(`Basis.from_euler(Vector3(theta, -heading, -bank))`). С маятником эти три поля начнёт заполнять он — вывод не меняется.
Поправки на смещение головы от точки (ε×r, ω×(ω×r)) не вводятся: платформа сама поворачивает сиденье, вращательную
часть ускорения головы даёт её движение.

**Величины** — `class_name MotionSample extends RefCounted` (`scripts/motion_rig/motion_sample.gd`), считает
`class_name MotionSource extends RefCounted` (`scripts/motion_rig/motion_source.gd`) из последовательности
(`pilot_position`, `pilot_velocity`, `pilot_basis`, время `t` с) и только из неё:
- `MotionSource.push(tel: Telemetry, dt: float) -> void` — шаг физики (dt — шаг физики, с); `sample() -> MotionSample` —
  величины за интервал от прошлого `sample()` до текущего (среднее по интервалу = разность состояний / время интервала,
  без фильтров); `reset() -> void` — разрыв (см. «Когда шлётся» ниже).
- Связанные оси пилота (авиационные): вперёд F = −Z_local, вправо R = +X_local, вверх U = +Y_local.
- `surge`, `sway`, `heave: float` — м/с², удельная сила f = a − g_vec в связанной системе: проекции на F, R, U.
  a = (v_k − v_{k−n}) / (n·dt) по `pilot_velocity`; g_vec = (0, −Units.G, 0). Знаки: разгон вперёд → surge > 0
  (сверх g·sin(pitch)); сила вправо (скольжение/внешняя сила вправо) → sway > 0; «давит в сиденье» → heave > 0.
  Ожидаемые значения в модели точки: установившееся планирование — a = 0, f = +g вверх, т. е. heave = g·cos(pitch),
  surge = g·sin(pitch) (≈ +1.1 м/с² при pitch ≈ 6.6°), sway = 0; координированный вираж с креном φ — sway ≈ 0,
  heave ≈ g/cos φ (центростремительное ускорение уже в наклоне силы); невесомость → все ≈ 0. Наклон g в осях
  тела входит в surge/sway/heave честно; его повторение каналом углов платформы — настройка софта платформы.
- `roll`, `pitch`, `yaw: float` — градусы, ориентация `pilot_basis`: yaw — курс проекции F на горизонт, 0 = север,
  по часовой (восток = 90), диапазон [0, 360); pitch — угол F над горизонтом, нос вверх > 0, [−90, 90];
  roll — поворот вокруг F, правое крыло вниз > 0, (−180, 180]: roll = atan2(−R.y, U.y).
  Для одной точки совпадают с `rad_to_deg(theta)`, `heading`, `bank` модели (контрактный тест).
- `roll_rate`, `pitch_rate`, `yaw_rate: float` — град/с, угловая скорость пилота в связанной системе за интервал
  (из относительного поворота B_{k−n}ᵀ·B_k / время): roll_rate — вокруг F, правое крыло вниз > 0; pitch_rate — вокруг R,
  нос вверх > 0; yaw_rate — вокруг U, нос вправо > 0. В Godot-осях: pitch_rate = ω_x, yaw_rate = −ω_y, roll_rate = −ω_z.
- `airspeed: float` — м/с, |`air_velocity`|; `air_lateral: float` — м/с, проекция `air_velocity` (воздушная скорость
  аппарата) на R (скольжение вправо > 0). Пока точка = ЦМ.
- `t: float` — с, сумма dt с `reset()`; `on_ground: bool` — `Telemetry.on_ground` (для `generic`).
- `valid: bool` — false на первом `sample()` после `reset()`/создания (нет прошлого состояния): тогда ускорение и
  угловые скорости = 0, т. е. surge = sway = 0, heave = проекция +g на U; отправка такой пакет шлёт.
- Защита от телепорта: если |a| > 50·g на интервале — считается разрывом, как `reset()` (удар о землю < 50 g).
Инварианты: `MotionSource`/`MotionSample` — никакого сглаживания, ограничения, масштабирования и washout (это делает софт
платформы). Единственные исключения — на уровне отправки (MR-К2 v3, «Поток»): плавный вход на переходах и множитель
ускорений на земле для `srs`; это защита железа и обход общей шкалы усиления SRS, а не фильтр физики, `MotionSample` они не меняют.

**Когда идут живые сэмплы (v3).** Живой поток (`push` на каждом шаге физики, без `reset()` на смене фазы) — во всех фазах
своего пилота: `standing`, `walking`, `running`, `flying`, `landed`, `failed`, а также стоянка после столкновения
(`Game._crashed`: физика стоит, поза неподвижна) и экран итога после посадки. Касание, удар посадки, разбег, отрыв,
уклон склона — то, что даёт физика. На земле — те же величины (стоя неподвижно на склоне: a = 0, f = +g, heave = g·cos,
surge/sway — проекции g; углы — реальная поза).
`reset()` — только на настоящих разрывах: новый полёт и «Ещё раз»/«На старт», старт в воздухе, телепорт и любая
постановка крыла (`reset_on_ground`/`reset_in_air`), начало и конец буксира (`start_catch_up`/`_end_catch_up`),
снятие паузы (как в v2), плюс защита от телепорта (50 g). Ожидание и осмотр — без `reset()` (поза не менялась, ревью MR-5).
Живых сэмплов нет (сэмплы не считаются, `push` не вызывается): буксир (`_tow_step`), пауза (`_paused`, в т. ч. сетевая),
ожидание (`_wait_step`), осмотр (`inspect_mode`), меню и экраны вне сцены полёта, загрузка сцены. **Пакеты при этом идут**
(MR-К2 v3, «Поток»): удержание последней позы, пока сцена полёта жива, нейтраль — когда её нет.

**Кто зовёт (v3).** Отправкой владеет автозагрузка `MotionRig` (`scripts/motion_rig/motion_rig.gd`, в `[autoload]`
`project.godot`; без `class_name MotionRig`), живёт всё время работы игры, `process_mode = PROCESS_MODE_ALWAYS`
(тикает и на паузе дерева), свой `_physics_process` с приоритетом после сцены полёта. Интерфейс для `Game`:
- `MotionRig.attach(game: Node) -> void` / `detach(game: Node) -> void` — полёт есть/нет: `Game.set_flying(true/false)`
  плюс `detach` в `_exit_tree` (`Game` живёт и под главным меню — там нейтраль, а не удержание);
  пока присоединена и живых сэмплов нет — удержание, иначе — нейтраль;
- `MotionRig.step(tel: Telemetry, dt: float) -> void` — живой шаг физики своего пилота (внутри `MotionSource.push`);
- `MotionRig.reset() -> void` — разрыв (MR-К1); `MotionRig.place: String` — название места (для `srs` location).
`Game` больше не держит `MotionOutput`; `MotionOutput` (упаковка, сокет) — внутри `MotionRig`.
История: v1 → v2 (11.10, MR-5) — поток во всех фазах своего пилота вместо только `flying`, `t` — время с `reset()`.
v2 → v3 (12.10, MR-6) — пакеты идут всегда, пока вывод включён (было: в меню, на паузе, в ожидании, осмотре, на буксире
пакетов не было — SRS уходил в standby, и переход standby → живые данные при появлении давал рывок, выбивавший приводы
DOF Reality, отзыв владельца 12.10); отправкой владеет автозагрузка `MotionRig`.

## MR-К2. Пакет UDP и поток (v3)
Владелец: MR-2 (v2 — MR-5, v3 — MR-6). Потребители: приёмник `tools/motion_rig/recv.py`, Sim Racing Studio (софт DOF Reality H-серии),
свои/самодельные приёмники, инструкция игроку (MR-3). Основание — `docs/research/motion-rig-protocols.md`
(SimTools 2/3 и FlyPT Mover общего UDP-входа не имеют, родной вход DOF Reality — SRS API).
- UDP, один датаграм = один `MotionSample` на адрес:порт из MR-К3; каждые N = max(1, round(physics_hz / rate_hz))
  шагов физики (величины — за эти N шагов по MR-К1). Два формата, выбор — `format` в MR-К3. Все числа little-endian.

### Поток (v3): режимы, плавный вход, множитель на земле, непрерывность
Защита железа (отзыв владельца DOF Reality 12.10: рывок при появлении выбивал приводы). Исключение из «без сглаживания
в игре» (MR-К1), решение главной сессии 12.10: плавный вход и множитель — только на уровне пакета, `MotionSample` честный.
- **Пакеты идут всегда, пока `enabled`**: в полёте, на земле, в меню, на паузе, в ожидании, осмотре, на буксире, при
  загрузке сцены — один пакет на N шагов физики (тикает `MotionRig._physics_process`, `PROCESS_MODE_ALWAYS`), `seq`
  подряд. Режим пакета:
  - `live` — в этом тике был `MotionRig.step()`: сэмпл MR-К1;
  - `hold` — сцена полёта присоединена (`attach`), живого шага нет (пауза, сетевая пауза, ожидание, осмотр, буксир):
    последний живой сэмпл, угловые скорости = 0, остальное (ускорения, углы, скорости, `on_ground`) — как было:
    платформа стоит, где стояла (на паузе посреди полёта держим позу; статическая g вместо ускорений развернула бы
    платформу вбок на паузе в вираже);
  - `neutral` — сцены полёта нет (меню, экраны вне полёта, загрузка) или живого сэмпла ещё не было: стоя на ровном
    неподвижно — surge = sway = 0, heave = +G, roll = pitch = 0, yaw — последний отправленный (курс не крутим),
    скорости и воздушная скорость = 0, `on_ground` = true, `valid` = false. В `srs`: все ускорения, углы и скорость 0
    (кроме yaw).
- **Непрерывность при зависаниях основного потока** (загрузка сцены, первый кадр, долгие кадры): если очередного пакета
  нет дольше 1.5 периода (1.5/rate_hz с), поток отправки (`Thread`, сокет под `Mutex`) повторяет последний отправленный
  пакет (в `generic` — со своим `seq` и битом `synthetic`). Интервал между пакетами ≤ 2/rate_hz (+ дрожание ОС), пока игра
  жива и вывод включён. После зависания догоняющие шаги физики шлют пакеты как обычно.
- **Плавный вход (`ramp_s`, MR-К3)**: на любом переходе — смена режима (neutral↔live, hold↔live, neutral↔hold),
  `reset()` при живом потоке, включение вывода, `configure()` (смена настроек, в т. ч. знаков и множителя) —
  запоминается последний отправленный пакет P0 (значения полей пакета после перевода единиц, множителя и знаков) и
  в течение `ramp_s` шлётся P = P0 + (P_target − P0)·w, w = smoothstep(τ/ramp_s) = 3x² − 2x³, τ — время с начала
  перехода; P_target — текущий пакет нового режима (живой — меняется во времени). Новый переход посреди старого —
  P0 = текущий отправленный (без скачка). Углы — по кратчайшей дуге с приведением yaw к диапазону формата.
  Смешиваются все float-поля пакета (ускорения, углы, угловые скорости, скорости); `t`, `seq`, флаги, строки — нет.
  `ramp_s = 0` — без плавного входа. Выключение вывода (`enabled` → false): плавно в `neutral` за `ramp_s`, затем сокет
  закрыть. Выход из игры — без плавного ухода. Применяется в обоих форматах.
- **Множитель ускорений на земле (`ground_accel_scale`, только `srs`)**: поля `lateral_acceleration`,
  `longitudinal_acceleration`, `vertical_acceleration` (после перевода единиц: vertical = heave − G, т. е. отклонение
  от «стоя на ровном») умножаются на s; углы, угловые скорости, скорость — нет (уклон склона чувствуется углами).
  s ведётся ограничением скорости, без ступеньки: цель s* = `ground_accel_scale` при `on_ground` сэмпла, иначе 1;
  s сдвигается к s* не быстрее (1 − `ground_accel_scale`)/`ground_blend_s` в секунду. Касание: s начинает спуск с 1
  в момент касания, поэтому удар посадки (первые ~0.1 с) идёт с s ≳ 0.8 при умолчаниях (0.3, 0.4 с) — толчок посадки
  остаётся; разбег — при s = `ground_accel_scale`. Подскок — s не прыгает. После `reset()`/в `neutral` s = s* сразу
  (переход закрывает плавный вход). В `hold` — по `on_ground` удержанного сэмпла.
  `generic` множитель не применяет (честные величины; флаг «на земле» в пакете — приёмник масштабирует сам).
- Порядок для пакета: сэмпл режима → перевод единиц и смещений (MR-К2) → множитель на земле (`srs`) → знаки (MR-К3)
  → плавный вход (в пространстве итоговых полей) → упаковка.

### Формат `srs` — Sim Racing Studio API v102 (по умолчанию), 236 байт
Структура C с нативным выравниванием (репозиторий https://gitlab.com/simracingstudio/srsapi, MIT):

| смещение | поле | тип | значение |
|---|---|---|---|
| 0 | api_mode | char[3] | `api` (+1 байт выравнивания = 0) |
| 4 | version | uint32 | 102 |
| 8 | game | char[50] | `Deltaplan`, добито нулями |
| 58 | vehicle_name | char[50] | `Hang glider` |
| 108 | location | char[50] | название места старта (UTF-8, обрезать до 49 байт по границе символа), +2 байта выравнивания |
| 160 | speed | float32 | `airspeed`, км/ч |
| 164 | rpm, max_rpm | float32 ×2 | 0, 0 |
| 172 | gear | int32 | 0 |
| 176 | pitch | float32 | `pitch`, град |
| 180 | roll | float32 | `roll`, град |
| 184 | yaw | float32 | `yaw`, переведённый в (−180, 180], град |
| 188 | lateral_velocity | float32 | `air_lateral`, м/с (скольжение; в модели точки ≈ 0) |
| 192 | lateral_acceleration | float32 | `sway`, м/с² |
| 196 | vertical_acceleration | float32 | `heave − G`, м/с² (в установившемся полёте и стоя на ровном ≈ 0) |
| 200 | longitudinal_acceleration | float32 | `surge`, м/с² |
| 204 | suspension_travel | float32 ×4 | 0 |
| 220 | wheel_terrain | uint32 ×4 | 0 |

Знаки — как в MR-К1 (нос вверх, правое крыло вниз, вперёд, вправо, вверх — плюс); SRS их не документирует —
при обратном знаке инвертировать ось в SRS (инструкция MR-3). G = `Units.G`.
Единицы ускорений — м/с² (v2): SRS их не задаёт, примеры SRS гоняют ускорения 0..10, README допускает −10..10
(`docs/research/motion-rig-protocols.md`); в g (v1) наши ±0.1 были ≈ 1 % шкалы — heave не двигал платформу даже на
максимальном усилении (отзыв владельца DOF Reality 11.10). Знаки не меняются (подтверждены на платформе).
История: v1 → v2 (11.10, MR-5) — ускорения `srs` в м/с² вместо g; пакеты и на земле (MR-К1 v2). Раскладка и размер
не менялись. v2 → v3 (12.10, MR-6) — поток (режимы live/hold/neutral, повтор при зависаниях, плавный вход, множитель на
земле для `srs`); раскладка `srs` не менялась; `generic` — version 2 (новые биты флагов).

### Формат `generic` — свой, для самодельных и будущих приёмников, 64 байта
| смещение | поле | тип | значение |
|---|---|---|---|
| 0 | magic | char[4] | `DPMR` |
| 4 | version | uint32 | 2 |
| 8 | seq | uint32 | номер пакета с запуска отправки, +1 на пакет |
| 12 | flags | uint32 | бит 0 — `valid`, бит 1 — на земле (`Telemetry.on_ground`), бит 2 — `synthetic` (не живой сэмпл: `hold`, `neutral` или повтор при зависании), бит 3 — `ramp` (идёт плавный вход, значения смешаны) |
| 16 | t | float32 | с, время полёта (сумма dt с `reset()`; в `hold`/`neutral` — последнее живое, не растёт) |
| 20 | surge, sway, heave | float32 ×3 | м/с², удельная сила как в MR-К1 (горизонтальный полёт: heave ≈ +9.81) |
| 32 | roll, pitch, yaw | float32 ×3 | град, как в MR-К1 (yaw [0, 360)) |
| 44 | roll_rate, pitch_rate, yaw_rate | float32 ×3 | град/с, как в MR-К1 |
| 56 | airspeed | float32 | м/с |
| 60 | air_lateral | float32 | м/с |

Машиночитаемый контракт пакета (решение пользователя 10.10: protobuf не делаем — поток реального времени, приёмники
часто на микроконтроллерах), всё в `tools/motion_rig/` рядом с инструкцией игроку:
- `motion_generic.h` — packed C-структура `generic` (little-endian указан явно в комментарии, `static_assert(sizeof == 64)`,
  поля с единицами и знаками в комментариях);
- `motion_formats.py` — единственное место раскладок на Python (struct-формат и имена полей обоих форматов);
  `recv.py` и проверки берут раскладку только отсюда;
- сверка: `.h` (offsetof/sizeof через cc, если есть компилятор) = `motion_formats.py` = таблицы этого раздела, и
  пакеты игры (петля) разбираются `motion_formats.py`.

Приёмник `tools/motion_rig/recv.py` (Python stdlib): `--port`, `--format srs|generic`, печать строкой и `--jsonl файл`
(строка на пакет: все поля по именам выше, `t_recv`); понимает оба формата; неверный размер/заголовок — строка-ошибка, не падение.

## MR-К3. Настройки (v3)
Владелец: MR-2 (v3 — MR-6). Потребители: панель настроек, отправка, инструкция игроку (MR-3).
- `configs/motion_rig.json` (слои `Config`): `enabled: bool = false`, `host: String = "127.0.0.1"`,
  `port: int = 33001` (SRS по умолчанию), `rate_hz: int = 60` (1…physics_hz), `format: String = "srs"` (`srs` | `generic`).
- `signs: Dictionary` — знак каждой выводимой величины, `"direct"` (по умолчанию) | `"inverse"`, ключи ровно:
  `surge, sway, heave, roll, pitch, yaw, roll_rate, pitch_rate, yaw_rate`. Применяется в обоих форматах к значению
  поля пакета после перевода единиц и смещений MR-К2: `inverse` → поле × (−1) (SRS vertical: −(heave − G), по MR-К2 v2);
  yaw — отрицание, затем приведение к диапазону формата (generic [0, 360), srs (−180, 180]). `MotionSample` и MR-К1
  знаков не меняют (честные величины); инверсия — только при упаковке. Неизвестное значение/ключ — как `direct`.
  Зачем: знаки SRS не документированы, платформы у нас нет — игрок правит сам без новой сборки (решение пользователя 10.10).
- `ramp_s: float = 2.5` — с, плавный вход на переходах (MR-К2 v3 «Поток»), 0…10, 0 — выключен.
- `ground_accel_scale: float = 0.3` — множитель ускорений `srs` на земле, 0…1 (1 — как в полёте).
- `ground_blend_s: float = 0.4` — с, время перехода множителя 1 ↔ `ground_accel_scale` (отрыв/касание), 0.05…2;
  только в конфиге. Вне диапазона — зажать в диапазон.
- История: v1 → v2 (10.10) — добавлен `signs`. v2 → v3 (12.10, MR-6) — `ramp_s`, `ground_accel_scale`, `ground_blend_s`.
- Читать — `Config.value("motion_rig", "<ключ>")`.
- Ключи машинные (не облако Steam): в `UserSettings.LOCAL_KEYS` и `steam/partner/auto_cloud.json` → `local_keys`
  (тест S7 сверяет списки).
- UI: `scripts/ui/settings_panel.gd`, раздел «Платформа подвижности» / «Motion platform»: флажок «Вывод движения»,
  поле адреса `host:port`, частота (Гц), формат (`SRS (DOF Reality)` / `Generic`);
  знаки `signs` — компактно (флажки «инв.» по 9 величинам) или только в конфиге, если UI раздувается;
  «Плавный вход, с» (`ramp_s`) и «Ускорения на земле, ×» (`ground_accel_scale`, подпись — только SRS). Сохранение — `UserSettings.save_patch("motion_rig", …)`; применяется сразу,
  без перезапуска полёта. Неверный адрес — отправка выключена, без исключений и без падений.
- Выключено → сокет не создаётся, на шаг физики — ноль работы сверх одной проверки флага.
- Отправка не блокирует кадр: `PacketPeerUDP` (неблокирующий `put_packet`), ошибки отправки (нет приёмника) молча
  пропускаются; сколько-нибудь заметной работы в шаге физики нет (≤ ~10 мкс на пакет).
