# Сжатие данных мест

Скрипты, числа, команды — `tools/research/location_compression/`.

|---|---|---|
| detail высоты | 3 666 258 (.br) | 5 563 873 (.zst) |
| far высоты | 4 053 115 (.br) | 5 668 044 (.zst) |

| osm.json | нет | 2 948 792 |

Итого по местам: ongudai 10,78 -> 16,96; aushkul 8,78 -> 14,26; askarovo 8,32 -> 12,98 МБ. Рост на место +5…6,7 МБ: высоты +3,5 МБ (+45% к brotli), osm.json +1…3 МБ (новый файл; в `user://locations/<ключ>` пишется для каждой точки), PNG +10% (другой encoder GDScript, без оптимизации), так как Godot-PNG хуже. pck не сжимает файлы (export_presets: только фильтры), поэтому pck растёт 1:1 с data (4 места ≈ 61 МБ из 148).

## Причины

1. Сборщик пишет `PackedByteArray.compress(COMPRESSION_ZSTD)` (dem_stage.gd `_write_layer`), project.godot не задаёт `compression/formats/zstd/*`, значит уровень по умолчанию 3 (подтверждено: результат Godot 5 563 873 байт совпадает с файлом в репозитории), окно 27, LDM выключен. Brotli q11 против zstd 3 — главная разница (на тех же данных zstd 19 даёт 4,07 МБ против brotli 3,67).
2. Формат: float32 с квантованием 1/32 м. Мантисса float32 после квантования всё ещё «шумит» в младших байтах, zstd без разнесения байтов и предсказателя берёт мало. Данные по сути — целые 17 бит (диапазон до 2,4 км x 32).
3. osm.json (JSON сырым текстом) раньше не хранился на месте.

## Варианты (средние МБ на место, 2 слоя высот; время на место, 2 слоя; Godot 4.7.2 headless, 1 поток)

Измерено в Godot (`results/godot_summary.json`). Ошибка — против текущих значений (уже кратных 1/32 м); для шагов грубее — ошибка квантования.

| вариант | МБ/место | запись | чтение | макс. ошибка |
|---|---|---|---|---|
| сейчас: float32 + zstd 3 | 11,03 | 0,3 с | 0,05 с | 0 |
| float32 + zstd 12 (Python) | ≈9,3 | 1,5 с | 0,05 с | 0 |
| float32 + zstd 19/22 (только project.godot) | 8,2 | 10 с / 8 с | 0,07–0,09 с | 0 |
| EXR float32 (Godot пишет zip) | 9,67 | 0,1 с | 0,08 с | 0 |
| EXR half | 3,68 | 0,04 с | 0,06 с | 1,97 м — не годится |
| PNG: Godot save_png сохраняет FORMAT_RH в 8 бит (11 КБ, потеря); 24 бит в RGB8 | 7,59 | 3,4 с | 0,16 с | 0 |
| int 1/32 + среднее W/N + zigzag + разнесение байтов + zstd 3 (GDScript) | 5,64 | 2,4 с | 2,2 с | 0 |
| то же + zstd 19 | 5,32 | 5,6 с | 2,1 с | 0 |
| WebP lossless, 24 бит в RGB8, шаг 1/32 | 5,46 | 1,7 с | 0,13 с | 0 |
| WebP lossless, шаг 1/8 | 4,20 | 1,6 с | 0,12 с | 0,0625 м (RMSE 0,038) |
| int 1/8 + предсказатель + zstd 3 (GDScript) | 4,35 | 2,2 с | 1,85 с | 0,0625 м |

Python-прикидка (сумма 4 мест x 2 слоя = 44,1 МБ сейчас; `results/py_sizes.json`): шаг 1/4 с градиентным предсказателем (W+N-NW) и zstd 19 — 10,4 МБ (2,6 МБ на место, ошибка до 0,125 м); 1/32 — 18,0 (zstd 19); 1/8 — 12,9. Предсказатель «градиент» лучше «среднего» на ~15%, «left» хуже.

Выводы по запрошенным форматам:
- EXR: Godot пишет float32 с zip, выигрыш всего 12%; half (10 бит мантиссы) даёт ошибку до 2 м; на GPU грузится как RF сразу, но без выигрыша в размере.
- PNG 16 бит Godot не умеет (`save_png` из FORMAT_RH — 8 бит, 11 КБ вместо мегабайт). Обход: 24 бит в RGB8 (R=старший) — работает, но Godot-PNG слабее WebP (7,6 против 5,5 МБ).
- WebP lossless побитово точен (проверено: 0 расхождений), нативный кодек быстрый на чтении (0,12 с на оба слоя против 2 с у GDScript-декодера предсказателя), загружается `Image.load_from_file` без своего декодера, затем `ImageTexture` -> шейдер: `h = ((r*255*256 + g*255)*256+b*255)/Q + h_min` (фильтр nearest, билинейно считать в шейдере); для CPU-кода высоты распаковать циклом по массиву байт (≈0,3 с на 2,56 М клеток, не измерялось отдельно — цикл распаковки в GDScript из бенча ≈ 1 с вместе с предсказателем).
- PNG-слои: Godot `save_webp(lossless)` даёт −30…40% к PNG (detail10 1,82 -> 1,28 МБ, surface 236 -> 144 КБ, water 61 -> 39 КБ; побитово равно; чтение то же). У detail10 (серый+альфа) Godot сохраняет RGB при нулевой альфе (exact), поэтому 1,28 МБ; Python без exact — 0,25 МБ, т. е. если нули под альфой не нужны, можно получить ×5 (не проверено в Godot, нужен свой preprocess).
- osm.json: zstd 3 = 1,08 МБ (из 2,95), zstd 19 = 0,82 МБ (чтение 0,04 с); правка — сжатый файл + `decompress` + JSON.parse.

## Рекомендация

Взять WebP lossless: высоты в RGB8 (24 бит, смещение от min, шаг 1/8 м), остальные PNG-слои и сохранение в WebP, osm.json в .zst. Оценка на место: высоты 11,0 -> 4,2 МБ; PNG 2,4 -> ~1,6 МБ; osm.json 2,9 -> 1,1 МБ; итого каталог altai 16,8 -> ~7 МБ (≈ −9,5 МБ), 4 места и pck ≈ −35 МБ (из 148); кеш точки ≈ 14,5 -> ~6 МБ.

Шаг 1/8 м: ошибка квантования ≤ 0,0625 м, это в десятки раз меньше погрешности Copernicus (метры) и сглаживания (smooth_sigma); если нужна прежняя 1/32 — 5,5 МБ вместо 4,2.

Минимум без кода сжатия: `compression/formats/zstd/compression_level=19` в project.godot — высоты 11,0 -> 8,2 МБ, но запись высот на точку пилота ≈ 10 с вместо 0,3 с (уровень 12: −16%, 0,8 с на слой) и меняется для всех compress() игры; лучше этот уровень не трогать глобально, а брать WebP.

## Стоимость правки (оценка)

- dem_stage.gd: `_write_layer` (≈15 строк: квантование -> RGB8 -> `Image.save_webp`), поле `file`/`quantize`/`min` в info (≈5 строк);
- height_layer.gd `load_from_file` (≈20 строк: `Image.load_from_file`, цикл RGB -> float);
- osm_stage.gd (save_png -> save_webp), surface_stage.gd, river_stage.gd — по 1 строке; surface_layer.gd/terrain.gd — расширения в именах файлов (≈5 строк); osm_data.gd + osm_stage.gd — чтение/запись .json.zst (≈6 строк); пересобрать data/terrain; сбросить кеши user://locations (совместимость не нужна); тесты контрактов на имена файлов.
- Итого ≈60 строк в 7 файлах. Запись WebP ~0,8 с на слой — быстрее, чем PNG.

## Границы

Измерено на 4 местах x 2 слоях (altai, ongudai, aushkul, askarovo); время — один запуск headless на этой машине, на Ryzen 5 4500 чтение может быть в 1,5–2 раза дольше. WebP lossless в Godot — libwebp; поведение «exact» (RGB под альфой) зависит от версии Godot.
