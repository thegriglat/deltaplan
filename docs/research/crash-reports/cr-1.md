# CR-1. Диагноз группы A (GTX 1050 Ti, D3D12, стадия wind)

## Отчёты

Сырые отчёты — вне репозитория (`~/.cache/dp-crash-reports/`). Здесь только обобщённые признаки.

| Признак | Значение (одинаково у всех семи) |
|---|---|
| Issues | #4, #5, #6, #7, #8, #9, #10 (17.10.2026, 7 отчётов за ~3 мин: вылет при каждом запуске) |
| Версия | 1.5.18, коммит `cd1a8b` = тег `v1.5.18` (`cd1a8be7`); код читался на этом коммите |
| GPU | NVIDIA GeForce GTX 1050 Ti (Pascal, дискретная), Windows 10 (19045) |

Общие признаки:

1. В начале лога у всех: `Required Vulkan instance extension VK_KHR_surface not found` (`rendering_context_driver_vulkan.cpp:494`), затем `Your video card drivers seem not to support Vulkan, switching to Direct3D 12` (`display_server_windows.cpp:8103`). То есть D3D12 здесь — **запасной** драйвер при неработающем Vulkan на этой машине, а не выбор проекта (в `project.godot` на `cd1a8b` строки `rendering_device/driver.windows` нет; закрепление d3d12 было в коммите `2535908c` и откачено `7bc09e9d`).
2. Последняя нормальная строка лога у всех: загрузка мест/объектов (`WorldObjects: … за 3 с`), сразу за ней — поток ошибок D3D12 (по 83–89 сообщений об ошибке создания буфера на отчёт).
3. Первые ошибки (до всякого `storage_buffer_create`): `Close failed with error 0x80070057` (`command_buffer_end`, `rendering_device_driver_d3d12.cpp:2649`), `Reset failed with error 0x80070057` (`command_buffer_begin`, `:2632`), `Close failed with error 0x80004005`; затем `Can't create buffer of size: N, error 0x887a0005` (`buffer_create`, `:941`) — для **любых** размеров, от 128 Б до 14 137 088 Б.
4. Последние строки лога у всех: серия `Buffer argument is not a valid buffer of any type` (`buffer_update`, `rendering_device.cpp:1177`) и `Storage buffer supplied (binding: 0) must provide one ID (0 provided)` (`uniform_set_create`, `rendering_device.cpp:4678`) — и обрыв: ни одной строки после.
5. Размеры отказавших буферов складываются в сетки решателя ветра: 1 622 016 Б = 4·96·96·44, 1 767 136 Б = 4·98·98·46, 14 137 088 Б = 4·98·98·368 (число плоскостей кратно 46; сетка с гало). Это буферы `AirGpu.buffer()` решателя/фаз.
6. Расхождение: в #10 в настройках запуска записано `wind_model: off` («Упрощённый» ветер), в логе есть `air_model: analytic (air_model.enabled = off)`, но стадия всё равно `wind` и тот же поток отказов storage-буферов. Почему при `off` в этом запуске создавались буферы решателя — **не объяснено** (см. «Причина», подраздел 3).

## Механизм отчёта

- **Метка сессии.** Автозагрузка `CrashReporter` при старте пишет `user://session.lock` (`scripts/core/crash_reporter.gd:48-57`: версия, время, pid, `stage: ""`, graphics); при штатном выходе (`NOTIFICATION_WM_CLOSE_REQUEST`, `_exit_tree`) метку удаляют (`crash_reporter.gd:115-128`). Метка осталась к следующему запуску — прошлый запуск «оборвался» (любой нештатный конец: падение, зависание с убийством процесса, потеря питания), собирается отчёт (`crash_reporter.gd:44-46`). Поэтому «вылет» в отчёте не обязательно нативное падение: достаточно, что процесс не вышел штатно.
- **Стадия.** `LoadProgress.stage(key, …)` вызывает `CrashReporter.note_stage(key)` (`scripts/core/load_progress.gd:52`; `crash_reporter.gd:104-108`) — последняя начатая стадия загрузки (`weather`, `objects`, `wind`, `glider` …; `start` и `flight` — `scenes/main.gd:351,1271`). `wind` — этап «Рассчитываем ветер» (`scripts/game/game.gd:441`), в нём GPU-решатель считает поле ветра места. При записи стадии пишется и `vram` (`CrashReport.vram_text`, `crash_report.gd:162`): занятая видеопамять **в момент начала** стадии, не «перед обрывом» буквально.
- **Хвост лога.** Лог прошлого запуска — самый новый датированный `user://logs/godot*.log` (`crash_report.gd:46`, `pick_previous_log`); путь пользователя заменяется на «~» (`sanitize`); при длине выше ≈60 000 знаков обрезается начало (`trim_log`, `build_body`, `crash_report.gd:91`). Лог пишется непрерывно, но хвост может не включать последние строки, если процесс умер при записи — поэтому «обрыв после uniform_set_create» означает «дальше в файл не попало».
- **Отправка.** Следующим запуском, ≤ 3 попыток, issue в репозиторий отчётов (`crash_reporter.gd:130-`, `MAX_ATTEMPTS`). Семь отчётов за три минуты = семь запусков подряд, каждый оборвался на стадии wind.

## Причина

Степень уверенности по частям указана в каждом подразделе.

### 1. Потеря устройства D3D12 — первичное событие (вероятно)

Доказательство (по логам, логический вывод):

- Код ошибки `0x887a0005` = `DXGI_ERROR_DEVICE_REMOVED`. Он возвращается и для буфера в 128 Б, поэтому это не нехватка памяти (для неё был бы `E_OUTOFMEMORY`, `0x8007000e`) и не лимит размера буфера. Занятая VRAM — около 1,2 ГБ из 4 ГБ.
- Раньше этих отказов идут `Close/Reset failed` у списков команд (`0x80070057`, `0x80004005`) — типичное поведение D3D12 после сбоя устройства/драйвера.
- Воспроизводится на каждом из семи запусков в одной и той же точке (после загрузки объектов, на входе в стадию wind) — сбой детерминированный, а не случайный TDR.

Чего не хватает до «подтверждено»:

- В логе нет сообщения `GetDeviceRemovedReason` (Godot его не печатает), поэтому нельзя сказать, какой именно вызов убил устройство: ядро решателя ветра (локальный `RenderingDevice`), либо отрисовка главного устройства. Первые ошибки (`Close failed` без номера устройства) относятся и к тому, и к другому; ошибки `vertex_array_create/index_array_create/draw_list_bind_vertex_array` (главный рендер) идут рядом с ошибками `buffer_get_data` на 256 Б (чтение скаляров `AirGpu`, 64·4 Б).
- Порядок «сначала упало ядро ветра, потом главное устройство» вероятен (устройства D3D12 на одном адаптере теряются вместе при TDR/сбое драйвера), но из лога не доказывается.

Что именно вызвало: **гипотеза** — первые отправки решателя ветра на локальном RD через D3D12-драйвер NVIDIA Pascal (запас: сборка конвейера `CreateComputePipelineState`, 40 ядер SPIR-V → DXIL; проверялись только под wine/vkd3d-proton на RTX 4070 SUPER и по отчёту пилота с RX 5600 XT — `docs/guide/air-model-gpu/blocks.md`, раздел переносимости, `docs/guide/gpu-validation.md`). TDR по времени маловероятен: порции (`AirGpuJob`, первая 150 000 «весов», `air_gpu_job.gd:35-43`) оцениваются ≈ 0,1–0,5 с на такой карте при пороге Windows 2 с.

### 2. Хвост лога из заявки — следствие, не причина (подтверждено воспроизведением цепочки)

Цепочка в коде `cd1a8b`:

1. `AirGpu.buffer()` (`scripts/atmosphere/air_model/air_gpu.gd:143-154`) вызывает `rd.storage_buffer_create(...)` и сразу кладёт RID в `_owned`, **не проверяя `is_valid()`**; при потере устройства получается пустой RID (`rendering_device.cpp:1483`), затем `buffer_clear` на нём (`:1270`).
2. `AirGpu.upload()` (`air_gpu.gd:157-160`) → `rd.buffer_update` на пустом RID → «Buffer argument is not a valid buffer of any type» (`rendering_device.cpp:1177`).
3. `AirGpu._uniforms()` (`air_gpu.gd:214-228`) → `RDUniform.add_id(пустой RID)` → `rd.uniform_set_create` → «Storage buffer supplied (binding: 0) must provide one ID (0 provided)» (`rendering_device.cpp:4678`).
4. Дальше запись команд с пустым набором уникальных ресурсов. На Vulkan (воспроизведение) движок печатает ещё `Uniforms were never supplied for set (0) …` (`compute_list_dispatch`, `:6845`) и процесс жив. В отчётах после `uniform_set_create` строк нет: на потерянном устройстве D3D12 процесс, вероятно, завершился (нативное падение драйвера/движка) или завис на ожидании GPU и был убит пользователем. **Гипотеза**: что именно оборвало процесс, по логу не видно.

Нигде на пути нет проверки результата: ни в `AirGpu.buffer/upload/_uniforms`, ни в `AirGpuJob` (`air_gpu_job.gd:84-90` проверяет только `init`/`_setup`), ни в `AirRuntime` (`air_runtime.gd:189-198, 285-302`: `_device()` проверяет только успех `init`). Потеря устройства после `init` — слепое пятно: откат на аналитический ветер (`AirRuntime._analytic`, `air_runtime.gd:1226`) срабатывает только по ошибке `init` и по `_fail(...)` задач, а те опираются на `error` задачи, который не ставится при пустых RID.

Подтверждено: сам механизм «пустой RID → именно эти два сообщения» воспроизведён на Linux (см. «Воспроизведение»). Не подтверждено: что в Windows-запуске RID стали пустыми именно из-за потери устройства (вывод по коду ошибки).

### 3. Аномалия #10: `wind_model: off`, но решатель работал (не объяснено)

В #10 строка `air_model.enabled = off` напечатана `AirRuntime._analytic` (`air_runtime.gd:317, 1226`) — то есть загрузка шла по упрощённому ветру, и всё же стадия `wind` записана и в логе те же отказы storage-буферов (суммарно 13 различных размеров, как и в остальных). Версии: (а) `AirRuntime._cfg` берётся снимком конфигурации один раз в `_init` (`air_runtime.gd:175`), а `Config.reload()` после сохранения настроек (`settings_panel.gd:463-483`) снимок не обновляет, поэтому `_device()` в `_ready` (`air_runtime.gd:180-183`) мог создать RD и ядра до смены настройки; (б) стадия `wind` могла быть записана раньше, чем сработала проверка `off`. Ни одна не доказана; без запуска на машине пилота проверить нельзя. Практический вывод для правки: переключатель «Упрощённый ветер» у пилота **не спас** от обрыва (по крайней мере в этом запуске), его нельзя считать обходным путём без проверки.

### Зависимость от драйвера

Первичное событие (device removed) относится к **D3D12**. На Vulkan у этого пилота игру проверить нельзя: Vulkan на его машине не инициализируется (`VK_KHR_surface not found` — вероятно, повреждённая/отсутствующая установка Vulkan-ICD или старый драйвер). Слепота кода к пустым RID от драйвера не зависит — она проявилась бы и на Vulkan при любой неудаче создания буфера (воспроизведено на Vulkan). Выбор и смена драйвера на Windows — задача CR-4.

- Коммиты `v1.5.18..main` по теме вылетов: только `003d7d62` (строка стадии в лог со сбросом, время и память на смене стадии) — улучшает диагностику, не лечит. CHANGELOG 1.5.19–1.5.21 про D3D12/потерю устройства не упоминает.

Выбранная пилотом точка (место вне готовых) запечённого поля не имеет, поэтому группа A на неё не опирается. Это не проверено прогоном.

## Воспроизведение

D3D12 на Linux недоступен (RTX 4070 SUPER, Vulkan), потеря устройства не воспроизводится, поэтому **первичная причина не воспроизведена**. Воспроизведена вторая половина цепочки: пустой RID буфера → те же сообщения движка.

```
cd <копия>   # ветка с этим документом
export XDG_DATA_HOME=~/.cache/dp-xdg/$(basename "$PWD")
godot --headless --path . --import          # один раз
godot --path . --script tools/research/crash-reports/cr-1/repro_invalid_buffer.gd
```

Скрипт создаёт `AirGpu`, затем буфер размера, который драйвер не создаёт (`1<<40` float, `storage_buffer_create` возвращает пустой RID), `upload()` и ядро `air_vec` с этим буфером выходным. Воспроизвелось (Vulkan, окно): `Buffer argument is not a valid buffer of any type` (`buffer_clear :1270`, `buffer_update :1177`), `Storage buffer supplied (binding: 1) must provide one ID (0 provided)` (`uniform_set_create :4678`), `Attempted to free invalid ID: 0` (`_free_internal :7744`, как в отчётах при `release`); процесс при этом жив и штатно выходит, то есть на Vulkan пустой RID сам по себе не рушит игру. Анализ отчётов (`analyze_reports.py`, читает `~/.cache/dp-crash-reports/*.json`, пишет только агрегаты) даёт `summary.json`.

Что пока не проверено и требует машины с D3D12 на Pascal (или пилота): какое ядро/вызов убивает устройство. Вариант проверки на Linux — `tools/gpu_tests.sh` / запуск под `wine` (vkd3d-proton, `--rendering-driver d3d12`, `docs/guide/gpu-validation.md`), но на RTX 4070 SUPER под vkd3d-proton загрузка проходила (1.5.14), поэтому это ожидаемо не воспроизведёт.

## Предложение правки

Без кода. Для CR-4…:

1. **Проверка результата GPU-вызовов в `AirGpu`** (`air_gpu.gd`: `buffer`, `upload`, `_uniforms`, `_pipeline`): пустой RID → `error`, пометка «устройство нездорово», остановка задачи через существующий `_fail` → откат на аналитику (`AirRuntime._analytic`). Тест на воспроизведение: `repro_invalid_buffer.gd` превратить в GUT/GPU-тест (в `tests/atmosphere/`): буфер невозможного размера → задача завершается `failed` без сообщений `uniform_set_create`, и `AirRuntime.load_field()` возвращает `false` с аналитикой. Риск: низкий; не должно менять поведение на здоровом устройстве (только ранний выход).
2. **Зонд устройства перед стадией wind**: малое ядро (`air_vec` над 1 КБ) + `sync()` + чтение результата; не прошёл — GPU-ветер отключён для этого запуска. Тест: тот же скрипт; риск: +десятки мс на загрузку; на потерянном устройстве зонд сам может зависнуть — нужен таймаут `sync` (в Godot у `RenderingDevice.sync` его нет, значит зонд в отдельном потоке/по порциям).
3. **Предохранитель от петли вылетов**: если метка прошлого запуска закончилась на стадии `wind` (она уже есть в `session.lock`), следующий запуск начинается с отключённым GPU-ветром (запись в `user://`, показ в меню «Ветер: упрощённый — прошлый расчёт оборвался», кнопка включить). Это единственный способ, который избавляет пилота от цикла «7 запусков = 7 вылетов», даже если первопричина (D3D12/Pascal) не найдена. Риск: ложное срабатывание после ручного убийства процесса на этой стадии — приемлемо (деградация к упрощённому ветру).
4. **Переключатель «Упрощённый ветер» должен реально отключать GPU** (`AirRuntime`: перечитывать `enabled` при каждой загрузке, не из снимка в `_init`; не создавать RD в `_ready` без необходимости) — после проверки гипотезы из подраздела 3. Тест: загрузка с `enabled=off` не создаёт `RenderingDevice` (счётчик `AirGpu.init`).
5. **Диагностика для следующего поколения отчётов**: в строку стадии/лог — результат `RenderingDevice` после стадии (первое сообщение об ошибке и `rd.get_device_name()`), и сообщение «device removed» один раз вместо сотен (отчёты по 47 КБ на 83 одинаковые ошибки). Это упростит различение «упало ядро ветра» и «упала отрисовка».
6. **Связь с CR-4** (драйвер): у пилота Vulkan не стартует из-за отсутствия `VK_KHR_surface`; что делать с драйвером на Windows вообще — решает CR-4. Для группы A после п. 1–3 игра должна жить на D3D12 с упрощённым ветром.
