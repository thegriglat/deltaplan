# CR-14: нативный стек вылета #20/#21

## Отчёты
- #20, #21 (thegriglat/deltaplan-reports): версия 1.6.0 (d6df90c8b), Linux, NVIDIA GeForce RTX 4070 SUPER, Vulkan 1.3.277 / Forward+, graphics high, стадия `wind`, обрыв через 0,3 и 1,1 с после начала стадии.
- Общее: сеанс без перезапуска, место загружено дважды, затем загрузка другого места; последние строки лога - `[stage] wind` и `PlaceData: ...`. Сценарий игрока (по сообщению пользователя): крупный город, затем популярное место из каталога - падение на первой же смене.
- Оба отчёта - тот же класс, что группа B в `cr-2.md`.

## Механизм отчёта
Как в `cr-2.md`: отчёт создаётся при следующем запуске по метке незавершённого сеанса (`scripts/core/crash_reporter.gd:121-130`, отправка `:46-52`); стадия - `CrashReporter.note_stage` (`:106-111`), в лог `[stage]` пишется через `printerr` (`scripts/core/crash_report.gd:202-203`). Хвост лога при жёстком обрыве неполон.

## Причина
Уверенность: **вероятно** (механизм по коду и по debug-логам подтверждён ошибками «null instance»; прямой связи именно этой ошибки с SIGSEGV в релизе прогоном не доказано, сборки с символами не было).

### Нативный стек
- Прогон под gdb, официальный редактор 4.7.2 (без символов, кадры `??`): `Thread 1 "godot" received signal SIGSEGV` - главный поток, верхний кадр `pthread_mutex_lock` (libc), ниже ~15 кадров движка без имён (адреса в бинаре), затем `__libc_start_main`; рабочие потоки (пул, `async-io`, libcuda) - в ожидании. После `continue` - `SIGABRT`. Повторяющиеся вложенные кадры соответствуют вызовам VM GDScript.
- Пользователь на релизной сборке: SIGSEGV главного потока, ветка после ObjectDB::get_instance (проверка слота), разыменование nullptr (разбор координатора, pc в релизном бинаре).
- GDScript backtrace падения снять не удалось: в релизе вызов `Callable` на удалённый объект не проверяется; в редакторе тот же вызов даёт ошибку (ниже).

### Цепочка (подраздел 1: основная)
1. `WorldObjects.build` вызывает `clear()` (`scripts/world_objects/world_objects.gd:275-284`, дети - `queue_free`) и присваивает новый `_place` (`:197`); `_work_fn = _place.height_at` (`:205`) - `Callable` на метод `PlaceData` (RefCounted).
2. `Callable` на метод хранит только ObjectID, ссылку на RefCounted не держит. `OsmLayer` передаёт его в `OsmTraffic.build` и `CityTrees.build` (`scripts/world_objects/osm_layer.gd:158-180`); узлы сохраняют как `_height_fn` (`osm_traffic.gd:105`, `city_trees.gd:79`).
3. При смене места прежний `PlaceData` освобождается, узлы трафика и городских деревьев ещё живут и в `_process` зовут `_height_fn`: `CityTrees._process` `city_trees.gd:158`, `OsmTraffic._process` `osm_traffic.gd:507` -> `advance` `:590` -> `_place_visual` `:680`.
4. Debug/редактор: `SCRIPT ERROR: Attempt to call function 'null::height_at (Callable)' on a null instance.` - в моём логе 84 раза, первый сразу за строкой `PlaceData:` первой же загрузки после меню; повторяется после каждой смены места. Релиз: `Callable::callp` без проверки -> `ObjectDB::get_instance` -> nullptr -> разыменование -> SIGSEGV.
5. Почему стадия `wind`: ошибки идут в кадрах загрузки сразу после строки `PlaceData` (по логам); связь с расчётом ветра как таковым не установлена.

### Подраздел 2: гонка маски (вторая проблема, не доказана как причина вылета)
`ShrubScatter._build` (`shrub_scatter.gd:293 -> 409 -> 435 -> 419`) и `RockScatter._build` (`rock_scatter.gd:285 -> 378 -> 401 -> 440`) в рабочих потоках читают `Terrain.surfaces` через `forest_at`/`surface_at` (`terrain.gd:685,695,1048-1062`), пока главный поток в `set_surfaces` (`terrain.gd:1136-1141`) очищает и пересобирает массив слоёв места. Следствие в debug: ~40 подряд `Out of bounds get index ~14,5M (on base: PackedByteArray)` в `SurfaceLayer._mask_channel` (`surface_layer.gd:224`) - размеры `mask_width/height` и `_mask_data` от разных слоёв. Дополнительно `set_forest_mask` (`surface_layer.gd:136-145`) присваивает размеры раньше `_mask_data`. Ожидание задач разброса перед сменой слоёв: `_check_key` ждёт только при смене ключа (`shrub_scatter.gd`), смена места через `set_surfaces` идёт раньше. Уверенность: **вероятно** как гонка (ошибки в логах), **гипотеза** как причина SIGSEGV.

## Исправлено ли в main
**нет.** `git diff d6df90c8b main` по `osm_layer.gd`, `osm/osm_traffic.gd`, `osm/city_trees.gd` пуст; `world_objects.gd:205` в main тот же. Правку ведёт CR-17.

## Предложение правки
Правку делает CR-17 (код не менялся).
1. Освобождаемый `PlaceData` не должен переживать узлы: либо держать ссылку на `PlaceData` в узлах OSM (`OsmTraffic`, `CityTrees`, остальные потребители `height_fn`), либо перед сменой места выключать их `_process` (`set_process(false)`, `free()` синхронно, а не `queue_free`) до освобождения `_place`; не передавать `Callable` на метод RefCounted в долгоживущие узлы - передавать данные (`PackedFloat32Array` высот) или объект-держатель.
2. Для гонки маски: перед `set_surfaces` дожидаться/останавливать задачи `ShrubScatter`/`RockScatter` (по образцу `_check_key`), либо потоку передавать неизменяемый снимок слоя; `set_forest_mask` присваивать `_mask_data` до размеров.
3. Тест на воспроизведение (debug, `tests/`): загрузить место A (с OSM-трафиком), сменить на B, прогнать кадры - ни одной ошибки `null instance`; второй: смена места с большой маской на малую при идущем разбросе - ни одной `Out of bounds` из `_mask_channel`. Риск: нужно проверить все `Callable(place, "height_at")`; смена порядка освобождения может задержать смену места на кадр.
