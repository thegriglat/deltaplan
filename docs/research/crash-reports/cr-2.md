# CR-2 Диагноз группы B: RTX 5060 Laptop, Vulkan, стадия wind/objects

## Отчёты
- Issues #11–#15 (приватный репозиторий отчётов), все: версия 1.5.19 (b0da8b, тег v1.5.19), Windows 10, NVIDIA GeForce RTX 5060 Laptop (Blackwell), Vulkan API 1.4.351, Forward+, graphics high.
- Стадия последней строки: #12–#15 — `wind`, #11 — `objects` (до `wind`).
- VRAM перед обрывом 690–895 МБ — не исчерпание.
- Общие признаки (по строкам `[stage]` хвоста, без копирования лога):
  - В каждом отчёте обрыв — **не первая загрузка** процесса: перед ним есть стадия `menu`, затем новый цикл `start → … → objects → wind`. Первая загрузка в сессии у всех завершилась (`wind → glider → flight`), в #14 успешно прошли две загрузки, обрыв на третьей.
  - Время стадии от запуска: #15 — 46,6 с (вторая загрузка), #14 — 1550 с, #13 — 623 с, #11 — 2630 с, #12 — 3337 с.
  - Расчёт поля первой загрузки: 6,6–12 с; в сессии до обрыва в полёте проходили пересчёты поля «срок 15 мин» на том же GPU без сбоев.
  - Ни одной строки ERROR/WARNING от GPU/Vulkan рядом с обрывом (в #11, #12 есть посторонние `AirPlace: область вне слоя рельефа` — повторяются весь сеанс, к обрыву не привязаны).
  - В #13 первая загрузка взяла поле из кеша (стадии wind не было), вторая — пошла на расчёт.
- Группа A (CR-1, GTX 1050 Ti, D3D12) отличается: там есть ошибки RenderingDevice. Группа C (#3) — другая версия и стадия. Общее с A — только стадия wind.
- Зависимость от драйвера: у группы B API один (Vulkan), сравнить с D3D12 по этим данным нельзя; причина, по отчётам, привязана к GPU/RTX 5060, но не доказана.

## Механизм отчёта
- Отчёт — не пойманное падение, а признак «прошлый запуск не завершился штатно»: метка `user://session.lock` ставится при старте и удаляется при закрытии окна/выходе (`scripts/core/crash_reporter.gd:121-130`); найдена метка при следующем запуске — собирается отчёт и уходит в GitHub (`crash_reporter.gd:46-52`). Вылетом считается и убитый из диспетчера задач зависший процесс.
- «Стадия» — последнее значение `CrashReporter.note_stage` (`crash_reporter.gd:106-111`), вызывается при смене стадии экрана загрузки; в лог пишется строка `[stage] …` через `printerr` со сбросом на диск (`scripts/core/crash_report.gd:202-203`). Остальной лог при жёстком обрыве может не дойти до файла, поэтому «нет ERROR» не доказывает отсутствие сообщений.
- «Время» — `Time.get_ticks_msec()` с запуска процесса на момент смены стадии, «VRAM» — `rd.get_memory_usage` основного устройства (`crash_report.gd:166-170, 206-210`): после последней смены стадии данных нет — неизвестно, обрыв это сразу после строки или через минуты (зависание).

## Причина
Подтверждена только область, не строка кода.

### Что известно (подтверждено по отчётам)
- Обрыв лежит в окне между сменой стадии на `objects`/`wind` и следующей строкой `[stage] glider` при **повторной** загрузке места в той же сессии, а не при первой.
- Что делает код в этом окне (v1.5.19): `scripts/game/game.gd:417` (`objects`), параллельно `_air_field_job` (`game.gd:~520-560`): ожидание снимка поверхности (`AirRuntime.wait_place`, пул потоков), стадия `wind` (`game.gd:541`), `AirRuntime.load_field` (`scripts/atmosphere/air_model/air_runtime.gd:364`) → `stop()` (`:764`) → `_begin` → фазы и решатель Пикара на GPU порциями. В #11 обрыв случился ещё до стадии `wind`, т. е. до первой порции GPU этой загрузки: значит, дело не только в ядрах ветра.

### Гипотеза 1: состояние общего локального RenderingDevice после предыдущей загрузки (вероятно)
- `AirRuntime` — один узел на всю игру, один `RuntimeGpu` (локальный RD) на жизнь узла (`air_runtime.gd:159, 212-221`). Все задачи (фазы, Пикар, окна клипмапа, `_building`, `_coarse_job`) разделяют его.
- `AirGpuJob.release()` вызывает `gpu.release()` (`air_gpu_job.gd:198-205`), а `RuntimeGpu.release()` (`air_runtime.gd:~1765-1778`) освобождает **все** буферы после `_base` и сбрасывает общие наборы привязок — не только буферы этой задачи. `stop()` (`:764-783`) зовёт `release()` у нескольких задач подряд, а `setup()` при смене ключа места ставит `_clip = null` без `release()` (`:239`): буферы клипмапа предыдущей загрузки остаются на общем RD или освобождаются под ногами живых задач. Первая загрузка идёт на чистом RD, поэтому проходит, повторная — на RD с «хвостом».
- Против: на Linux/NVIDIA (4070 SUPER, Vulkan 1.3.277) это не даёт ни падения, ни ошибок RD (см. «Воспроизведение»); нужен драйвер Windows/Blackwell (1.4.351) либо отличающиеся условия.
- Ограничивает уверенность: нет ни одного лога с ошибкой RD; прямого доказательства использования освобождённого RID нет — только чтение кода.

### Гипотеза 2: сброс/зависание GPU (TDR) или сбой драйвера на новой карте (гипотеза)
- Защита от TDR (порции ≤ 200 мс по худшей цене, `air_gpu_job.gd:36-43`) подогнана под RTX 4070 SUPER и RX 5600 XT и на Blackwell/Windows не проверялась (`docs/guide/gpu-validation.md:65`). Лог без ERROR и обрыв без сообщений совместимы с падением драйвера или с зависанием окна (убитый процесс даёт ту же метку).
- Ограничивает: в первой загрузке и пересчётах в полёте на том же GPU сбоев не было, т. е. нагрузка порции сама по себе не фатальна; сочетание «повторный» + «Blackwell» — единственный признак.

### Не причина
- Исчерпание VRAM (690–895 МБ), ошибка компиляции ядер (ядра собираются при старте `air_runtime.gd:203`), гонка стадий `objects/wind` в одной загрузке (первая загрузка в каждом отчёте проходит с тем же порядком).

## Исправлено ли в main
**нет.** `git diff v1.5.19 main` по `scripts/atmosphere/air_model/air_runtime.gd`, `air_gpu.gd`, `air_gpu_job.gd`, `air_clipmap.gd` — без изменений; в `scripts/atmosphere` менялись только `air_phase.glsl` и `air_phase_cpu.gd` (перенос теплосодержания, TW-3; к жизненному циклу RD не относится). В `scripts/game/game.gd` добавлена буксировка (`tow_session`, `_choose_tow_start`), порядок стадий загрузки и ветра тот же. Коммитов с правкой этого пути между v1.5.19 и main нет.

## Воспроизведение
- Сценарий: `tools/research/crash-reports/cr-2/run.sh --cycles=5` (окно, GPU; меню → «Лететь» → 20 с полёта → меню, пять раз подряд в одном процессе, место askarovo, ветер 18 км/ч). Нужен дисплей и сеть для первой загрузки места (в тестовой копии ~2 мин).
- Результат на Linux, RTX 4070 SUPER, Vulkan 1.3.277, код копии (main): **не воспроизвелось** — пять загрузок подряд без обрыва, без ошибок RD (только посторонние `NO GRAB` и одно `height_at` на пустой Callable в первой загрузке меню-мира).
- Ограничение прогона: загрузки 2–5 шли **без расчёта поля** (8–11 с, стадии `wind` не было — те же условия, поле из атмосферы/кеша), т. е. путь «повторная загрузка с новым расчётом на GPU» не проверен. Для следующего шага: менять ветер/час между циклами (параметр `--wind` фиксирован — добавить смену), включить `DP_AIR_CHUNK_LOG`, слой валидации (`tools/gpu_validate.sh --check=core`); D3D12/Blackwell/Windows недоступны.
- Для пилота: достаточный признак — воспроизводится ли при 2-й загрузке с другим ветром и сразу после неё в диспетчере видно «не отвечает» (зависание) или процесс исчезает (падение).

## Предложение правки
1. Диагностика (первой): в `AirRuntime.setup/load_field` и перед первым `submit` повторной загрузки писать строки `printerr` (сброс на диск): «load_field: пересчёт, RD буферов=N», «порция k: вес/мс» — чтобы следующий отчёт показал, умирает ли процесс до первой порции GPU.
2. Жизненный цикл RD (файлы `air_runtime.gd: stop/setup/RuntimeGpu.release`, `air_clipmap.gd: release`): при смене места явно освобождать клипмап (`_clip.release()`) до `RuntimeGpu.release()`; освобождать буферы задачи по метке `mark()/free_from()` вместо общего сброса всего после `_base`; на повторной загрузке — синхронизировать RD (`rd.sync()`) перед `release`.
3. Тест на воспроизведение: GPU-тест (`tools/gpu_tests.sh`), N раз подряд `AirRuntime.setup` на разных местах/ветрах с `load_field` + проверка `rd` без ошибок под слоем валидации (GPU-AV на ядрах ветра работает); расширить `repro.gd` сменой ветра.
4. Риск: правка общего RD затрагивает окна клипмапа в полёте (дрейф кадра); проверять замером порций и `test_air_runtime_gpu`. Отдельно — сверить с CR-4 (смена драйвера на D3D12 на Windows не снимает причину, если она в жизненном цикле RD, но может изменить проявление).
