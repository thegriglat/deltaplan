# CR-11: причина потери устройства GPU в отчёте

## Отчёты
Только признаки (данные пилотов в репозиторий не входят; сводка по issues — `gh issue view <n> -R thegriglat/deltaplan-reports`).

| Issues | Версия | GPU | API | Стадия | Признак |
|---|---|---|---|---|---|
| #4–#10 (7) | 1.5.18 (cd1a8b) | GTX 1050 Ti | d3d12 (откат с Vulkan, CR-4) | wind | `Can't create buffer … error 0x887a0005` 83–89 раз, затем `Reset failed 0x80070057` / `Close failed 0x80004005` (11–40 раз), каскад пустых RID |
| #17 | 1.5.21 (2d6e5b) | RX 5600 XT | vulkan | меню | ошибок движка в хвосте нет; потери устройства не видно |
| #18 | 1.5.21 (2d6e5b) | RX 5600 XT | d3d12 | flight, 84,5 с от запуска, ветер `off` | `error 0x887a0005` 114 раз и каскад пустых RID; `Reset/Close failed` нет |

Общее: во всех D3D12-отчётах единственный код — `0x887a0005` (`DXGI_ERROR_DEVICE_REMOVED`) из `buffer_create`; момента самой потери в хвосте нет (хвост — конец журнала после сотен повторов; начало каскада обрезано/свёрнуто). В #18 GPU-ветер выключен, значит потеря устройства не только от ядер ветра. Игра после потери продолжала работать и сыпать ошибки (отчёт создан при следующем запуске) — процесс жив, причину можно было спросить у устройства.

## Механизм отчёта
`scripts/core/crash_report.gd` (после CR-7): `build_body` (`:91-132`) кладёт в issue сведения о системе (`system_info`, `:217`: `gpu_api`, `renderer` — драйвер рендера и метод) и хвост журнала прошлого запуска (`read_previous_log`, `:46`; `trim_log` до 60 000 знаков, `fold_repeats` сворачивает подряд идущие одинаковые ошибки). Причины потери устройства в отчёте нет нигде: берётся только то, что движок сам напечатал. Стадия/подстадия и «признак жизни» (`liveness_lines`, `:138`) показывают, где оборвалось, но не почему. Строки стадий пишутся через `printerr`, чтобы журнал сбрасывался на диск (`stage_line`, `:263`).

## Причина
Что мешает получить причину сейчас (по исходникам `4.7.2-stable`, подтверждено чтением кода; на Windows не запускалось):

1. **D3D12: причина не запрашивается.** `GetDeviceRemovedReason` и DRED в `drivers/d3d12` не вызываются (0 вхождений; в `master` тоже 0). Метка `command_insert_breadcrumb` — `// TODO: Implement via DRED` (`rendering_device_driver_d3d12.cpp:5662-5664`). `ExecuteCommandLists` возвращает `void` (`:2487`), сбой `Present` — только `print_verbose` (`:2508`, в релизе не видно), `fence_wait` смотрит лишь `WAIT_FAILED` (`:2398-2406`). Первый видимый след — ошибка следующего вызова, который вернул `DXGI_ERROR_DEVICE_REMOVED` (`buffer_create`, `:941`). Поэтому `0x887a0005` — это «устройство уже удалено», а не причина: на удалённом устройстве все вызовы отдают этот код независимо от того, был ли это TDR, сбой драйвера или GPU page fault (так описано в документации Microsoft; практически не проверялось). Последующие `0x80070057` / `0x80004005` у `Reset`/`Close` — следствия.
2. **D3D12: флаги не помогают.** `--gpu-validation` включает слой отладки D3D12 (`rendering_context_driver_d3d12.cpp:124-139,213`); он не даёт причины удаления, требует установленной у пилота функции Windows «Graphics Tools», а при её отсутствии `D3D12GetDebugInterface` не получается, `_initialize_debug_layers` возвращает ошибку и инициализация D3D12 проваливается (откат на Vulkan, CR-4). `--gpu-abort` доступен только в debug-шаблонах (справка `main.cpp:658`). Ключей проекта `rendering/rendering_device/d3d12/*`, включающих DRED или причину, нет (есть только `agility_sdk_version`).
3. **Vulkan: отчёт есть, но узко.** Расширение `VK_EXT_device_fault` запрашивается как необязательное (`rendering_device_driver_vulkan.cpp:603`). При `VK_ERROR_DEVICE_LOST` от `vkQueueSubmit` (`:3266-3269`) движок вызывает `print_lost_device_info` → `on_device_lost` (`:6928`), печатает «** Report from VK_EXT_device_fault **» (описание, vendor infos, адреса), затем `CRASH_NOW_MSG("Vulkan device was lost … (TDR)")` — процесс аварийно завершается. Кроме `vkQueueSubmit` потеря не разбирается: `fence_wait` (`:3052-3057`), `vkAcquireNextImageKHR` (`:4026-4038`), `vkQueuePresentKHR` (`:3319`) дают общую ошибку `VkResult error %d` без отчёта. Если драйвер расширение не поддерживает, печатается «VK_EXT_device_fault not available.» — причины нет. Брэдкрамбы («Last known breadcrumb») — только в debug/dev-шаблонах и точнее с `--accurate-breadcrumbs` (`:7005-7010`, `main.cpp:663`); в релизном экспорте их нет. На Linux NVIDIA 550 (RTX 4070 SUPER) `VK_EXT_device_fault` в `vulkaninfo` нет — у NVIDIA-пилотов, вероятно, тоже (для их драйверов не проверено); у AMD (RADV/Windows-драйвер) — вопрос к проверке на машине пилота.
4. **Связь с группой B.** В отчётах группы B (Vulkan, CR-4) нет ни «Vulkan device was lost», ни «FATAL» — то есть путь `vkQueueSubmit → DEVICE_LOST → CRASH_NOW_MSG` у них не срабатывал либо обрыв другой природы. Это согласуется с выводами CR-2/CR-4 и является уверенным отрицательным признаком только для этого пути (`вероятно`, потому что журнал мог не дойти до диска).

**Ответы на вопросы карточки.** (1) Сам движок на D3D12 причину не пишет; на Vulkan — частично, см. п. 3. (2) `RenderingDevice.get_driver_resource(DRIVER_RESOURCE_LOGICAL_DEVICE)` возвращает нативный указатель: на D3D12 — `ID3D12Device*` (`:5737-5739`), на Vulkan — `VkDevice`; проба на Vulkan: ненулевой дескриптор устройства, физического устройства и очереди (`results.json`). Из GDScript вызвать COM-метод нельзя — нужен GDExtension (C++/Rust). Расширение уровня `INITIALIZATION_LEVEL_SERVERS` загружается до создания окна и устройства (`main.cpp:3226-3227` против `DisplayServer::create` на `:3368`), поэтому оно успевает включить DRED до `D3D12CreateDevice` (по документации Microsoft: `ID3D12DeviceRemovedExtendedDataSettings` через `D3D12GetDebugInterface`; не проверено). (3) Внешние средства — в «Предложении». (4) Различение по коду — таблица ниже.

**Различение по коду** (`GetDeviceRemovedReason`, коды DXGI; по документации Microsoft, не проверено на железе):

| Код | Имя | Что говорит |
|---|---|---|
| 0x887a0005 | `DXGI_ERROR_DEVICE_REMOVED` | в логе игры — лишь состояние; в `GetDeviceRemovedReason` — устройство физически/логически удалено (обновление драйвера, отключение, сбой) |
| 0x887a0006 | `DXGI_ERROR_DEVICE_HUNG` | зависание GPU: команды слишком долго не завершались (типично TDR после `TdrDelay`, по умолчанию 2 с) |
| 0x887a0007 | `DXGI_ERROR_DEVICE_RESET` | устройство сброшено из-за ошибки выполнения команд |
| 0x887a0020 | `DXGI_ERROR_DRIVER_INTERNAL_ERROR` | внутренняя ошибка драйвера |
| 0x887a0001 | `DXGI_ERROR_INVALID_CALL` | неверный вызов приложения; не про железо |

Отличить TDR от сбоя драйвера по одному `0x887a0005` нельзя; TDR виден как `DEVICE_HUNG` (иногда `DEVICE_RESET`) в причине, а также как событие Windows «Display» 4101 («драйвер перестал отвечать и был восстановлен») в системном журнале. Адрес page fault и последняя операция — только через DRED.

Степень уверенности: п. 1–3 — `подтверждено` чтением кода 4.7.2 (на Windows и на Vulkan-потере не запускалось); поведение Windows/драйверов — `вероятно` (по документации, без проверки).

## Исправлено ли в main
`нет`. В `scripts/` нет ни обработки потери устройства, ни запроса причины (`grep` по `DEVICE_REMOVED`, `0x887a`, `gpu_loss` — пусто; `GpuLossLogger` из CR-К2 v2 — задача CR-8). Движок: в `master` Godot на 2026-10-23 `GetDeviceRemovedReason` в D3D12-драйвере тоже нет, DRED — `TODO`.

## Воспроизведение
Windows/D3D12 недоступны на Linux (RTX 4070 SUPER, Vulkan); потерю устройства принудительно не вызывали (риск зависания единственной GPU машины, на ней идут чужие замеры). Что сделано:
1. `tools/research/crash-reports/cr-11/test_classify.gd` — классификатор строк журнала, 13 проверок, 0 ошибок (образцы — строки ошибок из #4–#10, #18 и исходников 4.7.2).
2. `probe_driver_resource.gd` на Vulkan: `get_driver_resource` отдаёт ненулевые дескрипторы логического/физического устройства и очереди; класс `Logger` есть (`_log_error`, `_log_message`) — основа для CR-К2 v2. Команды — в README каталога.
3. Не проверено: сам вызов `GetDeviceRemovedReason`/DRED (нужна Windows), отчёт `VK_EXT_device_fault` (на этой NVIDIA расширения нет). Проверить можно на Windows-машине (по просьбе — у пилота) искусственным TDR: бесконечный цикл в compute-шейдере длиннее `TdrDelay`; делать только на тестовой машине.

## Предложение правки
Варианты (без пересборки движка), по возрастанию цены:

| № | Вариант | Что даёт | Цена | Риск |
|---|---|---|---|---|
| 1 | Классификатор журнала (`GpuLossLogger` по CR-К2 v2, прототип `device_loss_classifier.gd`) + одна строка `[gpu-loss] api=… code=… name=… reason=unknown` в журнал при первом срабатывании (через `printerr`) | Факт потери, API, имя кода, и главное — строка не обрезается в хвосте, где каскад ошибок вытесняет начало | малая, GDScript; три ОС одинаково | не даёт причину (честно пишет «не получена»); `Logger` вызывается из любых потоков — только под `Mutex` |
| 2 | Опрос событий Windows при следующем запуске после потери (`OS.execute("powershell", …)`: журнал System, провайдер `Display`, id 4101, окно времени вокруг обрыва; в отчёт — только провайдер, id, время, имя драйвера) — **по согласию пилота** | Отличает TDR (4101) от не-TDR; без нативного кода, Windows-only | средняя: ~1–2 с, зависит от локали/прав/антивируса; текст события локализован — брать id, не текст | не менять систему пилота; нет события ≠ нет TDR (drivers пишут свои id); приватность — только поля выше |
| 3 | GDExtension (Windows x64, C++/godot-cpp или Rust) уровня `SERVERS`: до `D3D12CreateDevice` включает DRED (авто-брэдкрамбы, page fault), после потери берёт `get_driver_resource(LOGICAL_DEVICE)` → `GetDeviceRemovedReason` + DRED-выгрузку и печатает 1–3 строки | Точная причина (`HUNG/RESET/DRIVER_INTERNAL_ERROR`) и, при DRED, последняя операция и адрес page fault | высокая: кросс-сборка DLL в `tools/build.sh`, в Linux/macOS D3D12 нет — нужен `.gdextension` только с Windows (поведение на других ОС без библиотеки не проверено); совместимость с 4.7.x; подпись DLL | ложные срабатывания антивируса на неподписанной DLL; DRED замедляет кадр (оценка Microsoft — малая; не измерено); включать лучше по флагу после прошлой потери (метка уже есть), а не всем |
| 4 | Отчёт Vulkan: ничего менять; при потере в `vkQueueSubmit` движок сам печатает отчёт, если драйвер поддерживает; в классификаторе ловить «Report from VK_EXT_device_fault» и «device was lost» | Причина Vulkan там, где драйвер её отдаёт | нулевая (входит в 1) | потери вне `vkQueueSubmit` не разбираются; NVIDIA — вероятно, расширения нет |
| 5 | Диагностика по просьбе: пилот смотрит Event Viewer (System → Display 4101), `TdrDelay` (`HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers`) | Руками подтверждает/опровергает TDR | ручная | **автоматически системные настройки не менять**; правка реестра только пилотом, осознанно |
| 6 | Правка движка (`GetDeviceRemovedReason` в `Present`/после `ExecuteCommandLists` + DRED) / задача в апстрим | Правильное решение везде | пересборка шаблонов — вне условий задачи | апстрим: в `master` 2026-10-23 не сделано |

**Рекомендация.** Сразу — вариант 1 (+4 как часть того же логгера): входит в CR-8, не требует нативного кода и закрывает ближайшую проблему «в отчёте нет даже факта потери и строка теряется в хвосте». Следом — вариант 2 как опция по согласию пилота: он дешевле расширения и отличает TDR. Вариант 3 — только если после 1+2 причина останется неясной; сначала проверка на Windows-машине с искусственным TDR. Варианты 5 и 6 — по ситуации. Флаги `--gpu-validation`/`--gpu-abort` для пилотов не рекомендуются (п. 2 «Причины»).

**Тест на воспроизведение.** `test_classify.gd` (строки #4–#10, #18 → «потеря D3D12, причина не получена», ложных срабатываний нет). Для CR-К2 v2: тест `Logger`, которому подаётся строка `error 0x887a0005` → `GpuHealth.is_failed()`; на Windows — искусственный TDR (см. «Воспроизведение», п. 3) и проверка строки `[gpu-loss]` в хвосте после каскада из сотен ошибок.

**Риски и границы.** Корректность кодов DXGI/DRED/TDR взята из документации Microsoft и не проверялась на железе; возможность включить DRED из расширения до создания устройства — по порядку инициализации в `main.cpp` (прочитано), на практике не проверялось; у D3D12 с Agility SDK интерфейс настроек берётся из фабрики устройства (`device_factory`), без неё — глобально (`rendering_context_driver_d3d12.cpp:120-139`); как будет при бинарниках, собранных иначе, — не проверялось. Группы пилотов малы (GTX 1050 Ti и RX 5600 XT — по одной машине).
