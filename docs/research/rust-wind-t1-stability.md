# RW-6z: открытый T1 — неустойчивость задачи или ошибка переноса

## Постановка

T1 (RW-6q/6x) сверяет поле крейта (`Formula`) с запечённым полем GPU и в пяти полях видит 5–314× допуска W8. Гипотеза: это не ошибка переноса, а неустойчивость задачи — слабый ветер (U10 < 2,5 м/с, Fr < 0,3: 21–79 % несходимости Пикара на GPU, блуждание 0,2–0,55 м/с, [order-and-picard §5.2–5.3](air_phase/order-and-picard.md)). Опыт меряет, насколько сдвигается поле **крейта** при (1) порядке float-сложения (`CHUNK` в `det_sum`, `rust/picard_rs/src/util.rs`, 4096→1000), (2) возмущении входа на 1e-6 (U10·(1+1e-6); дополнительно T + 1e-6·(T+273,15)), и сопоставляет с расхождением крейта и эталона. Только опыт: ничего не чинилось, допуски и `t1_open_*` не менялись. Допуск — как в T1: `1e-3·u0` + полкванта f16 (θ′: 0,05 К + полкванта), по файлу эталона.

Правило вердикта (карточка): R = max по уровням и каналам x_tol [chunk1000 и pert_u10 против base, клетки Пикара] / max x_tol [base против GPU, клетки Пикара]. R ≥ 0,1 — instability; R < 0,01 — port_error; между — mixed. Если base против GPU на клетках механизмов > 1× — ошибка переноса механизмов независимо от R.

- Все проходы крейта на всех уровнях — `Converged` (10–160 итераций, div_rms ≤ 3e-7), область landing_hill и thermal_plain заморожена целиком (0 итераций, статус прохода `Converged м0/т0`). Клеток nonconv у крейта нет ни в одном поле.
- U10 крейта (`PhaseStats.u10`) совпадает с `u10` в метаданных файла эталона (4,497; 2,00; 1,83; 1,91; 8,50; 0,30). Fr — `PhaseStats.fr` = U_a / (N·relief) (relief ≥ 1 м), N = `n_bv` — среднее по столбцам, считается в `phase/prepare.rs` (формула не перепроверялась по §4.1 вручную); у plateau_landing и thermal_slope N = 0 (нейтральная/неустойчивая свободная атмосфера), Fr = 1000 — «не определён», критерий Fr к ним неприменим.
- **CHUNK 4096→1000: поля побитно равны** (max |Δ| = 0 по всем каналам и уровням), хотя невязки при этом отличаются в 16-м знаке. `det_sum` входит только в нормы невязок и критерий останова; число итераций не изменилось, значит порядок сложения поле не меняет.
- **Возмущение 1e-6 по U10**: max |Δu| ≤ 6e-5 м/с; ≤ 6,5e-3 допуска. Усиление 3–34 раза — задача на этих входах слабо чувствительна. Чтобы линейно дать thermal_slope расхождение 1,45 м/с, входу нужно сместиться на ~4 % (оценка линейной экстраполяцией; нелинейность не проверялась). По T + 1e-6·(T+273,15): ≤ 0,87 допуска на plateau_landing (Δu 3e-3 м/с, окно 100 м), 0,07 на thermal_slope — это чувствительность к нагреву, на R не влияет (в правило входят только chunk и pert_u10).
- Контроль lee_bowl: сдвиги 0 / ≤ 2e-3 допуска, расхождение с эталоном 0,6× — как ожидалось.

### Разбор по клеткам

Классы клеток уровня: *mech* — колонны области, замороженные механизмом (маска `freeze`, для `w_mech` — `freeze_mech`); клетки окон 50/100 м отнесены по колонне области (окна сами замороженных колонн не имеют — решаются целиком), *picard* — остальные. *conv_both* — picard-клетки уровня, где решения крейта `Converged` (GPU неизвестен), *nonconv* — иначе (пусто).

- **ridge_west, plateau_landing**: расхождение целиком на клетках Пикара, крейт сходится и неподвижен. Над допуском клетки класса F (42 клетки области 400 м у ridge_west; 20 920 у plateau_landing, + 31 класса A).
- **thermal_slope**: на Пикаре 311× (u0 3,5 м/с; max |Δ(u,v)| 0,42·u0 в области, но 96–99 % клеток в пределах 10 % / 20 % местной |U|: dx100 — 95,1 / 98,7 %, dx400 — 96,2 / 98,4 %); на механизмах 12–28×. Сверх допуска — класс F (351 872 клетки dx50, 168 794 dx100, 41 706 dx400) и A (150 217 dx400).
- **thermal_plain** (область 400 м, 9,8×) и **landing_hill**: область заморожена целиком — это сравнение механизмов с GPU. В thermal_plain сверх допуска колонны D (1 838) и F (985); landing_hill — F (320 477 из 331 776 колонн). Крейт не меняется ни при каком возмущении (сдвиг 0).
- ridge_west dx400: v 1,3×, остальные ≤ 1,0×.

## Вывод

1. **Неустойчивости самого крейта нет**: порядок сложения не меняет поле, возмущение 1e-6 даёт сдвиг на 3–4 порядка меньше расхождения с эталоном (R ≤ 2,6e-3). Объяснить 5–314× чувствительностью крейта нельзя.
2. Формальный вердикт всех полей — `port_error` (R < 0,01 или механизмы > 1×). Но это значит только «не неустойчивость крейта». Опыт **не различает** ошибку переноса и блуждание/несходимость эталона GPU: в запечённых файлах нет статуса решателя GPU (поля `iters`/`stop` не пишутся; `u10` и `inflow_k` есть), а блуждание GPU при U10 < 2,5 м/с (поля с 1,8–2,0 м/с: plateau_landing, thermal_slope, thermal_plain) документировано. На клетках Пикара у thermal_slope, plateau_landing остаётся открытым: либо эталон блуждал, либо порт отличается.
3. На **механизмах** (заморожено) блуждания нет по построению, а расхождение есть (thermal_plain 9,8×, thermal_slope 27,8×, landing_hill 548×) — это ошибка переноса механизмов/фаз либо эталон считался с другими фазами (RW-6u), независимо от Пикара.
4. Крейт ни в одном поле не даёт nonconv-клеток: даже при U10 1,8–2,0 м/с он сходится за 10–160 итераций. Значит, оценка «размаха блуждания» по вариантам крейта бесполезна (~1e-5 м/с); размах нужно брать из эталона.

## Предложение критерия для слабого ветра (W8 v2; контракт меняет координатор)

По решению пользователя 2026-10-29 02:03: классы клеток.
- **mech** (заморожено) и **conv_both** (Пикар сошёлся у обоих): жёсткий допуск как сейчас (`1e-3·u0` + полкванта f16). Классификация по статусу крейта (есть в `Formula`-отчёте: `PassReport.stop`, `WinReport.stop`, теперь и `div_rms`) и статусу GPU (нужен — см. ниже).
- **nonconv**: допуск по горизонтальной скорости как доля местной |U| эталона (с полом 0,1 м/с) для ≥ 98 % клеток при 20 % и ≥ 95 % при 10 %. Опора на числа опыта (thermal_slope, Пикар, как верхняя оценка): 95,1–96,2 % в 10 %, 98,4–98,7 % в 20 % местной |U|; в остальных полях Пикара — 100 %. Для несошедшегося эталона по литературе: блуждание 0,2–0,55 м/с (10–20 % U10), поэтому и 10–20 %.
- Чего опыт не даёт: размаха блуждания (огибающей) — крейт не блуждает; nonconv у крейта пусто. Для этого нужны два прогона GPU (разные порядок/старт) или логи итераций поздних снимков, и **статус GPU в запечённых файлах** (добавить в `bake_air.gd`/`air_baked_field.gd` запись `stop`, `iters`, `div_rms` по уровню — после этого класс conv_both/nonconv строится по обоим).

## Ограничения

- Статус GPU — «нет данных» (как получить: запись `stop/iters/div_rms` в `tools/terrain/bake_air.gd` и перепекание; восстановление запуском Godot оценено в >1 ч и не делалось).
- Возмущение 1e-6 линейное и малое; крупные возмущения (1e-3, 1e-2) и другие стартовые поля (тёплый/холодный старт Пикара) не пробовались. Многопоточность не варьировалась (T8 побитный).
- Отнесение клеток окон 50/100 м к mech по колонне области условно (окна решаются без заморозки).
- Fr для N = 0 не определён (1000); критерий Fr < 0,3 проверялся только на landing_hill (0,05) и thermal_plain (0,38).
- «Последние итерации» (размах по снимкам) не снимались.
