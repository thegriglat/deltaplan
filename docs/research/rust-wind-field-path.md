# Путь поля Пикара: что переносить в RW-6 и в каком порядке (RW-6a)

Разбор по чтению кода `feature/rust-wind` (2026-10-26); GPU и Godot не запускались. Время на CPU — **расчёт** по замерам `picard_rs`, не замер. Полные таблицы (17 шагов с ключами конфига, 16 карточек задач) — `tools/research/rust_wind/field-path-tables.md`. «GD» — GDScript игры; `am/` — `scripts/atmosphere/air_model/`.

## Выводы и рекомендации

1. **В `picard_rs` нет сборщика случая.** Крейт читает готовые массивы R1 (`cell, tu, tv, tw, nu_bg, Q, gam, cplz, sp_*, ubg, vbg, lam, Kx/Ky/Kz, fixed_*, b_*`); игра строит их на GPU ядром `air_picard.glsl:K_SETUP` (~100 строк) из плоскостей `AirCase.prepare()` (`am/air_case.gd:289`, ~220 строк; `col, lev, prm`). Оба переносятся в RW-6 (RW-6d, RW-6e); в плане и `rust-air-integration.md` этого пункта нет.
2. **`adv2` не переносить:** в коде игры его нет (`grep adv2` по `scripts/`, `configs/` — пусто), в `README` крейта он «выключен в эталоне». Пункт в `rust-air-integration.md` устарел.
3. **Фазы и заморозку колонн отложить без расхождения T1 нельзя** для слабого ветра (штиль, жара, вечер: область заморожена целиком). **Рекомендация:** в RW-6 переносить фазы полностью (RW-6k–6m, ≈ 1750 строк GD; построчный CPU-двойник `am/air_phase_cpu.gd` — готовая спецификация), но после Пикара без фаз; T1 сильного ветра закрывается раньше, слабого — после фаз.
4. **Вход `domain_case`:** игра передаёт шесть условий напрямую (час, ветер меню, направление, `t_max`, небо, режим притока); остальное `domain_case` выводит сам. **Рекомендация:** перенести в RW-6 подмножество «погода и солнце для поля» (≈ 600 строк GD, RW-6c, модуль `dp-air::field::weather_core`); RW-12 раньше не поднимать — `derive`, `AtmoDay`, `_cache_coefficients` полю не нужны. **Пробел W5:** нет флага режима притока `"start" | "inflow"` (`StartWeather.wind_ref_of`; `wind_ref` в W5 — другое) — нужен W5 v2.
5. **Окна 100/50 м** (вопрос 4): 0,56× и 0,99× области по ячейкам; сдвиг при 10 м/с — 50 м раз в ~80 с; пара mech + heat на 8 потоках 2,7–4,7 с (50 м), 1,3–2,3 с (100 м), на 2 потоках 8–14 с и 4–7 с. **Рекомендация: переносить последним хвостом RW-6 (RW-6n, 6o) с выключателем `window_levels_m = []`**, T1 поля сначала на уровне области. Причина: без окон разгон у склонов занижен на 5–25 % — меняет полёт, а физику без решения не меняем; стоимость ограничена (~2–3 дня); `nest` и сдвиг пишутся как общая операция «грубый → мелкий» (первый шаг иерархии `air-cascade`).
6. **Грубый старт 1200 → 400 м** — общая операция `prolong` (`K_PROLONG`, ~30 строк), RW-6f, тест T4a.
7. **Загрузка на CPU — главный продуктовый риск**, которого нет в `rust-air-integration.md`: там время одного решения (6,2 с на 8 потоках), а игра решает пару (mech + heat), окна и два прохода подбора притока `k`. Оценка 20–30 с (8 потоков), 70–100 с (2 потока) без запечённого поля (раздел «Окна»).
8. **T1 поля без GPU:** восемь запечённых GPU-полей островов (`data/locations/{training_island,volcano_island}/air/`, три уровня, ветер 6–8,5 м/с, `inflow`) — готовый эталон сильного ветра (f16). Слабый ветер требует фикстур RW-1 с настоящим GPU, а генератор по W8 — headless, где поле не считается (`am/air_runtime.gd:unavailable_reason`).

## Путь поля по шагам

Цепочка: `Game._load_air_field` → `AirRuntime.setup/load_field` → `_begin` → `_prep_task` (вход области и грубой сетки, параллельно) → `PreparedCase` (`prepare` обоих решений) → фазы → грубый Пикар → Пикар (mech, затем heat) → `WindField.from_mac` → окна → `_levels_done` (проход 2) → `_apply` → `Atmosphere.set_air_field` → `AirFieldSet.sample`. Подробно (файл:функция, вход/выход, поток, ключи):

- **Загрузка** (`air_runtime.gd:load_field` 378): сначала запечённое поле (`_load_baked` 493, `baked_enabled = true`) и кеш диска (`_load_cached` 633); иначе `_begin` (935): 1 или 2 прохода (`max_passes = 2`; «inflow» или штиль — один, `k = 1`), `k` из памяти по румбу.
- **Вход** (`_prep_task` 1015, рабочий поток, области 1200 и 400 м параллельно, ~0,5 с на 400 м; `am/air_place.gd:domain_case` 33): рельеф `block_mean` 25 → 400 м, `gam`, `z_i`, `z_i_col` (`zi_terrain_alpha = 0.33`, `zi_terrain_smooth_m = 5000`), `z0_map`, `heat`, профиль притока. `DX = 400`, `DOMAIN_L = 38400`.
- **Плоскости** (`PreparedCase.from_case` 1758 → `air_case.gd:prepare` 289; ~0,7 с пара): `col` 14 плоскостей, `lev` 5, `prm`.
- **Фазы** (`am/air_phase_job.gd` + `air_phase.glsl`, GPU порциями `chunk_ms = 8`; иначе CPU `air_phase_cpu.gd`): `weights`, `omega`, `freeze`, `freeze_mech`, `warm`, `mech_field`, `mech_field_mech`. `omega.use_map = false`, `nonconv.mech_w = 0.5`, `nonconv.late_from = 500`, `omega.fallback_iters/omega = 300 / 0.5`.
- **Грубый Пикар** (`_after_phases` 1116, `_poll_coarse` 1139, `coarse_start` 1177; `picard_start = "coarse"`, `picard_coarse_factor = 3`): пара mech → heat на 1200 м (32×32), состояния в `warm_coarse`; пропускается при прошлом поле или `all_mech`; ошибка — старт с фона.
- **Пикар 400 м** (`_start_picard` 1267, `am/air_picard_job.gd`): `tol 2e-5 / 5e-7 / 1e-6`, `check_every = 10`, `max_outer = 3000`, `timeout_s = 60`; GPU порциями (`poll_slice 40 мс` при загрузке, 5 мс в полёте). `_prolong` (389) переносит грубое решение: билинейно по горизонтали в индексах грубой сетки со смещением начала, по высоте тот же `dz`, сдвиг уровней `ksh = (z_bot − z_bot_грубой)/dz`.
- **Сборка** (`field_async` 1188, `_build_field` 1215 → `wind_field.gd:from_mac` 170): поле без ореола в центрах, `w_conv = w − w_mech`, клэмп 40 / 10 м/с; чтение буферов — главный поток, сборка — рабочий.
- **Окна** (`_start_windows` 1388 → `am/air_clipmap.gd`, `air_window_*.gd`, `air_window.glsl`): `window_levels_m = [100, 50]`, `window_shift_frac = 0.25`.
- **Проход 2** (`_levels_done` 1472, `start_speed` 1579, `_next_k` 1557, `inflow_p` 1529): U на 10 м над стартом → `k₁ = k₀·(u10/U)^(1/p)`, p по таблице [[3; 0,57], [6; 0,75], [10; 0,90]], `k ∈ [0,3; 1]`, `pass_tol = 0.03`.
- **Подача и опрос** (`_apply` 1600 → `Atmosphere.set_air_field` `atmosphere.gd:533` → `AirFieldSet.set_field`; `air_velocity_at` 763): `blend_s = 60`, `edge_blend_cells = 5`.
- **Пересчёт** (`_process` 878, `needs_recompute` 825): `recompute_game_min = 15`, допуски 0,05 м/с, 1°, 0,25 °C; **сдвиг окон** (`_update_windows` 1437) — только в покое.

Решение ведётся из `_process` главного потока порциями GPU. В крейте оно станет одной фоновой задачей (свой `rayon`-пул, `INTEGRATION.md`, «Нити»); стадии конечного автомата остаются только как `Status.progress`.

`conditions_of` (339) даёт ровно эти шесть. **Выводится внутри `domain_case`** (в крейт): `WeatherModel.config/reference_context/ground_context` (колбэк `detail.sample` заменяется растром W5), `diurnal_state` (температура, `cap`, `heat`), `diurnal_range_k`, `sky_params`, `monthly`, `typical_max_c`; профиль θ̄ и `z_i` (поиск по 23 000 шагам); `AirZiTerrain`; `cell_surface/cell_z0`; `WindProfile.apply_to_case` (α, класс устойчивости, `z_sat`, `max_profile`); `SurfaceHeating`, `SunClock.solar_position`, `SurfaceHeat.mix_flux`, температура воды.

Не нужно полю (остаётся RW-12): `WeatherModel.derive` (~160 строк), `td_day`, `haze_k_rh`, `AtmoDay`, `_cache_coefficients`.

**Рекомендация:** подмножество в `weather_core` внутри RW-6 (RW-6c, 1 день) — те же конфиги, колбэков нет, W3 цел, RW-12 потом достраивает, а не переписывает. «Поднять RW-12 раньше» дороже (~700 лишних строк) и блокирует RW-6; «игра передаёт готовые `z_i`, `gam`, `heat`» противоречит решению пользователя «всё тяжёлое считает Rust».

Следствие: при Rust-поле `unavailable_reason()` («headless», «нет GPU») теряет смысл — CPU есть всегда, поле начнёт считаться и в headless-тестах (сейчас там аналитика). Что делает `air.backend = rust` в headless, решить в RW-7.

## Карта фаз и заморозка колонн

**В игре включено:** `AirRuntime` всегда считает фазы и передаёт Пикару `freeze_mask(_mech)`, `freeze_field(_mech)`, `nonconv_mask/field`, `late_from = 500`, `omega_fallback = (300; 0,5)`. Не используется только карта ω (`omega.use_map = false`).

Заморозка (`air_picard_job.gd`, `air_picard.glsl`): колонна, отданная механизму (H штиль, сильное D, F свободная конвекция, G вечерний сток; вес ≥ `freeze_w = 0.5`), после каждой итерации переписывается полем механизма (`K_FREEZE`), её невязка в критерии обнуляется (`K_RMASK`), а в шаблонах прогонок её точки — тождество (`K_FIXROW`). Заморожена вся область — итераций нет, поле механизма + `finalize`. У mech и heat маски разные.

**Граница T1.** Штиль 2 м/с в полдень на острове — область заморожена целиком (`docs/guide/air-model/limits.md:86`); при U10 0,3 и 1,5 м/с заморожено всё, при 12 м/с у холма нет (`phases.md`). Доля замороженного для фикстур W8 неизвестна (`frozen_frac` в `last_info`, но фикстуры её не несут). Вывод: в сильном ветре Пикар без фаз даёт поле того же порядка, не то же (D/F/G — механизм); в слабом — принципиально другое. Отложить без расхождения T1 нельзя.

**Что переносить:** (1) `AirPhase.prepare` и классификатор (веса, Σ = 1, маски, ω; `air_phase.classifier.*`) — 6k; (2) механизмы A (линейная теория через DCT-II, 13 высот `agl_levels_m`), B (пузырь срыва), D (слои Лапласа, SOR 400 итераций, ω 1,9), H — 6l; (3) F (баланс θ′), G (Прандтль + D8), тёплая сборка `warm/mech_field(_mech)/nonconv_field` — 6m; (4) заморозка в решателе — 6g; (5) запасные правила — 6h.

**Рекомендация:** сначала Пикар без фаз на сильном ветре, затем фазы и T1 слабого ветра. Переключатель `air.backend` общий (RW-7), поэтому до RW-6m `rust` для слабого ветра заведомо отличается от `gd`; RW-13 не раньше RW-6m. Причина: фазы определяют поле там, где живут термики; отбросить — поменять физику без решения.

## Окна 100/50 м

Два окна 64×64 с шагом 100 и 50 м (стороны 6,4 и 3,2 км), `dz = dx/2`, потолок 2000 м над максимумом рельефа окна. Граница — поле родителя (область → 100 → 50), зона релаксации 4 клетки, поправка потока Σ = 0; старт «родитель + 30 V-циклов», при сдвиге — старое окно + 4 V-цикла.

| Уровень | Сетка | Ячеек с ореолом | К области |
|---|---|---|---|
| область 400 м, Онгудай | 96×96×50 | 499 408 | 1,00 |
| окно 100 м, Онгудай | 64×64×62 | 278 784 | 0,56 |
| окно 50 м, Онгудай | 64×64×112 | 496 584 | 0,99 |
| то же, плоский рельеф (расчёт) | 64×64×~44 / ~84 | ~200 000 / ~375 000 | 0,40 / 0,75 |
| острова (запечённые поля) | 50 м: nz 94–98; 100 м: 48–52; область 96×96×36 | — | — |

Сдвиг — когда пилот ушёл от центра дальше 0,25 стороны (800 м для 50 м, 1,6 км для 100 м). Период (`window_estimate.json`): 10 м/с — 80 и 160 с; 15 м/с — 53 и 107 с; 25 м/с — 32 и 64 с. Сдвиг 100 м пересчитывает и 50 м; круг в термике сдвигов не даёт; сдвиг — только в покое `AirRuntime`.

**Время на CPU (расчёт).** База — `picard_rs` на области, tol 1, мс/итерацию (`out/final/README.md`): heat 50,7 / 62,8 / 115,9 / 155,1, mech 40,2 / 49,3 / 90,5 / 119,8 на 8 / 6 / 3 / 2 потоках. Допущения: время линейно по ячейкам; итерации окон — как у GPU игры (`clipmap.md`: 100 м — 40 + 40 загрузка, 50 + 40 сдвиг; 50 м — 40 + 50 и ~35 + ~65) — верхняя граница, нижняя — ×0,58 (tol 5 / tol 1 на области; для окон не измерено). Подготовка входа, сборка и `setup_s` (0,4–0,9 с) не включены. Пара mech + heat, секунды:

|---|---|---|---|---|
| 100 м, загрузка | 1,2 – 2,0 | 1,5 – 2,5 | 2,7 – 4,6 | 3,6 – 6,1 |
| 100 м, сдвиг | 1,3 – 2,3 | 1,6 – 2,8 | 3,0 – 5,1 | 4,0 – 6,8 |

GPU игры для сравнения: окно 100 м ≤ 1 с, 50 м ≤ 3 с. Нагрузка в полёте при 10 м/с: сдвиг 50 м занимает 3–6 % времени 8 потоков и 10–18 % времени 2 потоков; кадру фон мешать не должен (часть ядер игре), но rayon внутри gdext при работающем кадре **не проверялся**.

**Загрузка целиком (8 потоков, оценка):** область, пара холодная 6,2 + 6,2 = 12,4 с (u3, tol 5; грубый старт ожидаемо ×0,7 по AP-20: 793/1140 итераций); грубая 1200 м — 0,12 от области на итерацию; окна 3,6–6,1 с; проход 2 — область с тёплого старта (~1,5 с) и окна 3,6–6,1 с. Итого ≈ 20–30 с; на 2 потоках ≈ 70–100 с. Сейчас на GPU: 3,3–3,9 с без окон, 5,0–5,5 с с окнами (`runtime.md`, `clipmap.md`). Рычаги: запечённые поля и кеш, выключатель окон, тёплый проход 2.

| Вариант | Последствия для T1 | Последствия для полёта |
|---|---|---|
| A. Перенести (nest-окна на CPU), RW-6n/6o | T1 полный, как фикстуры GD | как сейчас; +4–19 с к загрузке, фон 3–18 % потоков |
| B. Заменить (область 400 м + приземный слой, позже иерархия `air-cascade`) | точки `ground`, `lee`, `thermal` вне допуска 3 % (разница уровней у земли 6–18 %); фикстуры RW-1 с `window_levels_m = []`, W8 v2 | разгон у склонов ниже на 5–25 % (`limits.md`), вариометр у бровки слабее; дешевле |
| C. Отказаться | как B | как B, навсегда |

**Рекомендация: A последним хвостом, отключаемым.** Причины: физика не меняется без решения; стоимость известна; параллелится с фазами; слабые машины выключают; откат на B — выключатель; `nest`/`prolong` — общие операции `air-cascade`.

## Приземный слой `WindField`, опрос, набор уровней (RW-6i)

- `from_mac` (170): центры граней, маска `tcode & 3`, `w_mech` — `w` без нагрева, `w_conv = w − w_mech`, `z0` числом или картой, клэмп 40 / 10.
- `sample` (505), `sample_theta`, `sample_w_conv`: по четырём столбцам линейно по высоте между центрами; **ниже центра первой воздушной клетки** — лог-профиль к нулю на `z0`; билинейно по столбцам; сдвиг `z_c = y + (hc_c − h)·exp(−agl/dx)`; `ground_h` — по растру 25 м (W5; разница с `GroundField` — в допусках W8).
- Столбцы для RW-8/RW-10 (`_build_boundary_layer` 327, `_build_convective` 374): `u*`, `U_out`, `A_out = 600`, `desc`, `w*`, `hmix` (сглаживание потока тепла `HEAT_SMOOTH_M = 1500`), `turb_at` 422. Метаданные термиков: `heat`, `z_i(_col)`, `gam`, `u10`, `z0` — внутренний доступ крейта (`AirThermals.build` читает поле целиком, RW-10).
- `AirFieldSet`: уровни от мелкого к грубому, `edge_weight` smoothstep по 5 клеткам, остаток — следующему уровню, непокрытое — аналитике. Аналитика остаётся в GD до RW-9: крейт отдаёт слагаемое «field» и его долю, фасад дополняет (зафиксировать в W7).
- Подмена `set_field(new, blend_s)`: «старое» — снимок текущей смеси (≤ 3 набора, доли < 1e-3 отбрасываются), доля нового — smoothstep по времени атмосферы. В крейте время — `advance_to(t)`; два опроса на одном `t` равны (T6).

## Пересчёт, подмена, проход 2, запечённые поля

- **Пересчёт**: причина — смена ветра (|Δu10| > 0,05, |Δwdir| > 1°, смена режима притока), погоды (небо, |Δt_max| > 0,25 °C), срок (`slot` 15 мин). Очереди нет: не успевший пересчёт сменяется новым на последний срок. Ошибка или таймаут — прежнее поле. Тёплый старт — оба решения своим состоянием; в Rust `init: State` на каждый `solve`, состояния хранит крейт; нет после смены места, запечённого поля, кеша.
- **Проход 2**: точка старта — первый фокус до загрузки; высота земли по растру; поле прохода 1 не подаётся и служит откатом (`_use_previous_pass`); если проход 1 упёрся в предел итераций (слабый ветер) или `k` не изменился — прохода 2 нет.
- **Запечённое поле** (`am/air_baked_field.gd`, 476 строк) и **кеш** (`scripts/atmosphere/air_field_cache.gd`): формат `dp-air-baked` (f16 + zstd), ключ — место, старт, условия, `model_hash` (хеш кода `air_model/`: любая правка `.gd` его сбрасывает). 8 файлов, 45 МБ. Без них загрузка острова обходится без расчёта. **Рекомендация (RW-6p):** читать формат в крейте (источник T1 и начальное поле), перепечь острова расчётом крейта до RW-13, `model_hash` заменить хешем крейта; `tools/terrain/bake_air.gd` считает GPU-путём, который уйдёт в RW-13.
- Каждое новое поле пересобирает источники термиков на главном потоке (~0,4–0,6 с, `clipmap.md`) — уходит в крейт с RW-10.

## Разбиение RW-6 на задачи

Каждая ≤ 1 дня (6c, 6g, 6i — верхняя граница). Карточки (скоуп, тесты) — в приложении. Зависимости: RW-4, RW-5.

- **6b** вход области: `block_mean`, сетка, `gam`, `z_i`, `AirZiTerrain`, `cell_surface/z0` из растров — тест: дамп GD (`hc` ≤ 1e-3 м, `gam` ≤ 1e-7 К/м).
- **6c** `weather_core`: погода и солнце, `SurfaceHeat`, `surface_flux`, `WindProfile` — тест: `H[ny·nx]` ≤ 1 Вт/м², α и `max_profile` точно.
- **6d** `AirCase.prepare` → `col/lev/prm` (после 6b, 6c).
- **6e** `K_SETUP` → R1 в памяти (`picard_rs::Case`) — тест: Онгудай R1 (`$AIR_CASCADE_DATA`), затем итерации в допуске AP-20.
- **6f** `prolong`, цепочка 1200 → 400 м — тест **T4a**.
- **6g** заморозка в решателе и отмена `solve` (контракт `picard-rs` R6 → v4, меняет координатор) — тест T4, регрессия R6 v3 при пустой маске.
- **6h** ω-откат, `late_mean`, `nonconv`, `max_outer = 3000`.
- **6i** `Field`: `from_mac`, `sample*`, приземный слой, `FieldSet`, подмена — тест: T1 по запечённым полям, T2.
- **6j** оркестровка: конвейер, проходы `k`, срок, тёплые состояния, фон, таймаут, откат, политика потоков — T2, T8.
- **6k–6m** фазы (классификатор; A, B, D, H; F, G и сборка) — числа `test_air_phase.gd`, затем **T1 слабого ветра**.
- **6n, 6o** окна (`nest`, `flux/corr`, `shift`; клипмап) — сверка с `window_gpu_refs.py`.
- **6p** запечённые поля и кеш. **6q** приёмка: T1/T4/T4a/T2, бенч.

**Порядок и параллельность.** Потоки: A (вход) 6b ‖ 6c → 6d → 6e; B (решатель) 6f ‖ 6g → 6h; C (поле) 6i → 6p; D (фазы) 6k → 6l ‖ 6m; E (окна) 6n → 6o — последним. Склейка 6j (после 6e, 6f, 6i), затем 6q. Первый видимый результат (Пикар в Rust, сильный ветер, без фаз и окон): 6b–6f, 6i, 6j ≈ 7 агент-дней, ~3 календарных при трёх потоках. Весь RW-6 — ≈ 13–15 агент-дней (по чтению кода и строкам GD, не замер).

## Тесты

- **T1 поле.** Сильный ветер — восемь запечённых полей (три уровня, f16: допуски по каналам шире `u_rel ≤ 1e-3`); слабый — фикстуры RW-1 (нужен GPU). Допуски W8: слагаемое поля `u_rel ≤ 1e-3`, `th_abs ≤ 0,05 К` после одинакового числа итераций; в точке 0,1 м/с + 3 %. Прогон крейта и при `tol_scale = 1`, и при 5 (GPU игры — tol 1, паритет итераций). Сверка — `dp-stand compare`.
- **T2.** Штиль → поле ≈ 0; нет разрыва на краю уровня и окна (в GD изменение за 50 м в полосе края не больше, чем внутри: `clipmap.md`); `blend_s` монотонна; два опроса на одном `t` равны; пределы 40 и 10 м/с.
- **T4.** `div_rms`, непротекание у земли, невязка (`picard_rs/residual/`); замороженные колонны = поле механизма.
- **T4a.** (1) `prolong` постоянного и линейного полей точен на разнесённой сетке, сдвиг по z и смещение начала учтены; (2) поток массы через грани сохраняется в допуске; (3) mech и heat стартуют каждый своим состоянием; (4) итераций от грубого старта меньше, чем с фона, на случаях AP-20 (1140 → 793 на 6 случаях; ориентир, не паритет); (5) отказ грубого → старт с фона без падения; (6) грубый пропускается при прошлом поле или `all_mech`.
- Воспроизводимость: один вход — одно поле при 2 / 4 / 20 потоках (T8).

## Риски и открытые вопросы

1. **W5 v2:** добавить `inflow_mode: "start" | "inflow"` в условия; без него проходы `k` не воспроизвести.
2. **Загрузка на CPU** (20–30 с / 70–100 с): допустимое время решает координатор/пользователь.
3. **Фикстуры RW-1:** генератор по W8 — headless, где поле не считается; нужен запуск с RenderingDevice под замком GPU или запечённые файлы.
4. **Паритет итераций:** GPU игры — tol 1, крейт — `tol_scale = 5` (решение пользователя 2026-10-24); W8 требует «одинаковое число итераций» — T1 прогонять при обоих.
5. **Объём вырос** с «встраивания Пикара» до: сборщик, фазы, погода, `WindField`, окна, оркестровка. Оценки — по чтению кода.
6. **Смежное:** `AirThermals.build` (RW-10) читает поле целиком — интерфейс внутреннего доступа фиксируется в 6i; `cloud_physics.gd` использует `AirPlace.DOMAIN_L`/`AirRuntime.DX` (RW-11); карта фаз для `wind_field_debug.gd` — W7 `debug_raster`.
7. **Не проверено:** сетка 200 м, Windows/macOS, rayon в gdext при кадре, итерации окон на CPU, время сборщика в Rust, доля замороженного для фикстур.
