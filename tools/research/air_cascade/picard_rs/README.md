# picard_rs — Пикар 400 м на Rust (шаг 0, AC-R1, AC-R3, AC-R4)

Порт одной итерации Пикара AM-01 (`tools/research/air3d/air.py`, ядра CuPy) на Rust:
`f32`, плоские массивы с ореолом в раскладке R1 (вход читается без перестановок), явный
`rayon::ThreadPool`. Подготовка случая (рельеф, K_b, губки, нагрев) **не** портирована — берётся
из фикстуры R1. Код игры и эталон не менялись. Контракты — `docs/contracts/air-cascade.md` (R1, R2, R3 v3).

## Структура

| Модуль | Что |
|---|---|
| `case.rs` | чтение `<случай>.json` + `.bin` (R1); `Consts` — постоянный вход (типы, губки, K_b, Q, проводимости проекции, границы) |
| `kernels.rs` | поточечные ядра: `apply_bc`, `kloc` (местное K), `build_mom` (шаблон импульса), `build_heat` |
| `lines.rs` | зебра-прогонки Томаса по линиям (z, x, y), невязка `resid` |
| `mg.rs` | V-цикл проекции: огрубление по x, y, прогонки по z, самый грубый уровень 20×(z, x, y) |
| `solver.rs` | `Picard` — состояние итерации (`Fields`, шаблоны, рабочие буферы): `outer_step`, `project`, `residuals`, `solve`, `finalize` |
| `blocks.rs` | сверка блоков одной итерации с R1 (как `tests/atmosphere/test_air_picard_gpu.gd`) |
| `report.rs` | результат R2, отклонение от `sol_*` |
| `util.rs` | детерминированные редукции, `Shared`, `fmadd`, `isa_branch` (ветка диспетчера) |

Шаблон — строка `[f32; 8]` (C0…C6, b) на клетку: прогонка читает коэффициенты клетки одним
доступом. Параметры (`dtau_u`, `mom_sweeps`, …) берутся из `params` JSON случая. Пул потоков
создаётся в `main` из `--threads` и вызывается через `pool.install`; глобального состояния нет.
Единственный `unsafe` — `util::Shared`: запись в непересекающиеся линии одного цвета зебры
(соседи вне линии принадлежат другому цвету и в проходе не пишутся).

## CLI и воспроизведение

```
cargo build --release --manifest-path tools/research/air_cascade/picard_rs/Cargo.toml
F=tests/atmosphere/fixtures/air_model/ref
picard blocks $F/flat_wind.json $F/agnesi.json $F/heated_slope.json $F/saddle.json   # таблица и max_block_rel=…
picard solve  $F/saddle.json --threads 8 [--max-iters 2000] [--out out/saddle_release_t8.json]
picard isa                                                        # ветка multiversion на этом процессоре (AC-R4)
picard bench  $F/saddle.json --threads 1,4,8,16 [--iters 20] [--out-dir out]   # --solve: полное решение вместо K итераций
picard solve  <случай> --tol-scale 0.03 --diag    # диагностика: ужесточить критерий, таблица отклонения по полям
python3 contract/check_contract.py --results out && python3 contract/tolerance.py out/*_release_t8.json
```

## Онгудай 400 м: Rust против эталона (AC-R3)

Случаи — `~/data/air_cascade/ongudai/ongudai_d400_{u3_heat,u3_mech,u0_heat,u6_heat}.{json,bin}` (AC-R2, вне git, 38 МБ каждый;
сетка 96×96×50 = 460 800 клеток, 400 м; 381 458 воздушных). Эталон — AM-01 f64 на CuPy (RTX 4070 SUPER), `t_ref_s` в JSON случая.
Машина замера: Xeon E5-2666 v3 (Haswell, 10 ядер / 20 потоков, 2,9 ГГц, макс. 3,5; L3 25 МБ), `rustc` release (fat LTO, без
`target-cpu`, базовый x86-64: SSE2, без AVX2/FMA). Замеры — под замком cpu (вес 18 из 18 слотов, `CPUQuota=1800%`), машина
свободна от других замеров. Воспроизведение:

```
cd <копия>; P=tools/research/air_cascade/picard_rs; D=~/data/air_cascade/ongudai
cargo build --release --manifest-path $P/Cargo.toml
for c in u3_heat u3_mech u0_heat u6_heat; do for t in 6 8 18; do
  .dpcli/dpcli lock cpu <ID> --no-tmux -- $P/target/release/picard solve $D/ongudai_d400_$c.json --threads $t --out $P/out/ongudai_d400_${c}_release_t$t.json
done; done
.dpcli/dpcli lock cpu <ID> --no-tmux -- $P/target/release/picard bench --solve $D/ongudai_d400_u3_heat.json --threads 4 --out-dir $P/out/bench   # также 10, 12, 14, 16, 20
python3 $P/contract/tolerance.py --iters-tol 20 $P/out/ongudai_d400_*_release_t8.json
python3 $P/out/table.py     # таблицы ниже
```

12 основных результатов (R2) — `out/ongudai_d400_<случай>_release_t{6,8,18}.json`; точки 4/16/20 потоков — `out/bench/`.
`host.git` в JSON — `318c88b73` (коммит кода, с которого сняты все результаты, кроме `bench/`, где он тоже `318c88b73`). Время «всего» — от начала подготовки случая в процессе до финала (без чтения `.bin` с диска и запуска процесса);
оно включает подготовку (`setup_s` 0,4–0,9 с: инициализация состояния, шаблоны, V-цикл), итерации и проверки невязок.
Отдельно измеренного времени по фазам нет; «мс/итерацию» — среднее по итерациям без проверок.

### Невязки по итерациям (Rust против `history_ref`)

График — `out/residuals_ongudai_u3.svg` (импульс, θ′, ∇·u; сплошная — Rust, толстый штрих — эталон; рисует `out/residuals.py`, matplotlib в окружении нет — чистый SVG). Строки таблицы — выборка проверок (полный ряд — `history` / `history_ref` в `out/*_t8.json`); ряды совпадают с эталоном f64 на кривой во все проверки (разница ≤ 0,2 %).

Выборка проверок — `out/mv/residuals_table_ac_r3.md` (перенесена из README ради размера).

наибольшее |Rust/эталон − 1| по всем проверкам и величинам обоих случаев: 0.002

Потоки: 6 — слабая машина пилота (Ryzen 5 4500, 6C/12T), 8 — средний ПК, 18 — полная квота этой машины. 6 и 8 потоков на Xeon
с 10 физическими ядрами ≈ 6 и 8 физических ядер (планировщик ОС может класть потоки на HT-сиблинги; закрепления нет), поэтому
эффективность падает после 8–10 потоков: 10 физических ядер дают 87,3 мс, 12–20 потоков — 86 → 82,4 мс (ускорение 4 → 18 потоков 2,26× из 4,5× идеальных). Число потоков в пуле проверено (`pool_threads` и `process_cpu_s` в JSON): CPU-время процесса растёт с потоками (144 → 271 → 289 с), а стена нет — лишние потоки занимаются ожиданием/кражей задач; предел — физические ядра, малые задачи (линии 50–98 клеток) и память. Ранняя серия (до исправления) показывала 82,61 мс на 16/18/20 с разбросом 0,01 % — совпадение; в перемере 83,4 / 82,4 / 83,1. Точка 20 потоков при квоте 18 ядер — «квота 18 ядер».

Критерий: u_rel ≤ 1e-3, th_abs ≤ 0,05 К, итерации ±20 — все четыре случая с запасом ≥ 20× (худший `worst` = u0: 4,3e-2).
Итерации совпадают с эталоном **точно** (191/231/201/131). Точность не зависит от числа потоков (редукции в f64 фиксированными
блоками): таблица «сверка» — одна на все потоки.

### Штиль (u0_heat): был u_rel = 0,018 — ошибка счёта итераций, не схемы

Эталон при записи графа CUDA делает один шаг и считает его в `it`; Rust считал на 1 меньше. Исправлено (`Criterion::pre_steps`): u_rel 4,3e-5. Разбор — `out/mv/stil_ac_r3.md`.

### Сравнение с GPU игры (ориентир, не требование паритета)
GPU игры — `docs/guide/air-model-gpu/picard.md` (RTX 4070 SUPER, та же сетка 98×98×52 с ореолом, f32, после А1): итерация
4,2 мс (GPU-метки), решение 3 м/с с нагревом 130 итераций — GPU 0,58 с, стена 1,1–2 с («кадры»/«загрузка»), пара 400 м — 2,0 с.
Числа итераций игры (130, пара 190) — другие параметры/старт, не итерации фикстуры (191/231); сравнение по-итерационно:

| | мс/итерацию | к GPU игры (4,2 мс) |
|---|---|---|
| GPU игры, f32 | 4,2 | 1× |
| CuPy f64 (эталон, t_ref/итерации, с проверками) | 9,122 с / 191 = 48 | 11× |
| Rust, 18 потоков | 82,4 | 20× |
| Rust, 8 потоков | 102 | 24× |
| Rust, 6 потоков | 139,5 | 33× |

Решение целиком (u3_heat): Rust 16,6 с (18 п.), 20,5 с (8 п.), 28,0 с (6 п.); эталон CuPy f64 9,1 с; GPU игры 0,6 с GPU-время
(стена 1–2 с) на 130 итераций — на 191 итерации ≈ 0,8 с GPU. То есть Rust на CPU медленнее GPU игры в ~10–25× по стене
(20–33× по итерации).

### Оценка для Ryzen 5 4500 (Zen 2, 6C/12T) — оценка, не замер
Измерено лишь на Xeon E5-2666 v3. Пересчёт: 6 потоков на Xeon = 139 мс/итерацию. Zen 2 против Haswell: IPC выше примерно на
25–30 %, частота при 6-ядерной нагрузке ~4,0 ГГц против ~3,2 ГГц all-core у Xeon (+25 %), 12 потоков (SMT) поверх 6 ядер дают
в таких цепочках зависимостей +10–25 %. Ограничение: L3 4500 — 8 МБ (рабочее множество ≈ 120–150 МБ: шаблоны 8×460 800×4 Б
на 5 систем + поля), память двухканальная DDR4 (≈ 40 ГБ/с против ~68 у Xeon): выигрыш на этом может быть меньше.
Итого: **~80–110 мс/итерацию** (грубо ×0,6–0,8 от 139 мс) → u3_heat 191 итерация ≈ **15–21 с**, одно решение штиля/6 м/с 11–22 с,
пара (mech + heat, 422 итерации) ≈ **34–46 с**. Допущения: частоты и IPC по спецификациям; неопределённость ±30 %.

## Где запас (чтение кода, без переделки; оценки выигрыша — оценки)
Оценка по подсчёту: итерация = 18 полных прогонок импульса (2 × 3 компоненты × 3 направления) + 24 прогонок тепла (4 × 2 скаляра × 3) +
≈ 5 прогонок V-цикла + 60 прогонок грубого уровня ≈ 47 полных прогонок × 460 800 клеток = 21,7 млн клеточных прогонок на итерацию.
На 1 потоке 603 мс/итерацию (замер AC-R4, `out/mv/ongudai_d400_u3_heat_release_t1.json`; в AC-R3 было оценкой ≈ 690) → ≈ 28 нс ≈ 81–97 тактов (2,9–3,5 ГГц) на клетку·прогонку — на порядок больше, чем даёт арифметика (≈ 16 flop, 2 деления,
≈ 55 Б трафика): время определяют зависимость по линии (деления) и неудобные обращения к памяти. Доля фаз (оценка — по GPU-разбивке
итерации из picard.md): импульс ~35 %, тепло ~30–40 %, V-цикл ~25–30 %.

| # | Находка | Где | Оценка выигрыша |
|---|---|---|---|
| 1 | Два деления на клетку в прямом ходу Томаса (`cc/den`, `(r-a*dprev)/den`); одно обратное `1/den` + два умножения | `lines.rs::sweep_dir` | 10–25 % (деление ~13–20 тактов в цепочке зависимостей) |

| 3 | Линии по y и z идут шагом `nx·4` и `nx·ny·4` ≈ 38 КБ: каждая клетка — новая строка кэша и страница. Вести пачку соседних линий вместе (8 по x = 256 Б) и/или блокировать | `lines.rs::sweep_dir`, dir 1 и 2 | 1,5–2× на y/z-прогонках (2/3 всех) — оценка |

| 5 | В горячем цикле `if c != 0.0`, проверка границ на каждого из 4 соседей, `unsafe get` — не векторизуется; вынести границы из внутреннего цикла, соседей — срезами | `lines.rs:73–86` | 10–20 % |
| 6 | Нет SIMD: рекуррентность по линии не векторизуется, только поперёк линий (находка 3, 4–8 линий в регистре AVX2) и в поточечных ядрах; сборка — базовый x86-64. `multiversion` — AC-R4 | вся сборка, `kernels.rs` | 1,3–2× при перестройке на поперечный SIMD с AVX2 — оценка |

Лишних копий и выделений `Vec` внутри итерации нет: буферы создаются в `Picard::new`/`Mg::new`. Суммарно находки 1–5 и 7–8 дают
оценку ×1,6–2,5 на этих же ядрах без SIMD, с перестройкой под AVX2 (6) — до ×3–4; на 18 потоках это ~25–50 мс/итерацию —
оценка, не замер. Оптимизация — отдельная задача после шлюза; в AC-R3 новых попыток ускорения не делалось.

## Вывод (жизнеспособность по числам)
- **Корректность — да.** Онгудай 400 м, все 4 случая: итерации как у эталона f64 (191/231/201/131), u_rel ≤ 4,3e-5 (допуск 1e-3),
  th_abs ≤ 3e-5 К (допуск 0,05 К), ∇·u совпадает с эталоном; результат не зависит от числа потоков. Расхождение штиля 1,8e-2 было

## Отличия от эталона и допущения

- Счёт `f32`, как GPU игры; **дивергенция ∇·u считается разностями в f64** и округляется в f32 (иначе
  при почти бездивергентном поле ошибка вычитания f32 сравнима с самой ∇·u: 1,04e-5 на flat_wind
  против допуска 1e-5). Редукции (суммы, нормы) — в f64 фиксированными блоками: результат не
  зависит от числа потоков.
- Проверка типов клеток/граней не нужна: типы читаются из фикстуры (подготовка не портирована).
- Второй порядок переноса (`adv2`) выключен в эталоне и не портирован; `omega_u = 1`, окна (nest) — нет.
- Тёплый старт и окна не портированы (шаг 0). Без нагрева (Q ≡ 0) проход θ′_d пропускается: θ′_d ≡ 0 точно, как в эталоне.
- Первая проверка — после `check_every` итераций плюс `pre_steps` предварительных (1 у случаев Онгудая: эталон делает шаг при записи графа и считает его в `it`; у `ref/` — 0): `it` = 10, 20, … либо 11, 21, … как в `history` случая.
- Параметры берутся из JSON случая; `Cd = (κ / ln(Δz/2 / z0))²`, κ = 0,4 (совпадает с `cd` фикстуры).

## multiversion против AC-R3 (AC-R4)

Задание: крейт `multiversion` на горячих ядрах, без перестройки алгоритма (находки «Где запас» 1–5, 7–9 не делались; решение
пользователя 2026-10-24: CPU без AVX2 не поддерживаем — базовая ветка не оптимизировалась и не замерялась, она лишь собирается и работает).
Код — коммит `d103aee2a` (`host.git` во всех файлах `out/mv/*.json`).

**Итог: ускорения нет — ×1,00–1,03 по полному solve, в пределах разброса замера (~2 %).** Корректность сохранена: итерации
как у эталона и AC-R3, отклонения того же порядка. Выигрыш от AVX2+FMA на этих ядрах ожидаем не был и не получен: узкое
место — деление в цепочке зависимостей прогонки Томаса и неудобные обращения к памяти (см. «Где запас»), а не арифметика.
Векторизация поперёк линий (находка 3) — перестройка алгоритма, отдельная задача.

### Что сделано

- Зависимость `multiversion = 0.9` (цели `x86_64+avx2+fma` = x86-64-v3 и база; выбор ветки во время работы, кэш в атомике внутри
  крейта). На aarch64 и в сборке с фичей `base_only` атрибутов нет — один вариант кода (без FMA). Без `RUSTFLAGS`, `.cargo/config`
  и сборки под процессор сборщика.
- Ядра под `multiversion` — тела, которые считают пачки клеток, а не замыкания `rayon`: замыкание внутри функции с
  `target_feature` собирается отдельной функцией и свойства не наследует, поэтому горячий цикл вынесен в именованную функцию, а
  `par_iter` — в обёртку (раздача по `par_chunks_mut`, 512–1024 клеток на задачу). Это единственная структурная правка.

| ядро | файл | единица диспетчера | FMA |
|---|---|---|---|
| прогонка Томаса по линии `solve_line` (из `sweep_dir`) | `lines.rs` | линия (50–98 клеток) | да: `r -= c·x`, `b − a·c′`, `d′ − a·d`, обратный ход |
| невязка `resid_chunk` | `lines.rs` | 1024 клетки | да |
| восстановление/перенос V-цикла `restrict_chunk`, `prolong_chunk` | `mg.rs` | 1024 клетки | нет |
| местное K `kloc_chunk` | `kernels.rs` | 512 клеток | нет |
| шаблоны `build_mom_chunk`, `build_heat_chunk` | `kernels.rs` | 512 клеток | нет |

FMA — `f32::mul_add` через `util::fmadd::<FUSED>` (`FUSED = true` только в ветке `avx2+fma`, где это одна инструкция
`vfmadd`; в базе — умножение и сложение с двумя округлениями, как в эталоне; иначе `mul_add` ушёл бы в программный `fmaf`).
Это единственное, что меняет результат (округление).

### Какая ветка выбрана и как проверено

- `picard isa` печатает `isa_branch=x86_64+avx2+fma` на Xeon E5-2666 v3 (тот же диспетчер, что у ядер); в логе замера — то же.
- В бинаре есть `solve_line_avx2_fma_version`, `resid_chunk_avx2_fma_version`, `build_*_chunk_avx2_fma_version` (`nm`); в первых двух —
  инструкции `vfmadd` (`objdump`: 6 и 7). Автовекторизации ядер с `ymm` почти нет (2 инструкции в `build_heat_chunk`): ветвистые
  скалярные циклы компилятор не векторизует.
- Базовая ветка (на машине без AVX2 мы её запустить не можем): сборка `--features base_only` (без диспетчера, `isa_branch=base`)
  проходит `tolerance.py` на 4 фикстурах (worst 6,2e-4) и считает u3_heat; эквивалентность самой ветки `_ => base` внутри
  `multiversion` — по построению макроса, не по запуску на процессоре без AVX2 (такого нет).

### Сравнение (Xeon E5-2666 v3, замок cpu 18 слотов, `CPUQuota=1800%`)

Замер — один заход каждой точки (как в AC-R3), разброс повтора на одинаковом бинаре ~2 % (ниже), поэтому ускорение <×1,03

Сверка с эталоном: итерации совпадают с эталоном и AC-R3 на всех случаях и потоках (191/231/201/131); отклонения того же порядка,

### Почему нет выигрыша и что даст

- Рекуррентность прогонки Томаса: `den = b − a·c′` → деление `c/den` → следующая клетка; FMA сокращает цепочку на ~3 такта из ~25, а
  деление (13–20 тактов, `vdivss`) остаётся. 2–3 % — потолок такого изменения.
- Пошаговые ядра (`build_*`, `kloc`) ветвисты (тип клетки, направление апвинда, 6 граней) и ограничены памятью: ~55 Б на клетку.
- Достижимо только структурными правками: SIMD по 8 соседним линиям (находка 3, 6), кэш `cp`/`1/den` (2), порядок обхода (3). Они — отдельная задача.

## API (R6)

Библиотека даёт `picard_rs::api` (контракт R6 v1); CLI `solve`/`bench --solve` — тонкая обёртка над ней.

```rust
pub struct SolveOpts { pub threads: usize, pub max_iters: usize }   // Default: threads 0, max_iters 2000
pub fn solve(case: &Case, opts: &SolveOpts) -> anyhow::Result<Solved>
pub struct Solved { pub out: SolveOut, pub timing: Timing, pub dev: Dev, pub picard: Picard, pub pool: rayon::ThreadPool }
```

```rust
let case = picard_rs::case::Case::load(path)?;
let r = picard_rs::api::solve(&case, &SolveOpts { threads: 8, ..Default::default() })?;
println!("{} iterations, u_rel {:e}", r.out.iters, r.dev.u_rel);
```

- Каждый вызов строит свой `rayon::ThreadPool` (`pool.install`), глобальный пул не используется; одновременные
  вызовы независимы (`tests/api.rs`). Итерации и поля не зависят от числа потоков; поля — `Solved.picard.f`.
- `threads = 0` — все логические ядра (`available_parallelism`, при ошибке 1); в CLI `--threads 0` тоже (раньше = 1).
