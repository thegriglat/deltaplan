# picard_rs — Пикар 400 м на Rust (шаг 0, AC-R1, AC-R3)

Порт одной итерации Пикара AM-01 (`tools/research/air3d/air.py`, ядра CuPy) на Rust:
`f32`, плоские массивы с ореолом в раскладке R1 (вход читается без перестановок), явный
`rayon::ThreadPool`. Подготовка случая (рельеф, K_b, губки, нагрев) **не** портирована — берётся
из фикстуры R1. Код игры и эталон не менялись. Контракты — `docs/contracts/air-cascade.md` (R1, R2, R3 v3).

## Структура

| Модуль | Что |
|---|---|
| `case.rs` | чтение `<случай>.json` + `.bin` (R1); `Consts` — постоянный вход (типы, губки, K_b, Q, проводимости проекции, границы) |
| `kernels.rs` | поточечные ядра: `apply_bc`, `kloc` (местное K), `build_mom` (шаблон импульса), `build_heat` |
| `lines.rs` | зебра-прогонки Томаса по линиям (z, x, y), невязка `resid` |
| `mg.rs` | V-цикл проекции: огрубление по x, y, прогонки по z, самый грубый уровень 20×(z, x, y) |
| `solver.rs` | `Picard` — состояние итерации (`Fields`, шаблоны, рабочие буферы): `outer_step`, `project`, `residuals`, `solve`, `finalize` |
| `blocks.rs` | сверка блоков одной итерации с R1 (как `tests/atmosphere/test_air_picard_gpu.gd`) |
| `report.rs` | результат R2, отклонение от `sol_*` |

Шаблон — строка `[f32; 8]` (C0…C6, b) на клетку: прогонка читает коэффициенты клетки одним
доступом. Параметры (`dtau_u`, `mom_sweeps`, …) берутся из `params` JSON случая. Пул потоков
создаётся в `main` из `--threads` и вызывается через `pool.install`; глобального состояния нет.
Единственный `unsafe` — `util::Shared`: запись в непересекающиеся линии одного цвета зебры
(соседи вне линии принадлежат другому цвету и в проходе не пишутся).

## CLI и воспроизведение

```
cargo build --release --manifest-path tools/research/air_cascade/picard_rs/Cargo.toml
F=tests/atmosphere/fixtures/air_model/ref
picard blocks $F/flat_wind.json $F/agnesi.json $F/heated_slope.json $F/saddle.json   # таблица и max_block_rel=…
picard solve  $F/saddle.json --threads 8 [--max-iters 2000] [--out out/saddle_release_t8.json]
picard bench  $F/saddle.json --threads 1,4,8,16 [--iters 20] [--out-dir out]   # --solve: полное решение вместо K итераций
picard solve  <случай> --tol-scale 0.03 --diag    # диагностика: ужесточить критерий, таблица отклонения по полям
python3 contract/check_contract.py --results out && python3 contract/tolerance.py out/*_release_t8.json
```

## Онгудай 400 м: Rust против эталона (AC-R3)

Случаи — `~/data/air_cascade/ongudai/ongudai_d400_{u3_heat,u3_mech,u0_heat,u6_heat}.{json,bin}` (AC-R2, вне git, 38 МБ каждый;
сетка 96×96×50 = 460 800 клеток, 400 м; 381 458 воздушных). Эталон — AM-01 f64 на CuPy (RTX 4070 SUPER), `t_ref_s` в JSON случая.
Машина замера: Xeon E5-2666 v3 (Haswell, 10 ядер / 20 потоков, 2,9 ГГц, макс. 3,5; L3 25 МБ), `rustc` release (fat LTO, без
`target-cpu`, базовый x86-64: SSE2, без AVX2/FMA). Замеры — под замком cpu (вес 18 из 18 слотов, `CPUQuota=1800%`), машина
свободна от других замеров. Воспроизведение:

```

cargo build --release --manifest-path $P/Cargo.toml

done; done
.dpcli/dpcli lock cpu <ID> --no-tmux -- $P/target/release/picard bench --solve $D/ongudai_d400_u3_heat.json --threads 4 --out-dir $P/out/bench   # также 10, 12, 14, 16, 20
python3 $P/contract/tolerance.py --iters-tol 20 $P/out/ongudai_d400_*_release_t8.json
python3 $P/out/table.py     # таблицы ниже
```

12 основных результатов (R2) — `out/ongudai_d400_<случай>_release_t{6,8,18}.json`; точки 4/16/20 потоков — `out/bench/`.
`host.git` в JSON — `318c88b73` (коммит кода, с которого сняты все результаты, кроме `bench/`, где он тоже `318c88b73`). Время «всего» — от начала подготовки случая в процессе до финала (без чтения `.bin` с диска и запуска процесса);
оно включает подготовку (`setup_s` 0,4–0,9 с: инициализация состояния, шаблоны, V-цикл), итерации и проверки невязок.
Отдельно измеренного времени по фазам нет; «мс/итерацию» — среднее по итерациям без проверок.

Итерации совпадают с эталоном **точно** (191/231/201/131). Точность не зависит от числа потоков (редукции в f64 фиксированными
блоками): таблица «сверка» — одна на все потоки.

### Штиль (u0_heat): был u_rel = 0,018 — ошибка счёта итераций, не схемы
Первый запуск дал u_rel 1,8e-2 (ограничено допуском 1e-3). Разбор: максимум отклонения диффузный (rms 1,2e-3 м/с, макс 4,5e-2 м/с
при u0 = 2,57 м/с; 99,9-й процентиль 1,5e-2), а не локальный; отклонение падало на порядок за 10 итераций (190 → 200: 0,18 → 0,018):
решение в этой точке ещё быстро движется (невязка у критерия, не неподвижная точка), поэтому разница в **один шаг** даёт ~1e-2.
Причина: эталон `air.py::solve` при записи графа CUDA делает один выполненный шаг (`capture()` → `outer_step(); outer += 1`),
так что `it = 11, 21, …` в `history` — это 11, 21, … фактических шагов, а Rust делал 10, 20, … (и остановился на 200 вместо 201).
Исправлено: число предварительных шагов берётся из `history[0].it mod check_every` (0 для случаев `ref/`, 1 для Онгудая;
`Criterion::pre_steps`). После этого u_rel штиля 4,3e-5, u3: 1,7e-6 (до исправления 2,7e-4), итерации совпали. Остаточные 4e-5
штиля — f32 против f64 при медленно затухающем режиме; запас к допуску 23×. Дополнительно проверено: `--tol-scale 0.03` (критерий
строже в 33 раза) на штиле за 1200 итераций не сошёлся (status max) — штилевая конвекция без неподвижной точки в пределах
1200 итераций; это свойство модели (эталон останавливается по тому же критерию), не Rust.

### Сравнение с GPU игры (ориентир, не требование паритета)
GPU игры — `docs/guide/air-model-gpu/picard.md` (RTX 4070 SUPER, та же сетка 98×98×52 с ореолом, f32, после А1): итерация
4,2 мс (GPU-метки), решение 3 м/с с нагревом 130 итераций — GPU 0,58 с, стена 1,1–2 с («кадры»/«загрузка»), пара 400 м — 2,0 с.
Числа итераций игры (130, пара 190) относятся к другим параметрам/старту игры и **не** равны итерациям фикстуры
(191/231), так что сравнивать по-итерационно:

| | мс/итерацию | к GPU игры (4,2 мс) |
|---|---|---|
| GPU игры, f32 | 4,2 | 1× |
| CuPy f64 (эталон, t_ref/итерации, с проверками) | 9,122 с / 191 = 48 | 11× |
| Rust, 18 потоков | 82,4 | 20× |
| Rust, 8 потоков | 102 | 24× |
| Rust, 6 потоков | 139,5 | 33× |

Решение целиком (u3_heat): Rust 16,6 с (18 п.), 20,5 с (8 п.), 28,0 с (6 п.); эталон CuPy f64 9,1 с; GPU игры 0,6 с GPU-время
(стена 1–2 с) на 130 итераций — на 191 итерации ≈ 0,8 с GPU. То есть Rust на CPU медленнее GPU игры в ~10–25× по стене
(20–33× по итерации).

### Оценка для Ryzen 5 4500 (Zen 2, 6C/12T) — оценка, не замер
Измерено лишь на Xeon E5-2666 v3. Пересчёт: 6 потоков на Xeon = 139 мс/итерацию. Zen 2 против Haswell: IPC выше примерно на
25–30 %, частота при 6-ядерной нагрузке ~4,0 ГГц против ~3,2 ГГц all-core у Xeon (+25 %), 12 потоков (SMT) поверх 6 ядер дают
в таких цепочках зависимостей +10–25 %. Ограничение: L3 4500 — 8 МБ (рабочее множество ≈ 120–150 МБ: шаблоны 8×460 800×4 Б
на 5 систем + поля), память двухканальная DDR4 (≈ 40 ГБ/с против ~68 у Xeon): выигрыш на этом может быть меньше.
Итого: **~80–110 мс/итерацию** (грубо ×0,6–0,8 от 139 мс) → u3_heat 191 итерация ≈ **15–21 с**, одно решение штиля/6 м/с 11–22 с,
пара (mech + heat, 422 итерации) ≈ **34–46 с**. Допущения: частоты и IPC по спецификациям, не по замеру; без привязки потоков;
неопределённость ±30 %.

## Где запас (чтение кода, без переделки; оценки выигрыша — оценки)
Оценка по подсчёту: итерация = 18 полных прогонок импульса (2 × 3 компоненты × 3 направления) + 24 прогонок тепла (4 × 2 скаляра × 3) +
≈ 5 прогонок V-цикла + 60 прогонок грубого уровня ≈ 47 полных прогонок × 460 800 клеток = 21,7 млн клеточных прогонок на итерацию.
На 1 потоке ≈ 690 мс → ≈ 32 нс ≈ 95 тактов на клетку·прогонку — на порядок больше, чем даёт арифметика (≈ 16 flop, 2 деления,
≈ 55 Б трафика): время определяют зависимость по линии (деления) и неудобные обращения к памяти. Доля фаз (оценка — по GPU-разбивке
итерации из picard.md): импульс ~35 %, тепло ~30–40 %, V-цикл ~25–30 %.

## Вывод (жизнеспособность по числам)
- **Корректность — да.** Онгудай 400 м, все 4 случая: итерации как у эталона f64 (191/231/201/131), u_rel ≤ 4,3e-5 (допуск 1e-3),
  th_abs ≤ 3e-5 К (допуск 0,05 К), ∇·u совпадает с эталоном; результат не зависит от числа потоков. Расхождение штиля 1,8e-2 было
  ошибкой счёта итераций (смещение на 1 шаг), исправлено. Поле у старта (crop, центры клеток): max |Δ| u, v, w ≤ 2,6e-5 м/с, θ′ ≤ 9,1e-6 К
  по всем четырём случаям; невязки по итерациям совпадают с `history_ref` в пределах 0,2 %.
- **Скорость.** Полное решение 11,6–17,4 с на 18 потоках, 14,4–21,4 с на 8, 19,2–28,8 с на 6 (Xeon); пара — 33 / 41 / 55 с.
  Ряд ограничений: масштабирование до 8 потоков эффективно (0,9), дальше упирается в физические ядра/память (82–83 мс при 16–20 потоках).
  Для Ryzen 5 4500 оценка 15–21 с на решение и 34–46 с на пару (оценка, ±30 %).
- Против GPU игры (4,2 мс/итерацию, решение ~1–2 с) CPU-вариант медленнее в 20–33× по итерации и в ~10–25× по стене. Паритет не требуется
  (решение пользователя 2026-10-24: при успехе GPU-решатель Пикара убирается). Запас по коду на оценку ×1,6–2,5 без SIMD (таблица выше)
  оставляет достижимый диапазон для слабой машины порядка 8–15 с на решение — оценка, замера нет.
- Чего нет: 200 м и меньше (не измерялось; затраты ×4–8 по клеткам и ×~2 по итерациям), тёплый старт и окна (шаг 0 их не переносил),
  реальной Zen 2 (только пересчёт).

## Отличия от эталона и допущения

- Счёт `f32`, как GPU игры; **дивергенция ∇·u считается разностями в f64** и округляется в f32 (иначе
  при почти бездивергентном поле ошибка вычитания f32 сравнима с самой ∇·u: 1,04e-5 на flat_wind
  против допуска 1e-5). Редукции (суммы, нормы) — в f64 фиксированными блоками: результат не
  зависит от числа потоков.
- Проверка типов клеток/граней не нужна: типы читаются из фикстуры (подготовка не портирована).
- Второй порядок переноса (`adv2`) выключен в эталоне и не портирован; `omega_u = 1`, окна (nest) — нет.
- Тёплый старт и окна не портированы (шаг 0). Без нагрева (Q ≡ 0) проход θ′_d пропускается: θ′_d ≡ 0 точно, как в эталоне.
- Первая проверка — после `check_every` итераций плюс `pre_steps` предварительных (1 у случаев Онгудая: эталон делает шаг при записи графа и считает его в `it`; у `ref/` — 0): `it` = 10, 20, … либо 11, 21, … как в `history` случая.
- Параметры берутся из JSON случая; `Cd = (κ / ln(Δz/2 / z0))²`, κ = 0,4 (совпадает с `cd` фикстуры).
