# Пачка 1a (PR-6): прогонки пачками линий

Изменён только `src/lines.rs` (pub-сигнатуры те же). Арифметика каждой линии и порядок операций прежние; `compare_r2.py before after` -> `identical=4/4`.

## Что сделано
- Задача rayon = блок соседних линий (по первому свободному индексу: `BLOCK = [4, 32, 32]` для x/y/z, т. е. до 2/16/16 линий своего цвета) в одной плоскости; задач только по линиям нужного цвета (раньше половина задач выходила по чётности).
- Прямой ход ведётся по всем линиям пачки сразу: рабочие буферы `c'`, `d'` — локальные на задачу, раскладка `[позиция по линии][линия пачки]` (обращения подряд; независимые цепочки делений перекрываются). Массивы размера сетки (`Scratch.cp/dp`) не нужны, `Scratch` — пустой маркер.
- Границы вне внутреннего цикла: линии с несуществующим внеплоскостным соседом решаются отдельно (флаги `ok`), у внутренних линий проверок нет; первая и последняя клетка линии — отдельные инстанции (`FIRST`/`LAST`), а не `m > 0`/`m + 1 < n` в цикле; `c != 0` — выбор (select) без пропуска чтения, остальное как было. Нулевой коэффициент по-прежнему не меняет `r`.
- Границы блоков кратны 64 байтам `f32` (без ложного разделения строк кэша между задачами).
- Ловушка: замыкание `step` вокруг `#[inline(always)]`-шага внутри multiversion-функции теряло `target_feature` (fma не инструкция) — 157 мс против 84; решение — макрос вместо замыкания.

## Выбор размера пачки (u3_heat, 8 потоков, мс/итерацию, одиночные прогоны под замком)
1 линия на пачку (`[2,2,2]`) 83,8; `[2,8,8]` 74,9; `[2,16,16]` 72,1; `[4,16,16]` 70,9; `[2,32,32]` 69,9; `[4,32,32]` 69,3 (выбран); `[8,32,32]` 69,4; `[4,32,16]` 70,5. Выше 32 не пробовали (плато). Причина: 16 линий × 96 клеток × 2 буфера × 4 Б = 12 КБ — буферы остаются в L1 (32 КБ), строка кэша шаблона/поля используется пачкой целиком; для x шире 2 линий выигрыша нет (потоков чтения на линию 5).
