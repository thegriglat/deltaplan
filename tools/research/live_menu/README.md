# Замер старта: main и живое меню (LM-1)

## Методика
- Сборка `tools/build.sh linux --release` (копия LM-1), RTX 4070 SUPER, `DISPLAY=:0`, 1920×1080, `--audio-driver Dummy`.
- Три прогона на вариант в одном временном профиле и кеше шейдеров драйвера: 1 холодный, 2–3 тёплые.
- Окно меню: 40 с кадров без ввода (`--perf-menu=40`), рывок = кадр > 50 мс. Затем «Лететь» сигналом `fly_requested`
  (как кнопка) и обычный замер полёта 20 с (`--perf=20`).
- `proto` (`--live-menu-proto`, `scenes/main.gd`): после первого кадра меню `game.start` на `volcano_island/east_cliffs`,
  старт в воздухе (200 м вперёд, 150 м над землёй), ботов 0, автопилот по кругу, камера chase, фон меню скрыт, когда мир готов.
- «Лететь» — на встроенное место без сети (по умолчанию altai в чистом профиле качает рельеф из сети): у `main` —
  `training_island`; у `proto` — то же `volcano_island/east_cliffs`, что за меню (см. «Падение» ниже). Поэтому колонки
  «Лететь» main и proto несравнимы по месту: у proto это переход «мир уже загружен → начало полёта».
- `menu_s`, `world_ready_s` — от запуска процесса (`date` перед запуском).

## Воспроизведение
```
tools/build.sh linux --release
tools/bench/menu_bench.sh build/linux/deltaplan.x86_64 20 3 40   # аргументы: бинарник, секунд полёта, прогонов, окно меню
python3 tools/research/live_menu/check_startup_json.py tools/research/live_menu/startup.json
```
Сырые строки PERF — `raw/`, итог — `startup.json`. Падение proto при смене места:
`build/linux/deltaplan.x86_64 -- --live-menu-proto --perf-menu=10 --perf=5 --perf-menu-swap` → SIGSEGV (код 139).

## Оговорка: машина была перегружена
Во время серии load average 75–86 на 20 ядрах (параллельные задачи других агентов), GPU занят чужим счётом. Абсолютные числа
завышены в разы (до меню main тёплый 12–18 с, в спокойной машине первая серия дала 5–7 с; «Лететь» main 11 с вместо 19–23 с).
Относительная картина устойчива: две серии (в том числе первая, при меньшей нагрузке) дали тот же вывод. Холодный main
85 с и «Лететь» 105 с — перегрузка плюс первый запуск; точные холодные числа нужен повтор на тихой машине (то же скриптом).

## Что видно
1. main: меню — статичный фон, кадр 13 мс, рывков единицы (до 0.5 с при перегрузке), мир не грузится.
2. proto: мир за меню готов через 50–60 с от запуска в тёплом (~25–30 с после показа меню); всё это время главный
   поток отдаёт меню рывки: 230–256 кадров > 50 мс, сумма ~38 с из 40 с окна (то есть меню почти всё окно «ползёт»,
   медиана кадра 71–74 мс, худший 1.5–5 с; в холодном — один кадр ~25 с).
3. После готовности мира продолжается фоновый пересчёт поля воздуха: бот уходит из окон запечённого поля
   (`air_model: ... (сдвиг окон (запечённое поле))`, 13–31 с счёта, `baked=1` в момент готовности), ещё ~25 с рывков;
   в замере его ждали (`menu_air_wait_ms` ≈ 25 с) до «Лететь». Это ровно та нагрузка, что живое меню получит всегда,
   пока бот летает.
4. Где замирает загрузка: подробный профиль этапов — `tools/research/load_profile/README.md`; здесь этапы `game.start`
   (рельеф, объекты мира/OSM, поле воздуха, термики, облака) идут порциями между кадрами на главном потоке — в логе
   «Terrain 2–3 с, WorldObjects 2–3 с, поле 1–3 с (baked), камера/облака»; отдельный разбор по шагам не делался.

## Падение при смене места (находка прототипа)
«Лететь» из живого меню на другое место (volcano_island → altai или training_island) роняет release-сборку в SIGSEGV
во второй загрузке рельефа (после «поля рельефа», до конца WorldObjects) — 100% прогонов. В editor-сборке (debug) падения
нет, но `CityTrees._process` ругается на `height_at` освобождённого рельефа (старые объекты живут во время загрузки нового места).
Тот же переход через обычный `_fly` + `_show_menu` (мир создан обычным «Лететь») не падает; на то же место — не падает.
Проверено без эффекта: без автопилота, на земле, с ботами, `set_flying`, `restart`, отключение 3D, остановка пересчёта воздуха.
Причина не найдена (стек release-сборки без символов), в `main.gd` обхода нет — нужна правка game/world_objects (вне границ LM-1).
