The second pilot of the wind neural network was computed over a night and a day: on mountains the network has not seen, it is 4 times more accurate than the inflow profile and has no systematic bias, but in 10 % of points it is badly wrong — on steep terrain. In parallel the network was built into the game (ONNX on the CPU), and the first flight on it at Askarovo was "flyable". From a pilot's feedback, 1.0.3 (wind model choice) and 1.0.4 (simplified wind as in 0.8.0) were released.

<!--more-->

## Pilot P-2: 360 real terrains

Overnight, the user's answers to the gate's questions: add a steep deferred system — the Southern Alps of New Zealand (15 places); the target for non-converged solutions is the **mean of the late states** (the solver oscillates in weak wind, and the honest target is the mean); do not take places whose square floor is above 3000 m (the solver does not account for height and latitude: density, θ0 and Coriolis are constant — this goes into the risks of the next wave). Result: 360 places — a pool of 300 and 4 deferred mountain systems (Appalachians, Caucasus, Pyrenees, NZ Southern Alps) with 15 each.

Computing the set — 4320 cases in ~8 h on one GPU (the estimate was 10 h). About 20 % did not converge — almost all in weak wind. Training crashed once: counting the channel scale copied the whole target set in float32 and did not fit in 31 GB of memory; fixed by counting in chunks.

Result on the deferred mountain systems (60 m above terrain, converged solutions):

| | network P-2 | inflow profile |
|---|---|---|
| wind error, median / p90 | 0.62 / 1.84 m/s | 2.46 / 7.86 m/s |
| share of "ok" by wind (≤ max(0.3 m/s; 10 %)) | 35 % | 10 % |
| lift < 0.1 m/s (without / with heating) | 78 % / 72 % | 70 % / 62 % |
| mean speed bias at 60 m | +0.008 m/s | +2.32 m/s |

The verdict by the rule from the numbers is "fix the approach". What is visible:
- **there is no bias** in either height or wind strength; the wind overestimate at Ongudai from the first pilot (+14 %) is gone;
- on non-converged cases the network errs at the level of the solver's own scatter (median ratio 0.91);
- even on training places "ok" is only 49 % — it is not only about the data but about the network learning from scratch;
- the curve over the number of places: 25 → 300 places — 0.83 → 0.62 m/s, about −7 % per doubling, no plateau, but data is expensive;
- the network is 13 MB, 21 ms on the CPU with 4 threads.

## Decisions on direction

The user's decisions for the day:
- in the game the solver is replaced by the network, the solver stays offline as a data source; **speed and stability matter more than accuracy** — "better to lie a little than to slow the game down, it is a game after all, not a meteorological weather predictor"; a 10–15 % wind error at a spot is acceptable — a pilot will take it for a gust;
- the pilot's main question is **replaceability**: does the network reproduce the solver within the solver's own error (on Askervein the solver underestimates the speed-up at the summit by 15–20 %, i.e. it is itself off by ±10–20 %);
- in weak wind there may be no stationary field at all (a buoyancy-driven flow is non-stationary — like the Rayleigh–Bénard instability); the network gives a smooth mean — and that is right: variability is provided by thermals and turbulence.

A separate network for thermals is not needed: thermals are already computed from literature formulas (Deardorff, Allen, Holtslag–Boville) on top of the field, and the quantities they need are output by the field network.

## The network in the game

A new branch: a Godot extension with ONNX Runtime (CPU only, Linux and Windows builds), preparation of the network input in GDScript (matches Python to 7·10⁻¹²), a wind field from the network, a settings item "Neural network (experimental)" and a guard for the input's domain of applicability. The "Computing wind from terrain…" stage on network P-2 takes about 4 s, of which the network itself is 56 ms, the rest is field assembly in GDScript (to be sped up later).

The first flight on network P-2, Askarovo: "overall even 'flyable', nothing unusual at all".

## Pilot P-3: physical encoding

A discussion with the user — how to encode the input and output so that the network has less to learn. A plan for the next pilot emerged on the same data, without re-running the solver:
- **the base is linear flow theory** (potential flow via FFT), the network learns only the nonlinear correction (separation, stability, heating);
- the output is **speed-up and turning** relative to the base instead of u and v; the vertical is the **deviation from flow along the slope** (near the ground the flow cannot go through the slope — a boundary condition);
- the input is terrain slopes **at several scales** (at height z the flow feels terrain of scale ~z), **subgrid terrain** from 25 m tiles (a cliff inside a 400 m cell), a **separation mask** behind a lee slope steeper than ~0.3 and its downwind trace;
- packing the height profile with a few principal modes.

Set aside in mind: a triple feature plane with a vertical cut along the wind, the stream function, dimensionless numbers (Froude, Richardson), shallow-water hydraulics for saddles (Bernoulli with continuity), a cascade of 50/25 m windows around the pilot, a batch of cases in the solver (on the computation the GPU is busy with small kernels, not with calculations).

## Releases from a pilot's feedback

A pilot: the game sometimes crashes, and then rolling back to 0.8.0 saves the day — "on 0.8.0 the physics is less plausible, but tolerable for the sake of flying". Then harsher feedback: "Don't torment 1.0. It got worse. Right now 0.8 is the best, practically ideal".

- [1.0.3](/releases/1.0.3/): in settings "Wind over terrain" — "Calculated from terrain" or "Simplified" (the solver on the GPU is not started) ({{< commit 1680475 >}}); "Apogee" by real dimensions. There is no auto-disable after a crash — the user's decision, a settings item is enough.
- Analysis of "what changed since 0.8.0": slope, lee zones, thermals and turbulence in the simplified mode are the same; what changed is the **wind profile with height** — in 1.x it depended on the time of day and cloud cover (in the evening and in overcast weather noticeably stronger at height, in a clear noon weaker than in 0.8.0).
- [1.0.4](/releases/1.0.4/): in the simplified mode the profile is as in 0.8.0 — power-law, α = 0.14, at most ×1.8 of the wind at 10 m, independent of hour and sky ({{< commit 13449e5 >}}).
- The main menu shows the version and the short commit of the build ({{< commit 2d7b6e9 >}}): from a screenshot it is immediately clear which version the pilot is on.

Checked: the pilot's weight and flight choice are kept between launches; when switching between 0.8.0 and 1.x only the choice of new wings that do not exist in 0.8.0 is lost.

## dp: versions 7–10

The agent-process utility went through versions 7–10 in a day: background runs and shared GPU/CPU locks, editing the card of an already issued task, tolerant checking of report keys, acceptance progress. The lesson of the day: `dp gc` deleted the branch and working copy of a module that had already been merged into main but whose tasks were still running — together with the pilot's Python environment. Now gc does not touch a module with unclosed tasks and copies referenced by others ({{< commit a0e21b3 >}}). The future was also discussed: dp has grown into a small task tracker for AI agents; there is no reason to rewrite it in Go yet (speed is not the bottleneck, edits happen every hour), MCP — as a thin layer for frequent commands, if needed.
